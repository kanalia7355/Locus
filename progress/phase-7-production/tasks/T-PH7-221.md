## TASK DEFINITION (Assigned by Orchestrator)

- **Background**:
  - オーナー決定 2026-11-16（`progress/phase-6-extensions/OWNER_DECISIONS.md` テーマ 5）:
    「id と password の発行をしてログインする流れで固まったはず」。MFA は実装しない。
    同記録の【申し送り】で、MFA の代わりに
    **パスワードの最低強度・失敗回数による一時ロック・既存の `must_rotate`・
    ログイン履歴の管理者可視化**を既定にすると定めた。本ジョブは前半 2 つを実装する。
    ログイン履歴は `T-PH7-222`、TLS と本番起動要件は `T-PH7-223` が扱う。
  - いまの強度規則は**長さだけ**である。`backend/app/service.py:576`
    （`_provision` の `14 <= len(password) <= 128`）、`service.py:1004`
    （`rotate` の `len(new) < 14 or len(new) > 128 or current == new`）、
    `service.py:1068`（`recover`）、および `backend/app/main.py:58-60` の
    `Password.new_password`（`min_length=14`）。したがって
    `aaaaaaaaaaaaaa` は現在そのまま通る。
  - いまの失敗回数制御は `service.py:911-920` の `_limit` だけで、これは
    **プロセス内メモリ上の 60 秒窓**（`self.limits`、`login` では
    `_limit("peer:"+peer, 20)` と `_limit("user:"+digest(username), 5)`）である。
    再起動で消え、60 秒待てば何度でも再開できるので、
    **長時間かけた総当たりは止まらない**。`tests/test_security.py:111-136` が
    この 60 秒窓の 429 を固定しているので、その振る舞いは壊さないこと。
  - `must_rotate` は既存の仕組みをそのまま使う（発行時と管理者によるリセット後の
    初回ログインで必ず変更させる。**定期変更の強制ではない**）。本ジョブで
    `must_rotate` の意味を変えないこと。
- **Implementation Details**:
  1. **強度規則**を `backend/app/password_rules.py`（新規）に 1 か所だけ置き、
     `_provision`・`rotate`・`recover` の 3 経路すべてがそれを呼ぶ。
     Pydantic の `min_length` は入口の便宜であって規則の実体にしない
     （サービス層で必ず再検査する）。規則は次のとおり:
     - 長さ 14〜128（既存のまま）。
     - 小文字・大文字・数字・記号の 4 種のうち **3 種以上**を含む。
     - 利用者 ID を（大小無視で）含まない。
     - 同一文字の 5 連以上（`aaaaa`）、ASCII の連続 5 文字以上（`abcde` / `12345`）を含まない。
     - `backend/app/data/weak_passwords.txt`（新規、オフライン同梱）に
       **完全一致**（大小無視・前後空白除去）するものを拒否する。部分一致にしないこと。
       部分一致にすると既存テストの資格情報（`tests/conftest.py:18-21` の
       `Temporary-password-01!` 等）が全滅する。
  2. 拒否は既存の作法に合わせ `fail(422, ...)` の日本語メッセージで返す。
     **入力されたパスワードそのもの・その長さ・その一部をメッセージや
     ログ・監査行に出さないこと**。満たせなかった規則の種類までは返してよい。
  3. **一時ロック**を DB に持たせる。新規テーブル（例 `login_throttle`）に
     `user_id`（未知 ID の場合は `digest(username)` のみ。生の文字列を入れない）、
     `failures INTEGER`、`locked_until REAL`、`last_failure REAL` を持ち、
     `service.py:163-477` の `executescript` に `CREATE TABLE IF NOT EXISTS` で追加する
     （既存 DB をそのまま開けること。既存の追加移行の作法に合わせる）。
  4. ロックの規則:
     - 連続失敗が **閾値（既定 10 回）**に達したら **15 分**ロックする。
       閾値と時間は定数として 1 か所に置き、根拠をコメントに書く。
     - 成功ログインで `failures` を 0 に戻す。
     - `locked_until` を過ぎたら**自動で解ける**。管理者の操作を必要としない。
     - **ロック中の追加失敗で `locked_until` を延長しない**（下記 5 の理由）。
     - 管理者による明示的な解除経路を 1 つ用意し、`_audit` に記録する
       （`account.unlock`）。これは自動解除の代わりではなく併設。
  5. **他人を締め出す道具にしないこと**（本ジョブの要点）。ID だけ知っていれば
     誰でも他人のアカウントを失敗させられるので、次の 2 点で有限時間に抑える:
     - ロックは**絶対時刻の期限つき**で、期限到来で自動解除される。
     - **ロック中の失敗は期限を延ばさない**。延長式にすると、攻撃者が 15 分ごとに
       1 回失敗させるだけで対象を恒久的に締め出せる（これが実装してはならない形）。
     この 2 点はテストで固定する（受入条件 4）。
  6. 利用者 ID の存在を漏らさない。ロック中の応答は、未知 ID・既知 ID・
     ロック中のいずれでも**同一の本文と同一の状態コード**にする
     （`service.py:953-954` の既存方針「Do not expose whether an account exists」に従う）。
     ロック中であることを本人に知らせる文面を出したい場合は、
     **ID と正しいパスワードが一致したときだけ**出すこと。
  7. 既存の `_limit` による 60 秒窓は**残す**。DB のロックは長期の総当たり用、
     `_limit` は瞬間的な連打用で、役割が違う。
