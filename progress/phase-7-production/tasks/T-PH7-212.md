  3. 方言変換を純粋関数として切り出す（テスト可能にするため、engine 内に埋め込まないこと）。
     少なくとも次を扱う。
     - 占位子 `?` → `%s`。文字列リテラル内の `?` を書き換えないこと
       （`service.py` には日本語メッセージを含む SQL は無いが、将来の混入で壊れる経路なので
       テストで固定する）。
     - 型: `INTEGER`（真偽として使っている列を含む）・`REAL`（Unix 秒）・`TEXT` の対応を決める。
       `REAL` は `DOUBLE PRECISION` とし、**時刻を `timestamptz` に変えないこと**。
       `service.py` は 29 箇所で `time.time()` の float を書き、API も float を返しており、
       型を変えると応答の形が変わる。

     - `CREATE TRIGGER ... BEGIN ... END`（425〜439 行目の `membership_role_sync` /
       `membership_role_delete`）→ PostgreSQL では関数 + トリガに書き換える。
       意味（`memberships` への書き込みを `membership_roles` に写す）を変えないこと。
     - `BEGIN IMMEDIATE` → `BEGIN ISOLATION LEVEL SERIALIZABLE`。
       直列化の担保がアプリ側の `RLock` から DB 側に移るため、
       直列化失敗（`serialization_failure`）時の扱いを決めて実装すること
       （既定は再試行せず `StorageError` として上げ、呼び出し側の 5xx に任せる。
       黙って再試行すると、監査行や課金に相当する副作用が二重に走る）。
     - `PRAGMA table_info` 相当は `information_schema.columns` への問い合わせにする。

     `PostgresEngine`、未設定なら従来の `SqliteEngine`。既定は SQLite のままで、
     設定しない限り開発環境の挙動は一切変わらないこと。

     平文パスワードを含む URL のログ出力禁止）。`main.py` の既存の
     ローカル専用ガード（210〜215 行目の `ALLOW_CLOUD_EGRESS` / `LOCAL_ONLY_MODE` 検査）を
     緩めないこと。接続先ホストが loopback / 社内アドレス以外の場合の扱いを決め、
     決めた規則をテストで固定する（オーナー決定テーマ 5 の「社内ネットワーク内想定」）。
  5. 移行手順を `docs/MIGRATION_POSTGRES.md` に書き、**手順の中身をコード化**する。
     `storage.py` または engine に `export_snapshot(engine) -> dict` と
     `import_snapshot(engine, snapshot)` を置き、SQLite から読み出した全テーブルを
     engine 非依存の中間表現にしてから投入する形にする。
     外部キーの順序、`documents.grants` などの JSON 文字列列、`chunks` の本文、
     `audit` の全行を落とさないこと。移行後に件数とチェックサムを比較する検証手順を含める。
  6. **検索方式は本ジョブで変えない**。現在の語彙一致は SQL ではなく Python 側にある
     （`service.py` 2638〜2662 行目の `send()`。語の部分一致と日本語の文字 2-gram を
     数えて上位 5 件の chunk を採る。`related()` 2135 行目、`documents()` 2092 行目も同様に
     Python 側の照合）。SQLite の FTS5 は使っていないので、engine を替えても
     検索結果は変わらない。全文検索（`tsvector`）・ベクトル検索（`pgvector`）の採用は
     **別ジョブ**とし、本ジョブでは入れないこと。この事実を REPORT に明記する
     （`DATA-013` の「索引技術」部分は本ジョブでは閉じない）。
