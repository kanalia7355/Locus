# Task `T-PH7-212`: 本番ストアの PostgreSQL engine と移行手順（`DATA-013`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `DATA-013`。オーナー決定 2026-11-16 テーマ 5「postgres の方が良いのでは」
  （`progress/phase-6-extensions/OWNER_DECISIONS.md` 157 行目:
  「本番ストアは PostgreSQL。SQLite は開発・プロトタイプ用として残す」）。
- **Background**:
  - `T-PH7-211` で `backend/app/storage.py` に engine の継ぎ目ができている前提のジョブ。
    本ジョブは継ぎ目の裏側に PostgreSQL 実装を足すだけで、`service.py` の
    SQL 発行箇所（`with self.db()` 62 箇所）の構造は変えない。
  - **このリポジトリには PostgreSQL の試験設備が一切ない**ことを確認した:
    `pyproject.toml` の依存は `jsonschema` / `PyYAML` / `cryptography` と dev 一式だけで
    `psycopg` 系は無い。`backend` `tests` `scripts` `infra` `jobloop` に
    `postgres|psycopg|asyncpg` の出現は無い（`docs/` の設計記述のみ）。
    `infra/` は `README.md` 1 枚で、compose も CI のサービスコンテナも無い。
    オフラインが規約なのでドライバの新規導入（`pip install`）も本ジョブでは行わない。
  - したがって「稼働中の PostgreSQL に接続して全テストを通す」ことは本ジョブでは**できない**。
    ただし**オフラインで実行できる部分が大きい**ので、`allowed_paths` と `test_cmd` を
    `未確定` にはしない。オフラインで確かめられるのは、方言変換・スキーマ生成・
    移行手順の純粋部分・設定検証・継ぎ目の契約テストの枠組みであり、
    実機接続を要するのは最後の疎通確認だけである。
- **Implementation Details**:
  1. `backend/app/storage_postgres.py` に `PostgresEngine` を実装する。
     `StorageEngine` Protocol を満たし、`storage.py` と同じ `StorageError` /
     `StorageIntegrityError` に例外を正規化する。
  2. **ドライバの import は遅延させる**。`psycopg` の import は `connect()` の内側に置き、
     モジュールの import 自体はドライバ不在でも成功すること。これにより
     方言変換とスキーマ生成の試験がオフラインで走る。
     `pyproject.toml` には `[project.optional-dependencies]` に
     `prod = ["psycopg[binary]==<固定版>"]` を追記するだけとし、
     既存の `dependencies` と `dev` は変更しない（開発環境には入れない）。
     版の固定は必須。固定版を決められない場合は、その理由を REPORT に書き、
     追記自体を見送って `未確定` と記録すること（嘘の版を書かないこと）。
  3. 方言変換を純粋関数として切り出す（テスト可能にするため、engine 内に埋め込まないこと）。
     少なくとも次を扱う。
     - 占位子 `?` → `%s`。文字列リテラル内の `?` を書き換えないこと
       （`service.py` には日本語メッセージを含む SQL は無いが、将来の混入で壊れる経路なので
       テストで固定する）。
     - 型: `INTEGER`（真偽として使っている列を含む）・`REAL`（Unix 秒）・`TEXT` の対応を決める。
       `REAL` は `DOUBLE PRECISION` とし、**時刻を `timestamptz` に変えないこと**。
       `service.py` は 29 箇所で `time.time()` の float を書き、API も float を返しており、
       型を変えると応答の形が変わる。
     - `INSERT OR IGNORE`（494 行目・432 行目のトリガ内）→ `ON CONFLICT DO NOTHING`。
     - `CREATE TRIGGER ... BEGIN ... END`（425〜439 行目の `membership_role_sync` /
       `membership_role_delete`）→ PostgreSQL では関数 + トリガに書き換える。
       意味（`memberships` への書き込みを `membership_roles` に写す）を変えないこと。
     - `BEGIN IMMEDIATE` → `BEGIN ISOLATION LEVEL SERIALIZABLE`。
       直列化の担保がアプリ側の `RLock` から DB 側に移るため、
       直列化失敗（`serialization_failure`）時の扱いを決めて実装すること
       （既定は再試行せず `StorageError` として上げ、呼び出し側の 5xx に任せる。
       黙って再試行すると、監査行や課金に相当する副作用が二重に走る）。
     - `PRAGMA table_info` 相当は `information_schema.columns` への問い合わせにする。
  4. engine の選択経路を足す。環境変数 `LOCUS_DATABASE_URL` が設定されていれば
     `PostgresEngine`、未設定なら従来の `SqliteEngine`。既定は SQLite のままで、
     設定しない限り開発環境の挙動は一切変わらないこと。
     接続文字列は**検証してから使う**（空文字・`sqlite:` スキーム・
     平文パスワードを含む URL のログ出力禁止）。`main.py` の既存の
     ローカル専用ガード（210〜215 行目の `ALLOW_CLOUD_EGRESS` / `LOCAL_ONLY_MODE` 検査）を
     緩めないこと。接続先ホストが loopback / 社内アドレス以外の場合の扱いを決め、
     決めた規則をテストで固定する（オーナー決定テーマ 5 の「社内ネットワーク内想定」）。
  5. 移行手順を `docs/MIGRATION_POSTGRES.md` に書き、**手順の中身をコード化**する。
     `storage.py` または engine に `export_snapshot(engine) -> dict` と
     `import_snapshot(engine, snapshot)` を置き、SQLite から読み出した全テーブルを
     engine 非依存の中間表現にしてから投入する形にする。
     外部キーの順序、`documents.grants` などの JSON 文字列列、`chunks` の本文、
     `audit` の全行を落とさないこと。移行後に件数とチェックサムを比較する検証手順を含める。
  6. **検索方式は本ジョブで変えない**。現在の語彙一致は SQL ではなく Python 側にある
     （`service.py` 2638〜2662 行目の `send()`。語の部分一致と日本語の文字 2-gram を
     数えて上位 5 件の chunk を採る。`related()` 2135 行目、`documents()` 2092 行目も同様に
     Python 側の照合）。SQLite の FTS5 は使っていないので、engine を替えても
     検索結果は変わらない。全文検索（`tsvector`）・ベクトル検索（`pgvector`）の採用は
     **別ジョブ**とし、本ジョブでは入れないこと。この事実を REPORT に明記する
     （`DATA-013` の「索引技術」部分は本ジョブでは閉じない）。
- **Acceptance Criteria**:
  1. `tests/test_postgres_engine.py` が**ドライバ不在のまま** green であり、次を確かめる。
     - `backend/app/storage_postgres.py` の import がドライバ不在で成功する
       （`psycopg` が import 可能な環境でも、import が `connect()` の内側であることを
       monkeypatch で確かめる）。
     - 方言変換の純粋関数が、`service.py` の実在する SQL を入力にして期待どおりの
       PostgreSQL 文を返す。少なくとも `INSERT INTO audit ...`、
       `INSERT OR IGNORE INTO membership_roles ...`、
       2 つのトリガ定義、`SELECT ... WHERE project_id=? AND status='ready' AND id<>?` を含める。
     - 文字列リテラル内の `?` が書き換えられないこと。
     - `LOCUS_DATABASE_URL` の検証: 空文字・スキーム違い・外部ホストが拒否され、
       拒否の理由がパスワードを含まないこと。
     - 未設定時に `Service` が `SqliteEngine` を選ぶこと。
  2. `tests/test_storage_seam.py` の契約テストを engine でパラメータ化する。
     PostgreSQL は `LOCUS_DATABASE_URL` が**設定されていなければ skip**、
     **設定されていれば skip せず実行**する。設定済みなのに skip した場合は
     テストが失敗すること（skip が黙って常態化すると、未検証を緑と誤読する）。
  3. 移行の往復がオフラインで確かめられる。`export_snapshot` → `import_snapshot` を
     SQLite から SQLite へ通し、全テーブルの件数と全行の内容が一致すること。
     合成データは `tests/conftest.py` のフィクスチャに資料・会話・chunk・監査行を
     足して作る（`Service.seed_synthetic` 2401 行目が使える）。
     さらに、1 テーブルを意図的に落とした欠損スナップショットでは検証が**失敗する**ことを示す。
  4. 既定（`LOCUS_DATABASE_URL` 未設定）で `python -m pytest tests --ignore=tests/e2e -q` に
     退行がないこと。REPORT にその実行結果を記載する（本ジョブのゲートは上記 `test_cmd`）。
  5. `docs/MIGRATION_POSTGRES.md` に、実機で行う残りの確認が**未実施であること**を
     明記した節があること。少なくとも次を列挙する: 実機接続、`SERIALIZABLE` 下での
     同時実行、トリガ移植の等価性、全文検索・ベクトル検索の未着手。
     「PostgreSQL 対応完了」と書かないこと。
  6. 変更は許可パス内に収まる。`pip install` を実行しないこと。既存テストの削除・緩和は禁止。
