# Task `T-PH7-211`: ストレージ層を差し替え可能な継ぎ目に閉じ込める（`DATA-013` / `PROD-005`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Background**:
  - いま `backend/app/service.py` は `Service.__init__`（147 行目）で
    `sqlite3.connect(path, check_same_thread=False, isolation_level=None)` を直接開き、
    `row_factory = sqlite3.Row`・`PRAGMA foreign_keys = ON` を設定し、
    163〜477 行目の `executescript` でスキーマを作っている。
    `db()`（503〜515 行目）は `threading.RLock` を取って `BEGIN IMMEDIATE` を発行し、
    `sqlite3.Connection` を**そのまま呼び出し側へ渡す**。
  - `with self.db() as db:` は 62 箇所、`self.conn` の直接利用は 14 箇所ある。
    SQLite 固有の形がそのまま各所に露出している: `?` 占位、
    `PRAGMA table_info(...)`（479・499 行目）、`sqlite3.IntegrityError` の捕捉
    （591・717・3171・3226 行目）、`sqlite3.Error` の捕捉（1248・1289・1305 行目）、
    型注釈 `db: sqlite3.Connection` と `sqlite3.Row`（20 箇所以上）。
  - 本番ストアは PostgreSQL に決まったが、この状態で engine を足すと
    差分が `service.py` 全体に散り、**挙動変更と差し替えが同じ差分に混ざって**レビュー不能になる。
    本ジョブはその前提工事であり、**PostgreSQL をまだ入れない**。
- **Implementation Details**:
  1. `backend/app/storage.py` を新設し、engine の継ぎ目を定義する。
     - `StorageEngine` Protocol: `transaction()`（contextmanager。入ると書き込み直列化つきの
       トランザクションを開始し、正常終了で commit、例外で rollback）、
       `connection()`（読み書き用のハンドル）、`apply_schema(script)`、
       `ensure_column(table, column, definition)`、`columns(table) -> set[str]`、`close()`。
     - ハンドルは `execute(sql, params=()) -> Cursor` を持ち、`Cursor` は
       `fetchone()` / `fetchall()` で**マッピング風の行**を返す（`row["col"]` と `dict(row)` が
       現在と同じに使えること）。
     - engine 非依存の例外 `StorageError` と、その派生 `StorageIntegrityError` を定義する。
  2. `SqliteEngine` を `storage.py` に実装し、**現在の挙動をそのまま**移す:
     `check_same_thread=False`、`isolation_level=None`、`row_factory = sqlite3.Row`、
     `PRAGMA foreign_keys = ON`、`threading.RLock` による直列化、`BEGIN IMMEDIATE`、
     `path.parent.mkdir(parents=True, exist_ok=True)`。
     `sqlite3.IntegrityError` / `sqlite3.Error` は `StorageIntegrityError` / `StorageError` に
     包み直して送出する（元の例外は `__cause__` に残す）。
  3. `Service.__init__` は engine を受け取れるようにする（`engine: StorageEngine | None = None`、
     既定は `SqliteEngine(path)`）。既存シグネチャ `Service(path, *, scanner=...)` は
     **互換のまま維持**する。呼び出し元は `backend/app/main.py` 217 行目、
     `backend/app/cli.py` 24 行目、`scripts/measure_capacity.py` 278 行目、
     `tests/conftest.py` 17 行目の 4 箇所で、いずれも無改造で動くこと。
  4. `Service.conn` 属性は**残す**。`tests/test_account_toggle.py`・
     `tests/test_admin_project_storage_load.py`・`tests/test_administration_audit.py`・
     `tests/test_agents_registry.py` が `service.conn.execute("SELECT * FROM audit")` の形で
     直接 SQL を投げており（4 ファイル・計 69 箇所）、ここを書き換えると
     本ジョブの差分が「継ぎ目の導入」ではなくなる。`conn` は engine のハンドルを返す
     プロパティにし、SqliteEngine では現在と同じ接続が得られる形にする。
     **これらのテストは SQLite 方言の生 SQL に依存したままになる**ので、
     その事実を REPORT に明記すること（PostgreSQL 側の確認は `T-PH7-212` の契約テストが担う）。
  5. `service.py` から `import sqlite3` を**消す**。捕捉している例外を
     `StorageIntegrityError` / `StorageError` に置き換え、型注釈を継ぎ目の型に替える。
     `PRAGMA table_info` の 2 箇所（479・499 行目）は `engine.columns(table)` 経由にする。
  6. **挙動を変えない**。SQL 文字列・テーブル定義・トリガ・返り値の形・HTTP 状態コード・
     日本語のエラーメッセージ・監査の操作名はいずれも変更しない。
     スキーマの PostgreSQL 化、方言変換、接続設定の追加は本ジョブの対象外（`T-PH7-212`）。
  7. 実行時設定・環境変数・配備手順は増やさない。engine の選択は**コード内の既定値のみ**とし、
     設定経路は `T-PH7-212` で入れる。
- **Acceptance Criteria**:
  1. `import sqlite3` が `backend/app/storage.py` にのみ存在する。
     `tests/test_storage_seam.py` に、`backend/app/service.py`・`backend/app/main.py`・
     `backend/app/cli.py` のソースを読んで `sqlite3` の出現が 0 であることを確かめる
     テストがあること（将来の再混入を落とすため、目視ではなくテストで固定する）。
  2. `python -m pytest tests --ignore=tests/e2e -q` が green。
     既存テストの削除・緩和・skip 追加は禁止。`tests/e2e` は組み上げたフロントエンドと
     ブラウザを要するため本ジョブの検証コマンドから外すが、
     除外によって未確認になった範囲を REPORT に書くこと。
  3. **継ぎ目が実際に全経路を通っている証拠**を `tests/test_storage_seam.py` で示す。
     `SqliteEngine` を継承して 1 点だけ壊した fake engine を 3 種用意し、
     その engine を渡した `Service` では代表的な受入が**失敗する**ことを assert する。
     - commit しない fake（`transaction()` が常に rollback）→ 利用者作成・資料登録が永続しない
     - 1 行目を落とす fake（`fetchall()` の先頭を捨てる）→ 認可または一覧が壊れる
     - 一意制約違反を伝えない fake（`StorageIntegrityError` を送出せず成功を返す）→
       同名利用者の二重作成が拒否されなくなる
     いずれも「本来の受入が落ちる」ことを明示的に assert する。正常 engine では
     同じ受入が通ることも同じテスト内で示し、fake が単に壊れているだけではないことを示す。
  4. `Service(path)` および `Service(path, scanner=...)` の既存 4 箇所が無改造で動く
     （`tests/conftest.py` のフィクスチャが通ること、`backend/app/cli.py` の
     provisioning 経路のテストが通ることで示す）。
  5. 公開 API の応答が 1 バイトも変わっていない。`tests/test_api.py` などの
     完全一致表明が無修正で green であることをもって示す。
  6. 変更は許可パス内に収まる。`backend/app/local_model.py`・`frontend/`・`docs/` は触らない。
