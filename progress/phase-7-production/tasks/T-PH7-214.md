# Task `T-PH7-214`: 監査ログの改ざん防止（追記のみ・連鎖ハッシュ・検証ルーチン）（`DATA-015`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `DATA-015`（監査データの保全。
  `docs/plans/REQUIREMENTS_TRACEABILITY_MATRIX.md` 49 行目）。
  オーナー決定 2026-11-16 テーマ 5（`progress/phase-6-extensions/OWNER_DECISIONS.md` 150・161 行目:
  「ログの改ざん防止はよしなにやって」→「追記のみ・連鎖ハッシュ・取得専用の経路で実装する」）。
  方式の詳細は実装側に一任されている。
- **Background**:
  - `audit` テーブル（`backend/app/service.py` 473〜476 行目）は
    `id, at, actor_id, operation, target_id, outcome` の 6 列。
    `UPDATE audit` と `DELETE FROM audit` は現在コードベースのどこにも無く、
    事実として追記のみだが、**それを強制する仕組みは無い**。
    DB ファイルを直接開けば書き換え・削除ができる。
  - 監査行は **2 系統**から入る。
    1. Python 側の `Service._audit()`（544〜550 行目。`INSERT INTO audit VALUES (?,?,?,?,?,?)`）
    2. **SQL トリガ 9 本**（256・276・296・314・334・356・375・394・413 行目の
       `INSERT INTO audit SELECT lower(hex(randomblob(16))), (julianday('now') - 2440587.5) * 86400.0, 'system', 'delegation.invalidate', g.id, 'ok' FROM ...`）。
     Python 側だけで連鎖ハッシュを計算すると、**トリガ由来の行が連鎖から抜ける**。
     抜けた行をハッシュ無しで許す実装にすると、攻撃者は「トリガ由来に見える行」を
     差し込むだけで検出を迂回できる。この経路を塞ぐことが本ジョブの要点である。
  - `audit` の列を増やす案は採らない。理由は 2 つあり、いずれも実在する経路である。
    1. 上記トリガ 9 本は列名を書かない**位置指定の 6 値 `INSERT`** なので、列を増やすと全て壊れる。
    2. `Service.audit()`（3246〜3252 行目）は `dict(row)` をそのまま返し、
       `GET /api/admin/audit`（`backend/app/main.py` 779 行目）を通って
       画面の操作記録（`frontend/src/App.tsx` 1432 行目の `AdminList kind="audit"`）に出る。
       列を増やすと API の応答の形が変わる。
- **Implementation Details**:
  1. **追記のみを強制する**。`audit` に対する `UPDATE` と `DELETE` を拒否するトリガを足す。
     既存の作法がそのまま使える（245〜247 行目の
     `BEFORE DELETE ON delegation_events BEGIN SELECT RAISE(ABORT, '...'); END;`）。
     既存の削除保持トリガと同じ書き方にすること。
  2. **連鎖ハッシュは別テーブルに持つ**。`audit` の 6 列は変えない。
     - `audit_chain(audit_id TEXT PRIMARY KEY REFERENCES audit(id), seq INTEGER NOT NULL UNIQUE, prev_hash TEXT NOT NULL, row_hash TEXT NOT NULL)`
     - `audit_chain_head`（1 行のみ。`row_count INTEGER NOT NULL, head_hash TEXT NOT NULL`）
     `audit_chain` と `audit_chain_head` にも追記・更新の制約を入れる
     （`audit_chain` は `UPDATE`・`DELETE` 禁止、`audit_chain_head` は 1 行のみ存在できること）。
  3. **連鎖は `AFTER INSERT ON audit` のトリガで埋める**。これで Python 経路と
     トリガ経路の両方が同じ 1 本の経路を通る。SQLite にハッシュ関数が無いので、
     接続時に `conn.create_function("audit_sha256", 1, ...)` で登録した関数をトリガから呼ぶ
     （登録は `T-PH7-211` の `SqliteEngine` 側に置く。PostgreSQL では
     `pgcrypto` の `digest` などに対応させるが、本ジョブでは SQLite のみ実装し、
     対応予定を REPORT に書く）。
     関数が登録されていない接続で `INSERT` が**失敗する**ことを確認すること
     （黙って連鎖無しの行が増えるより、書き込みが落ちるほうが安全）。
  4. ハッシュの材料は `prev_hash` と当該行の 6 列すべてとし、
     **列の境界が曖昧にならない連結**にする（各値に長さを前置する、
     もしくは値に出現しない区切りを使う）。単純連結は、
     `operation` と `target_id` の切れ目をずらした別の行が同じハッシュになる余地を残す。
     採用した正規化をコメントで説明すること。
  5. `audit_chain_head` は同じトリガで更新し、`row_count` を +1、
     `head_hash` を最新の `row_hash` にする。これは**末尾の切り詰め**（最後の n 行の削除）を
     検出するためで、連鎖ハッシュだけでは末尾切り詰めは検出できない。
  6. **検証ルーチン**を足す。`Service.verify_audit_chain(actor)` と
     `GET /api/admin/audit/integrity`（`system_admin` 限定。既存の
     「管理権限が必要です」と同じ作法）。返す内容は
     `{"ok": bool, "checked": int, "first_bad_id": str | None, "reason": str}` の形とし、
     `reason` には改ざんの種類（内容不一致・欠落・挿入・末尾切り詰め・連鎖未整備）を入れる。
     **検証は読み取りのみ**で、行を書いたり直したりしないこと。
  7. **既存 DB の移行**。`_ensure_column`（498 行目）と同じ追記移行の作法で、
     既に `audit` 行があるデータベースに対しては `(at, id)` の昇順で連鎖を計算して
     `audit_chain` と `audit_chain_head` を埋める。移行直後に検証が `ok: True` になること。
     移行は 1 度だけ行い、2 度目の起動で連鎖を作り直さないこと。
  8. **保存期間との接続**。`T-PH7-213` は監査行を削除しない。監査行の削除が必要になった場合は、
     残す先頭行を新しい基点にして `prev_hash` を基点値に書き換え、
     `audit_chain_head.row_count` を整える専用の手続き（管理者操作のみ、
     操作自体を `audit` に `audit.truncate` として記録）だけが許される経路であることを
     コメントまたは docstring に書く。本ジョブでその手続きを実装するかは任意とし、
     実装しない場合は「監査行は削除できない」ことを REPORT に明記する。
- **Acceptance Criteria**:
  1. **中心となる受入**: 監査行を 1 行**改ざん**すると検出される。
     `tests/test_audit_chain.py` に次を置く。
     - 中間の 1 行の `outcome` を `'ok'` から `'denied'` へ書き換えると、
       検証が `ok: False` を返し、`first_bad_id` が**その行の id** を指す。
     - 中間の 1 行を**削除**すると `ok: False` になる。
     - **末尾の 1 行を削除**すると `ok: False` になる（`audit_chain_head` の件数照合で検出）。
     - 偽の行を**途中に挿入**すると `ok: False` になる。
     - 何も触らなければ `ok: True` で、`checked` が実際の行数と一致する。
     - 正当な追記を続けたあとも `ok: True` のままであること。
     改ざんは追記のみのトリガに阻まれるので、テストは意図的にトリガを迂回して行う
     （トリガを一時的に落とす・engine のハンドルを直接使う等）。
     **迂回したことがテスト内に明示されていること**。迂回できずに
     「`UPDATE` が拒否されたから合格」としてはならない。それは検証ルーチンの試験になっていない。
  2. `audit` への `UPDATE` と `DELETE` が通常経路で拒否される
     （トリガの `RAISE(ABORT, ...)` に当たる）。`audit_chain` への `UPDATE` / `DELETE` も拒否される。
  3. **トリガ由来の監査行も連鎖に入る**こと。委譲が無効化される経路
     （`memberships` または `membership_roles` の削除で
     `delegation.invalidate` が記録される経路。`tests/test_delegations.py` に既存の筋がある）を
     通して `audit` に `'system'` 由来の行を作り、その行が `audit_chain` に存在し、
     検証が `ok: True` を返すことを assert する。
     この行を改ざんした場合も `ok: False` になること。
  4. **応答の形が変わっていない**こと。`GET /api/admin/audit` の各行が
     以前と同じ 6 個のキーのみを返す（`audit_chain` の値が混ざらない）。
     `tests/test_administration_audit.py`・`tests/test_audit_regressions.py`・
     `tests/test_account_toggle.py`・`tests/test_agents_registry.py`・
     `tests/test_admin_project_storage_load.py` に退行がないこと。これらは
     `service.conn.execute("SELECT * FROM audit")` で件数や行を直接見ており、
     列を増やすと落ちる。
  5. 既存 DB の移行: 連鎖の仕組みが無い状態で作った監査行を含むデータベースを
     開き直すと連鎖が埋まり、検証が `ok: True` になること。
     さらに同じファイルをもう一度開いても `audit_chain` の件数が増えないこと。
  6. `GET /api/admin/audit/integrity` が `system_admin` 以外（一般利用者・未ログイン）で
     403 / 401 であること。
  7. **この仕組みで防げないこと**を REPORT に明記すること。少なくとも:
     DB ファイルへの書き込み権限を持つ者が全行のハッシュと `audit_chain_head` を
     まとめて再計算すれば検出できない（連鎖ハッシュは外部に基点を置かない限り
     それを防げない）。この限界を `tests/test_audit_chain.py` に
     「全体を再計算した偽造は検出されない」テストとして**明示的に固定**し、
     将来この前提が変わったときに気付けるようにする。
  8. 変更は許可パス内に収まる。既存テストの削除・緩和は禁止。`frontend/` は触らない。

## REPORT
- `backend/app/service.py`: Added audit-chain tamper protection for `DATA-015`.
  - Registered SQLite UDF `audit_sha256` per connection (`_register_audit_hash_function`) and added canonical hash helpers (`_audit_hash_payload`, length-prefixed UTF-8 fields for `prev_hash + 6 audit columns`) so column boundaries are unambiguous.
  - Extended schema with `audit_chain(audit_id, seq, prev_hash, row_hash)` and `audit_chain_head(id CHECK(id=1), row_count, head_hash)`. Added append-only/immutability triggers: `audit_no_update/delete`, `audit_chain_no_update/delete`, `audit_chain_head_no_delete`.
  - Added `AFTER INSERT ON audit` trigger `audit_chain_insert` to compute chain rows and update head in the same trigger path; this covers both Python `_audit()` inserts and SQL trigger-originated audit inserts.
  - Added idempotent migration `_migrate_audit_chain()` that backfills existing audit rows in `(at, id)` ascending order once when `audit_chain_head` is absent, leaving chain untouched on subsequent startups.
  - Added `Service._verify_audit_chain`, `Service.verify_audit_chain(actor)` (system_admin only, `管理権限が必要です`) returning `{"ok","checked","first_bad_id","reason"}`. Verification is read-only and reports `content mismatch`, `missing`, `insertion`, `tail truncation`, or `chain not provisioned`.
  - Added code comments/docstrings describing canonicalization and the truncation limitation (audit rows are not deletable by normal path; a dedicated re-anchoring admin procedure would be required if deletion becomes necessary, not implemented here).
- `backend/app/main.py`: Added `GET /api/admin/audit/integrity` returning `svc.verify_audit_chain(user)`; endpoint is system-admin protected through the service check, same pattern as other admin audit access.
- `tests/test_audit_chain.py`: Added regressions for ACs: middle-row tamper detected with `first_bad_id` pointing to tampered row; middle deletion detected; tail deletion detected by head count comparison (`tail truncation`); middle insertion detected; untouched chain ok with checked count equal to audit row count; legitimate append keeps chain ok; normal-path UPDATE/DELETE rejected for `audit` and `audit_chain`; trigger-originated `system` `delegation.invalidate` audit row is chained and tamper-detected; migration backfills existing audit DB and is idempotent on reopen; integrity endpoint requires system_admin (401 anon, 403 non-admin, 200 admin); audit API rows still expose only original 6 keys; full recompute forgery passes verification (known limitation) pinned as an explicit test; unregistered `audit_sha256` connection fails closed on audit INSERT.
- Inconsistency between documentation and code: None found in the files inspected for this job. I followed the job text as authoritative where it described behavior; existing code patterns (trigger RAISE(ABORT) style, `_ensure_column`/migration style, admin 403 message) were preserved.
- Risks / limitations:
  - **Known limitation (reported per AC 7):** this chain has no external anchor. A principal with write access to the DB file can tamper with audit rows and recompute `audit_chain` rows and `audit_chain_head` consistently; verification will not detect that full recompute forgery. This is explicitly pinned by `tests/test_audit_chain.py::test_full_recompute_forgery_is_not_detected`.
  - **Audit rows cannot be deleted** through the normal path; append-only triggers reject UPDATE/DELETE. `T-PH7-213` does not delete audit rows. No audit truncation/re-anchor procedure is implemented in this job.
  - **SQLite-only hash registration:** `audit_sha256` UDF is registered on the SQLite connection. PostgreSQL would need an equivalent (e.g. `pgcrypto` digest) in the engine/trigger path; not implemented in this job.
  - **Snapshot export/import not updated:** `backend/app/storage.py` `SNAPSHOT_TABLES` is outside allowed_paths and does not include `audit_chain`/`audit_chain_head`; snapshot import/export would omit chain state. I did not modify it because it is outside allowed_paths.
  - The verification routine is read-only and detects tamper/missing/insertion/tail-truncation/unprovisioned states; it does not repair chains.
