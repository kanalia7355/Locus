# Task `T-PH7-215`: 忙しい会話の中にある添付を、期限で消せてしまわないことの退行検査

## SCOPE — レビュアーへ（先に読むこと）

- **これは検査を 1 本足すだけの票である。** `backend/` には触らないこと。
  **守りは既に実装されている** —— `Service.delete_expired_retention` が
  資料の検証ループで `row["conversation_id"]` を見て
  `_retention_inflight_refusal` を呼んでいる。足りないのは**その 1 組み合わせを
  固定する検査**だけである。
- 既存の検査を書き換えないこと。足すこと。
- 保存期間の既定や境界、API の形を変える票ではない。

## 出どころ

`T-PH7-213` のレビュー 2 件が同じ穴を指摘した。**指摘は正しいが、
`T-PH7-213` の受入条件 1〜8 のどれも名指していなかった**ので、E3
（受入条件は契約）に従って新しい票へ出した。落としたのではない。

- 1 回目（`opencode/flint-40b-free`, 15:35）: 資料の削除経路が、その資料が
  属する会話の実行中ジョブを見ていない、という**コードの指摘**。
  これは実装された（`service.py` の資料検証ループ内、
  `if row["conversation_id"]: self._retention_inflight_refusal(...)`）。
- 2 回目（`opencode/iceman-free`, 16:17）: **コードは入ったが、その
  失敗筋を固定する検査が無い**。既存の検査が覆っているのは
  (a) 取り込み中の資料そのもの、(b) 忙しい会話の削除、
  (c) 実行中の添付を持つ会話の削除 —— の 3 つで、
  **(d) 忙しい会話の中にある `ready` な添付を、資料として直接消す**
  経路が無い。

## 失敗筋（この検査が無いと通ってしまうもの）

1. 会話に `queued` / `running` のチャットジョブが有る
2. その会話の添付資料は既に `ready` で、保存期間も満了している
3. 管理者が `POST /api/admin/retention/delete` を
   `{"document_ids": [<その添付>]}` で呼ぶ

`service.py` の `if row["conversation_id"]:` の 2 行が消えるか壊れると、
**200 が返って添付が消え、会話には実行中の仕事が残る。** 決めた規則
（実行中は 409、完了後に再実行）が資料の経路だけ破れる。
いまの検査一式はそれでも全部通る。

## 受入条件

1. `tests/test_retention.py` に検査が 1 本足されている。内容は上の
   失敗筋 1〜3 をそのまま組み立て、`POST /api/admin/retention/delete` が
   **409** を返すことを assert する。
2. 同じ検査で、**添付の行と会話の行が残っている**ことを assert する
   （件数ではなく、識別子で確かめること）。
3. その検査が、`service.py` の `if row["conversation_id"]:` の分岐を
   取り除くと**落ちる**ことを報告で示すこと（手で外して走らせ、
   元に戻す。`backend/` は許可パスに無いので、戻し忘れると scope で止まる）。
4. 既存の検査の削除・skip・緩和が 1 つも無い。`tests/test_retention.py`
   全体が通る。変更は許可パス内に収まる。

## 要件への批判（実装者はここに答えること）

**合成時計の作法に従うこと。** 既存の検査は
`monkeypatch.setattr(service, "_retention_now", ...)` で時刻を入れている。
`time.time()` を直接触る検査を書かないこと。会話を「忙しい」状態にする
やり方も、既存の検査が `enqueue_chat` でそうしているのと同じ形に
合わせること —— **自分で行を直接 UPDATE して忙しく見せかけると、
守りが見ている条件とずれて、検査が通っても何も証明しない。**
