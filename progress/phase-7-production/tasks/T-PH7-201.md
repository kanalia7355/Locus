## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `DATA-008`。オーナー決定 2026-11-16（`progress/phase-6-extensions/OWNER_DECISIONS.md`

  権利設定に変更があったら発火するようにする」。接続先 3 種は別々のジョブに分ける決定のため、
  **本ジョブは共通部分だけ**を作る。
- **Background**:
  - いま `backend/app/service.py` の `documents` 表には、**元保存先を指す列が 1 つも無い**
    （`id, owner_id, project_id, kind, name, content, status, reason, conversation_id, grants,
    created, index_checkpoint, failure_code`）。取り込みは `Service.upload` による
    利用者の手動アップロードだけで、元保存先の有無・権限・削除を知る手段が無い。
  - 資料の閲覧可否は `Service._can_read` 1 か所に集まっており、
    `documents` `document` `chunks` `related` `_citations` `_generated` `conversation` `send`
    の**すべてがここを通る**。元保存先の権限はこの共通面に足す。経路ごとに足すと必ず漏れる。
  - 設計の下敷きは `docs/plans/PHASE2_STORAGE_ACL_RESEARCH.md`（解釈 A/A2 を推奨）と
    `docs/plans/PHASE2_STORAGE_ACL_IMPLEMENTATION_PLAN.md`（Slice 1〜3）。
    両者は提案であって決定ではないが、オーナー決定 2026-11-16 で A/A2 相当が選ばれたので、
    その 2 文書の Slice 1・2・3 を**合成コネクタだけで**実装するのが本ジョブ。
  - **本ジョブは実在の外部サービスに一切つながない**。通信コードを書かない。
    `LOCAL_ONLY_MODE` と外向き通信の既定拒否（`backend/app/main.py` の起動時検査）は変えない。
    SMB は `T-PH7-202`、Google Drive は `T-PH7-203`、Box は `T-PH7-204`。
- **Implementation Details**:
  1. 新規パッケージ `backend/app/connectors/` を作る。`backend/app/agents/` と同じ並びに置く。
     - `base.py`: 接続先 1 種が実装すべき**共通インタフェース**。少なくとも次を持つ。
       - 対象オブジェクトの列挙（安定した不透明 ID、改訂値（etag 相当）、表示名、本文の取得）
       - **利用者 1 人がそのオブジェクトを読めるか**の判定（live 判定）
       - そのオブジェクトの**権限設定のハッシュ**（変更検知用。ACL 本体を保存しない）
       - 権限変更通知を受け取れるかどうかの申告（Drive/Box は可、SMB は不可 → ハッシュ比較）
       表示名と可変パスを安定 ID として使わないこと（移動・改名で同一性が壊れる）。
     - `synthetic.py`: **合成コネクタ**。すべてメモリ内。オブジェクトと
       「利用者ごとの読取可否」をテストから直接書き換えられる。ネットワーク・ファイル I/O なし。
     - `scheduler.py`: 巡回の制御。既定間隔は **600 秒（10 分）**、設定値で変更可能。
       時計は注入可能にする（テストで `time.sleep` を使わない）。
     - `__init__.py`: 接続先の登録表。`T-PH7-202` 以降がここに 1 行足すだけで増える形にする。
  2. `service.py` に**追加のみ**の表を作る（`CREATE TABLE IF NOT EXISTS` と
     既存の `Store._ensure_column` の作法に合わせる。既存列の意味は変えない）。
     - `storage_sources`: 不透明 ID、接続先種別、有効状態、非機密の設定参照。
       **資格情報はここにも監査行にも書かない。**
     - `source_objects`: 保存先 ID、安定オブジェクト ID、改訂値、権限ハッシュ、
       最後に観測した状態と時刻。
     - `document_source_bindings`: 資料 ID と保存先オブジェクト ID、取り込んだ改訂値、同期状態。
     既存のアップロード資料は**結び付けを持たない**。結び付けの無い資料の挙動は
     1 ビットも変えないこと。これが本スライスの退行不変条件。
  3. `Service._can_read` に**元保存先の関門を 1 つ足す**。既存の関門（プロジェクト権限、
     明示拒否、公開付与、個人所有、会話添付の束縛）は**そのまま全部残す**。
     元保存先の許可が既存の関門を飛び越えることは無い（積集合であって和集合ではない）。
     - 結び付けの無い資料: 従来どおり（新しい関門は何も課さない）。
     - 結び付けのある資料: 元保存先で**その利用者が今読めるか**を確かめ、
       読めなければ `_can_read` が `False` を返す。
     - 判定できない（コネクタが落ちている、改訂値が古い、状態不明）場合は**見せない**。
       同期の失敗を許可の証拠として扱わないこと。
  4. 取り込みの二重確認に元保存先の確認を足す。`_ingestion_allowed` と `process_next` は
     すでに「検査器に本文を渡す前」と「索引する前」の 2 回権限を見ている。
     同じ 2 点で元保存先の権限と改訂値も見る。失効・削除・改訂のずれ・判定不能なら索引しない。
  5. 巡回の駆動は `backend/app/main.py` の既存のワーカーループ（`worker()` 内の
     `svc.process_next` の隣）から呼ぶ。**新しいスレッドを作らない**。
     テストが 1 回分の巡回を直接呼べる形（`Service` のメソッド 1 本）にすること。
  6. 権限変更の**即時発火**を入れる。巡回間隔を待たずに、
     通知 1 件で当該保存先（または当該オブジェクト）の再確認が走る経路を作る。
     本ジョブでは通知の入口は内部メソッドまででよい（HTTP の受け口は 203/204 の設計課題）。
     通知を受け取れない接続先のために、巡回時の**権限ハッシュ比較**も同じ経路に入れる。
     ハッシュが変わらないときに再索引しないこと（10 分ごとに全件再索引しては使えない）。
  7. 失効が観測されたら、**先に見えなくする**。本文・チャンクの後片付けは次に行う。
     逆順にすると、片付けている間だけ見える窓ができる。
  8. 監査は既存の `Service._audit` の作法（トランザクション内・メタデータのみ）に合わせる。
     保存先の設定変更・巡回開始・権限の変化・失効による不可視化を記録する。
     本文・資格情報・接続先の生応答・権限そのものの内容は記録しない。
  9. 管理向けの `Service.storage_status` は現在 `"external_enabled": False` と
     `"configuration_available": False` を返している。合成コネクタしか無い段階で
     ここを `True` にしてはいけない（画面が「つながっている」と嘘をつく）。
     表示を増やすなら**サーバが実際に確かめられる事実だけ**にすること。
     フロントエンドは本タスクの対象外（許可パスに入れていない）。
