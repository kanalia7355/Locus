# Task `T-PH7-213`: 保存期間 1 年と期限到来の管理者通知（削除は管理者操作のみ）（`DATA-015`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `DATA-015`（`docs/plans/REQUIREMENTS_TRACEABILITY_MATRIX.md` 49 行目。
  現状は「本番の保存期間・バックアップ・安全な削除はいずれも未確認」）。
  オーナー決定 2026-11-16 テーマ 5（`progress/phase-6-extensions/OWNER_DECISIONS.md` 159〜160 行目:
  「保存期間の既定は 1 年。期限到来時は管理者に画面通知を出し、削除は管理者の操作で行う（無人で消さない）」）。
- **Background**:
  - いま保存期間の概念は実装に無い。`documents`（444 行目）・`conversations`（440 行目）・
    `messages`（455 行目）・`audit`（473 行目）はいずれも `created` / `at` に
    Unix 秒（`time.time()` の float）を持つだけで、期限も通知も削除導線も無い。
  - 時刻の扱いには既に作法がある。委譲の期限判定は
    `Service._delegation_now()`（`backend/app/service.py` 1266 行目）という**名前付きの境界**を
    通しており、テストは `monkeypatch.setattr(service, "_delegation_now", ...)` で
    合成時計を入れている（`tests/test_delegations.py` 146・211 行目）。
    保存期間も同じ作法に従えば、オフラインで完全に試験できる。
  - 「無人で消さない」は受入条件として明示的に守らせる必要がある。
    既存の常駐処理（`process_next` 2272 行目、`process_next_chat` 2995 行目、
    起動時の `recover_jobs` 517 行目）はいずれも行を書き換えるので、
    そこへ削除を足さないことをテストで固定する。
  - 画面側のポップアップは本ジョブの対象外（`frontend/` は許可パスに無い）。
    本ジョブは**通知が成立するためのサーバ側の事実**を作る。画面実装は別ジョブ。
- **Implementation Details**:
  1. 保存期間の既定を **365 日**とし、設定値にする。設定経路は既存の実行時設定の作法に合わせ、
     上限・下限と不正値の拒否（既存の `fail(422, ...)` と同じ作法）を入れる。
     0 や負数、小数、文字列は拒否する。`0 = 無期限` のような特別扱いを作らないこと
     （無期限が必要なら別の明示的な設定にする。暗黙の特別値は誤設定を無言で通す）。
  2. 時計の境界を `Service._retention_now() -> float` として足す
     （`_delegation_now` と同じ形）。期限判定は**この 1 箇所のみ**を通し、
     他の場所で `time.time()` を直接呼ばないこと。
  3. 期限到来の判定対象と基準時刻を次のように定める。
     - 資料: `documents.created`
     - 会話: `conversations.created`。会話に属する `messages` /
       `generated_answers` / `chat_jobs` は会話に従属し、個別に期限判定しない。
     - 監査: `audit.at`
     判定は `基準時刻 + 保存期間 <= _retention_now()` とする（等号を含む側を明記したうえで、
     その境界をテストで固定する）。
  4. 管理者向けの参照 API を足す。`GET /api/admin/retention`。
     `system_admin` 以外は 403（既存の「管理権限が必要です」と同じ作法）。
     返す内容は、種別ごとの期限到来件数と、画面に出すための最小限の一覧
     （識別子・名称・基準時刻・期限時刻）とする。**資料本文・会話本文・添付の中身は返さない**
     （通知のために本文を管理者へ開示しない。既存の負荷表示が本文を返さない作法と同じ）。
     期限到来が 0 件のときの形も決め、テストで固定する。
  5. 削除は**管理者の明示操作のみ**とする。`POST /api/admin/retention/delete` を足し、
     削除対象の識別子を明示的に受け取る。識別子を渡さない「期限到来を全部消す」形の
     既定動作を作らないこと。削除は `audit` に `retention.delete` として記録する
     （`_audit` 544 行目の作法）。期限が来ていない対象を指定した場合は 422 で拒否する。
  6. 監査行については、本ジョブでは**通知のみ**を実装し、削除は実装しない。
     監査行の削除は連鎖ハッシュの基点を作り替える手続きを伴うため、
     `T-PH7-214` の側で規定する。`GET /api/admin/retention` には監査の期限到来件数を
     出すが、`POST /api/admin/retention/delete` は監査行を対象に取れないこと（422）。
  7. 資料・会話の削除は既存の削除経路と同じ結果になること
     （`delete_document` 2461 行目、`delete_conversation` 2752 行目）。
     従属行（`chunks`・`messages`・`generated_answers`・`chat_jobs`）が残らないこと。
     取り込み中・応答生成中の対象をどう扱うかを決め（既定は 409 で拒否し、
     完了後に再実行させる）、決めた規則をテストで固定する。
- **Acceptance Criteria**:
  1. `tests/test_retention.py` に合成時計を使った次のテストがある。
     - 364 日経過では期限到来に出ない。365 日・366 日経過では出る（境界を両側から固定）。
     - 既定が 365 日であり、設定しない限り期限到来は発生しない
       （フィクスチャの作成直後は 0 件）。
     - 設定値が不正（0・負数・小数・文字列・上限超過）なら 422 で拒否され、
       拒否後も設定が変わっていないこと。
  2. **無人削除が起きない**こと。保存期間を超えた状態で
     `process_next()`・`process_next_chat()`・`recover_jobs()` を回し、
     さらに `Service` を閉じて同じファイルから作り直しても、
     `documents`・`conversations`・`messages`・`audit` の件数が 1 件も減らないことを assert する。
  3. `GET /api/admin/retention` が `system_admin` 以外（一般利用者・未ログイン）では 403 であり、
     応答に資料本文・会話本文が含まれないことを assert する
     （本文の既知の文字列が応答 JSON に出現しないことで示す）。
  4. 削除が管理者操作でのみ起き、監査に残る。`POST /api/admin/retention/delete` で
     1 件の資料と 1 件の会話を消すと、当該行と従属行が消え、
     `audit` に `retention.delete` が対象ごとに記録され、
     他の期限到来対象は**消えずに残っている**こと。
  5. 期限が来ていない対象の削除要求が 422 で拒否され、行が残ること。
     監査行を対象にした削除要求が 422 で拒否され、`audit` の件数が変わらないこと。
  6. 一般利用者が `POST /api/admin/retention/delete` を呼ぶと 403 で、行が残ること。
  7. `tests/test_api.py` と `tests/test_security.py` に退行がないこと。
     既存テストの削除・緩和は禁止。変更は許可パス内に収まる。
  8. REPORT に次を書くこと: 画面のポップアップが未実装であるため
     **この時点では管理者は期限到来に気付けない**（API があるだけ）という事実と、
     バックアップ・復旧（`DATA-015` の残り半分）が本ジョブの対象外であること。
