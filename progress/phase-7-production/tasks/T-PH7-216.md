# Task `T-PH7-216`: 管理 API の未ログイン応答を 403 に揃える

## SCOPE — レビュアーはここを先に読むこと（2026-11-28 23:17 当番）

**これはオーナーが決めた方針の実装である**（2026-11-28 23:16、
「管理 API の未ログイン応答：A」）。A は
**「403 で畳む側に管理 API 全体を揃える」**である。
`progress/phase-7-production/OWNER_DECISIONS.md` の
「管理 API の未ログイン応答は 401 か 403 か」に経緯が書いてある。

**この票は方針を議論する票ではない。** 403 に揃えるのは決まっている。

**揃える範囲は `/api/admin/*` だけである。**

- `/api/admin/*` 以外（ログイン、一般利用者向け API）は**今のまま 401 を返す。**
  ここを畳んだら、ログインできているかどうかが利用者に分からなくなる。
- **ログイン済みの非管理者はもともと 403 である。** これは変わらない。
- `T-PH7-213` の受入条件 3（`system_admin` 以外では 403）は**書き換えない。**
  この票はその作法に他を合わせる側である。

## 事実（当番が実測、2026-11-26 16:22 / 2026-11-28 23:17）

いま管理 API の中に作法が 2 つある。

- **保存期間の 3 本**（`GET /api/admin/retention`、`PUT /api/admin/retention`、
  `POST /api/admin/retention/delete`）は `request.cookies` を直接読み、
  `Service._authenticate_system_admin`（`backend/app/service.py:4755-4766`）を
  通る。この関数は**トークンが無ければ即 403**、`_authenticate` が 401 を
  投げたら**それを 403 に畳む**。
- **他の `/api/admin/*`（30 本以上）** は `user: Actor` の依存を通る。
  `Actor` → `Service.authenticate` は**未ログインで 401** を返す。

つまり未ログインの相手には、エンドポイントによって 401 と 403 が混在して
返っている。**401 は「このエンドポイントは存在する。認証すれば答える」と
教えてしまう。** A はそれを管理 API では見せない方針である。

既存の検査が 401 を固定している箇所がある（`tests/test_login_history.py` が
未ログイン → 401 を assert するなど）。**当番の概算では、`401` の表明と
`api/admin` の参照が同じ検査ファイルに同居しているのは 11 ファイル、
うち 4 行以内に隣接しているのは 6 箇所である。この数は概算であって
受入条件ではない —— 実装者が自分で数え、報告すること。**

## Implementation Details

1. `/api/admin/*` のすべての経路で、**未ログイン（セッション無効・期限切れ・
   トークン無し）が 403 になる**ようにする。
   実装の形は実装者が選んでよい。素直な道は、管理用の依存
   （たとえば `AdminActor`）を 1 つ作って `Actor` の 401 を 403 に畳み、
   管理ルートの依存をそれに差し替えることである。
   **`Service.authenticate` 自体を書き換えて 403 を返すようにしてはいけない**
   —— 一般 API の 401 まで畳んでしまう。
2. `401` を期待している既存の検査のうち、**`/api/admin/*` を叩いているものだけ**
   を 403 期待へ直す。**一般 API を叩いて 401 を期待している検査は 1 件も
   触らない。** どちらに当たるかを表で報告すること。
3. 揃えた作法を 1 行で書き残す。`backend/app/main.py` の管理ルート群の先頭に
   コメントで「管理 API は未ログインも 403 に畳む（オーナー決定 2026-11-28）」
   と書くこと。許可パスに `docs/` は入っていない。
