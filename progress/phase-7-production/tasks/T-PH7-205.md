# Task `T-PH7-205`: コネクタの許可判定を書き込み取引の外に出す（`DATA-008` 第 1 段の続き）

## TASK DEFINITION (Assigned by Orchestrator)

- **なぜこの票があるか**: `T-PH7-201` のレビュー（`opencode/flint-40b-free`,
  2026-11-22T12:06）が 2 周にわたって挙げた Medium を切り出したもの。
  **指摘は正しく、私が実測で確認した**。`T-PH7-201` 側で直せる分は直っており
  （巡回の `list_objects` / `permission_hash` は取引の外に出た。`service.py:912-922`）、
  残るのは**許可判定そのもの**で、これは取得の 8 経路に触る別の作業である。
- **いま何が起きているか（実測）**:
  - `_source_allows(self, db, actor, row)` は `db` を受け取る＝**取引の中で呼ばれる**。
    その中の `service.py:1154` で `connector.can_read(...)` を呼んでいる。
  - 呼び出し元は `_can_read`（`service.py:2484`、取得 8 経路から）と
    `_ingestion_allowed`（`service.py:2742`、走査前・索引前の再確認）、
    および所有者一覧の分岐（`service.py:2577`）。
  - `Service.db()` は `self.lock` と `BEGIN IMMEDIATE` を取る（`service.py:568-583`）。
- **なぜ急ぐか**: 合成コネクタは即答するので**いまは誰も困らない**。
  しかし `T-PH7-202`（SMB）/ `203` / `204` が**本物のネットワークコネクタ**を入れた瞬間、
  1 件の取得がネットワーク往復のあいだ**プロセス全体の書き込みロックを握る**。
  ワーカーループと全ハンドラが止まる。だから `202` / `203` / `204` は
  **この票に依存させた**。欠陥が実害になる前に直すためである。
- **Implementation Details**:
  1. 判定に必要な状態（binding、source 行、必要なら権限ハッシュ）を**取引の中で読み取り**、
     **取引を抜けてから** `connector.can_read` を呼ぶ。
  2. 呼び終えたあと、**読み取った状態がまだ有効かを再確認する**。
     取引を抜けている間に binding が変わりうるので、楽観的に信じないこと。
     変わっていたら**拒否側**に倒す（fail-closed）。
  3. 既存の fail-closed の性質を 1 つも緩めないこと。コネクタが例外を投げた、
     時間切れになった、判定不能を返した場合は**従来どおり拒否**。
  4. `_can_read` の 8 つの呼び出し元すべてで同じ扱いにすること。
     1 か所だけ取引の中に残っていれば、この票の目的は達成されない。
