# Task `T-PH7-222`: ログイン履歴の記録と管理者限定の閲覧（`IAM-005` 代替 / `IAM-016`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `IAM-005`（MFA を実装しない代わりの補償措置）、`IAM-016`（監査の保護）。
- **Background**:
  - オーナー決定 2026-11-16（`progress/phase-6-extensions/OWNER_DECISIONS.md` テーマ 5
    【申し送り】）: MFA を実装しない代わりに「ログイン履歴の管理者可視化」を既定にする。
    パスワードが漏れた場合、**気づけるのは履歴だけ**になるので、
    攻撃を見分けられる粒度が必要。
  - いまの記録は `service.py:544-550` の `_audit` 1 本で、列は
    `id, at, actor_id, operation, target_id, outcome` のみ
    （`service.py:473-476`）。`login` は成功時に
    `self._audit(db, user["id"], "session.start", user["id"])`
    （`service.py:958`）を書くだけで、**失敗は 1 行も残らない**。
    `fail(401, ...)`（`service.py:954`）で例外が飛び、`db()` の文脈を抜ける。
    つまり現状では総当たりの痕跡が一切残らない。
  - `T-PH7-221` が失敗回数とロック期限を保持するテーブルを作る。本ジョブは
    **出来事の列**（1 行 1 回の試行）を別に持ち、管理者に見せる。
    `T-PH7-221` の集計行で代用しないこと（回数だけでは攻撃の形が見えない）。
- **Implementation Details**:
  1. 新規テーブル（例 `login_events`）を `service.py:163-477` の `executescript` に
     `CREATE TABLE IF NOT EXISTS` で追加する。列は次のとおり:
     - `id TEXT PRIMARY KEY`、`at REAL NOT NULL`
     - `user_id TEXT`（既知アカウントのみ。未知 ID では `NULL`）
     - `username_digest TEXT NOT NULL`（`digest(username)`。同一 ID への反復を
       束ねるためだけに使う）
     - `outcome TEXT NOT NULL`（`success` / `bad_password` / `unknown_user` /
       `disabled` / `locked` / `temp_expired`）
     - `peer TEXT NOT NULL`（`login` が既に受け取っている接続元。
       `main.py:324-328` で `request.client.host` が渡されている）
     - `user_agent TEXT`（上限 256 文字で切る。無ければ `NULL`）
  2. **パスワードに関わる値を一切入れない**。入れてはいけないものを明示する:
     生のパスワード、その一部、そのハッシュ、**その長さ**、文字種の内訳、
     入力された生の利用者 ID 文字列（パスワードを ID 欄に打ち間違える事故があるため、
     未知 ID は `digest` のみ残す）。`outcome` は上の固定語彙だけを使い、
     例外メッセージをそのまま書かないこと。
  3. **失敗も必ず残す**。`fail(401, ...)` が例外で抜ける経路なので、
     記録は失敗を投げる**前**に書き、確実にコミットされるようにする
     （別トランザクション、または `fail` の前に `db.execute` + 明示コミット。
     どちらを選んだか理由をコメントに書くこと）。
     「例外で巻き戻って記録が消える」実装にしないこと。
  4. 保持は有限にする。古い行の刈り取り（既定 1 年、オーナー決定 4 の保存期間に合わせる）か
     件数上限のいずれかを実装し、選んだ根拠をコメントに書く。無人で消す範囲は
     この履歴テーブルに限る（資料の削除は管理者操作のままで、触らない）。
  5. 閲覧経路 `GET /api/admin/login-history` を追加する。
     - **サーバ側で `actor.system_admin` を検査**し、非管理者は
       `fail(403, "管理権限が必要です")`（`service.py:3246-3248` と同じ作法）。
       画面の出し分けを認可の代わりにしないこと。
     - 既定は新しい順で上限 200 件（`audit()` と同じ上限）。
       `username`（既知アカウントは ID 名を解決して返してよい）、`at`、`outcome`、
       `peer`、`user_agent` を返す。`username_digest` は返さない
       （管理者に見せる意味がなく、照合用の素材を増やすだけ）。
     - **攻撃が見分けられること**を受入条件にする: 同一アカウントへの連続失敗、
       同一接続元から複数アカウントへの失敗、ロック到達、
       失敗の直後の成功が、返された列から判別できること。
  6. フロントエンドは本ジョブの対象外（`frontend/` は許可パスに入っていない）。
     管理画面への配線はオーナー決定 6「管理画面は配線後」に従い別ジョブ。
- **Acceptance Criteria**:
  1. `tests/test_login_history.py`（新規）に次がある。
     - 成功ログイン 1 回で `outcome='success'` の行が 1 行増える。
     - **誤ったパスワードでも行が残る**（`outcome='bad_password'`）。
       401 が返っても記録が消えていないことを DB 直読みで確認する。
       記録していなければこのテストは落ちること。
     - 未知の利用者 ID では `user_id IS NULL` かつ `outcome='unknown_user'` で、
       **入力した文字列そのものがテーブルのどの列にも現れない**ことを表明する。
     - 無効化された利用者、仮パスワード失効、`T-PH7-221` のロック中の 3 つが
       それぞれ区別できる `outcome` で残る。
  2. **パスワードが漏れないこと**の否定テスト: 特徴的な文字列
     （例 `Zebra-canyon-77!-secret`）で失敗ログインを行い、その文字列が
     `login_events` の全列・`/api/admin/login-history` の応答本文・
     `/api/admin/audit` の応答本文・`caplog.text` のいずれにも現れないことを表明する。
     あわせて**長さが漏れないこと**を確認する: 長さの異なる 2 つの誤パスワードで
     失敗させ、保存された行が**完全に同一の形**（長さに依存する列・値を持たない）
     であることを表明する。
  3. **非管理者が読めないこと**: 一般利用者のセッションで
     `GET /api/admin/login-history` が 403 を返す。認可がサーバ側に無ければ
     このテストは落ちること。ログインしていない場合は 401。
     他人の履歴を自分の分として読む経路が無いこと（本ジョブでは
     利用者本人向けの閲覧経路を作らない）。
  4. **攻撃の形が見えること**: 1 つのアカウントに 5 回失敗させた後、
     別アカウントに同じ接続元から 3 回失敗させ、最後に正しく成功する流れを作り、
     管理者の応答から「連続失敗の回数」「同一接続元が複数アカウントを試したこと」
     「失敗直後の成功」の 3 点が判別できることを表明する。
  5. 保持上限が効いていることを、上限を小さく設定して確認する
     （古い行が消え、新しい行が残る）。
  6. `tests/test_security.py`・`tests/test_api.py`・`tests/test_administration_audit.py`
     に退行がない。既存の表明を削除・緩和しないこと。
  7. 変更は許可パス内に収まる。
