# Task `T-PH6-102`: モデル実行スロットを複数本にする（`UI-006` / `D-CONCURRENCY`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `UI-006`。オーナー決定 2026-11-16「待機列を複数本に」（選択肢 c）。
- **Background**:
  - いま回答生成は `backend/app/local_model.py` の `self.lock = threading.Lock()` による
    **1 本のスロット**で直列化されている。`generate()` は
    `self.lock.acquire(blocking=False)` に失敗すると 429「モデルは処理中です」を返し、
    それが `ModelBusy` → 待機列（202）になる。
  - 11/15 の実測で、1 応答が 35 秒かかる構成では 10 人同時だと 10 人目が
    待機上限 300 秒を超えて失敗することが分かっている。オーナーはスロットの複数本化を選んだ。
  - 管理画面の負荷表示（`service.py` の `model_slot`）は `enabled` と `busy` の
    真偽値だけなので、複数本になると**実態を表さなくなる**。ここも直す。
- **Implementation Details**:
  1. `LocalModel` の単一 `Lock` を **N 本のカウンティング・セマフォ**に置き換える。
     N は設定値とし、既定値は `1`（= 現在と同じ挙動）にすること。
     既定を変えると、実機性能を測っていない配備先でメモリ・GPU が溢れる。
  2. N の設定経路は既存の実行時設定（`configure` と `/admin/models/runtime`）に合わせる。
     受け付ける値は 1 以上の整数で、上限を設けること（上限値と理由をコメントに書く）。
     不正値は既存の `fail(422, ...)` と同じ作法で拒否する。
  3. 空きが無いときの挙動は**変えない**。従来どおり 429「モデルは処理中です」を返し、
     呼び出し側の `ModelBusy` → 待機列（202）の流れをそのまま使う。
  4. `service.py` の管理向け負荷表示 `model_slot` を、
     `{"enabled": bool, "busy": int, "total": int}` のように**実際の本数と使用中の本数**を
     返す形へ変える。`main.py` の該当レスポンス型も合わせる。
     フロントエンドは本タスクの対象外（許可パスに入っていない）。
  5. 既存の公平配分（1 人あたりの同時実行・待機上限）は**変えない**。
     N 本すべてを 1 人が占有できてしまう場合は、その事実を REPORT に書くこと
     （修正は別ジョブにする。ここで待機列の規則を書き換えないこと）。
- **Acceptance Criteria**:
  1. `tests/test_model_slots.py` に次の合成テストがある。
     - N=1 では現在と同じ: 2 本目の同時 `generate` は 429「モデルは処理中です」
     - N=2 では 2 本が同時に走り、3 本目だけが 429 になる
     - 1 本が例外で終わってもスロットが**返却される**（漏れない）こと。
       連続してスロットを使い切って例外を起こし、その後も生成できることで示す
     - 設定値が不正（0、負数、小数、文字列、上限超過）なら 422 で拒否される
  2. N の既定値が `1` で、設定しない限り現在の挙動が変わらない。
  3. 管理向け負荷表示が使用中本数と総本数を返し、テストで確認されている。
  4. `tests/test_api.py` と `tests/test_local_model.py` に退行がない。
  5. 変更は許可パス内に収まる。既存テストの削除・緩和は禁止。
