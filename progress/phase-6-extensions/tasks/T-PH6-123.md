# Task `T-PH6-123`: 入力検証を `:user-invalid` に合わせ、`aria-invalid` を同期する

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: UI 方針。`MODERN_WEB_ADOPTION.md`
  「`forms/validate-input-after-interaction`」
  「`accessibility/accessible-error-announcement`」（`GoogleChrome/modern-web-guidance`）。
- **Background**:
  - ログイン（`App.tsx:188,200`）、初回のパスワード変更（`App.tsx:215,227`）、
    利用者の追加（`App.tsx:1878` 付近と `ProvisionUser.tsx`）のフォームは
    `required` を付けているだけで、**`aria-invalid` が無い**。
    エラーは送信後に `role="alert"` の 1 行（`App.tsx:234` 他）で出るだけで、
    **どの欄が悪いのかが読み上げに出ない**。
  - 認証はこの製品の入口で、ここで詰まると他の機能に辿り着けない。
    パスワードの最低強度と失敗回数ロックが入る予定（`OWNER_DECISIONS.md` テーマ 5
    【申し送り】）なので、欄ごとのエラー表示は**いま整えるべき**。
  - 道具は `:user-invalid` 擬似クラス。**Baseline 2023-11**
    （Chrome 119+ / Edge 119+ / Firefox 88+ / Safari 16.5+）。
    `:invalid` と違い、**利用者が触った後にしかマッチしない**ので、
    何も入力していない欄が最初から赤くならない。
  - ガイドが重要な落とし穴を 2 つ挙げている。どちらも実装に反映すること。
    1. **`:user-invalid` は ARIA 属性を自動更新しない。** CSS だけ直しても
       読み上げには伝わらない。JS で `aria-invalid` を同期する必要がある。
    2. **Firefox と Safari は、空の `required` 欄を読み込み時点から invalid として
       公開する。** だから `aria-invalid="false"` を**初期値として明示的に置く**
       必要がある。未設定のまま放置してはいけない。
- **Implementation Details**:
  1. エラーの見た目は **`:user-invalid` にだけ**当てる。`:invalid` には当てない。
  2. **色だけで示さない。** 枠線の変化に加えて、欄の下に文言を出す。
     絵文字と警告アイコンは使わない（オーナー指示 2026-11-17）。
     記号が要るなら線画の SVG。
  3. 文言は**直し方を書く**（ガイドの要求）。
     「入力してください」ではなく、何が足りないかを書くこと。
     例: パスワードの強度なら「8 文字以上、英字と数字を含めてください」。
     実際の規則はサーバ側の検証に合わせること（画面だけ厳しくしない）。
  4. すべての対象欄に **`aria-invalid="false"` を初期値として置く**。
  5. `blur` / `change` / `input` / `invalid` を見て、
     要素が `:user-invalid` にマッチするかどうかで `aria-invalid` を更新する
     （`element.matches(":user-invalid")` で判定できる）。
     React の制御コンポーネントなので、状態として持つか ref 経由で属性を書くか、
     どちらでもよいが**1 か所にまとめること**（各欄に同じ処理を書き散らさない）。
  6. エラー文言は `aria-describedby` で欄に結ぶ。
     **ただし結ぶのは invalid の間だけ**。常時結ぶと、正常な欄にタブで入ったときに
     エラー文が読み上げられる（ガイドの指摘）。
  7. 送信して失敗したときは、**最初の不正な欄にフォーカスを移す**。
     既存の `role="alert"` の 1 行は残す（全体の説明として役割が違う）。
  8. ライブリージョンは**1 つだけ**にする。既存の `role="alert"` を使い回し、
     欄ごとに `aria-live` を増やさない。
  9. **サーバ側の検証を変更しないこと。** 画面の表示は許可と検証の写しであって
     代わりではない（`OWNER_DECISIONS.md` の規律）。
     画面を通っても最終判定はサーバ。
  10. 古いブラウザ向けの `.user-invalid-fallback` クラス方式は**採らない**
      （対象ブラウザがいずれも対応済み。不要な複雑さ）。
- **Acceptance Criteria**:
  1. 対象の全欄に `aria-invalid` の初期値 `"false"` が付いている。
  2. `styles.css` のエラー表示が `:user-invalid` にのみ当たっており、
     `:invalid` 単独の規則が無い。
  3. `App.test.tsx` に次のテストがある。
     - 何も入力していない状態で、どの欄も `aria-invalid="true"` に**なっていない**。
     - 空のまま欄を離れると、その欄が `aria-invalid="true"` になり、
       `aria-describedby` でエラー文言に結ばれる。
     - 入力して正しくなると `aria-invalid="false"` に戻り、
       `aria-describedby` の結びが外れる。
     - 送信に失敗すると、最初の不正な欄にフォーカスが移る。
  4. **`frontend/e2e/appearance.spec.ts` に次の検査を追加する。**
     - ログイン画面を開いた直後、`[aria-invalid="true"]` の要素が**1 つも無い**こと
       （Firefox / Safari の既定動作に起因する誤報を防いでいることの確認。
       Playwright は chromium 1 本しか走らせていないので、
       この検査は「属性が明示されていること」の確認として置く。
       その限界をコメントに書くこと）。
     - 空のまま送信すると、エラー文言が画面に出て、
       フォーカスが最初の欄にあること。
     - エラー表示時も既存の 3 幅で横スクロールが起きないこと。
     - 追加前に、現状でこれらが落ちることを確認すること（`screen-invariants` スキル）。
  5. `npm --prefix frontend run test` と `typecheck` と `lint` が PASS。
     `npm --prefix frontend run test:appearance` が全件 PASS。
  6. 既存テストの削除・緩和は禁止。変更は許可パス内に収まる。
     バックエンドを変更しない。
