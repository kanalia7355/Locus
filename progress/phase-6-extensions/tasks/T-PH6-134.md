# Task `T-PH6-134`: `workspace.spec.ts` の `enter()` が、自分が作るはずのものを待っている

## SCOPE — レビュアーへ（先に読むこと）

- **この票は `T-PH6-127` のやり直しではない。** あの票は `appearance.spec.ts` の
  口座の付け間違いを直し、**27/27 で通っている**（`:886` を含み、判定を
  緩めずに）。ここで直すのは**別の spec の別の欠陥**で、
  オーケストレーターが**単独実行で帰属を確かめた**ものである（下の実測）。
- **product（`frontend/src/`）は許可パスに入っていない。** 直す対象は検査の側である。
  **product の欠陥だと判断した場合は、直さずに REPORT に書いて止めること** —
  別票にする。
- **判断はこの票の受入条件に対して行うこと。** 条件の外で気づいたことは
  `## REVIEW` に所見として書き、`CHANGES_REQUIRED` の理由にしないこと。

## TASK DEFINITION (Assigned by Orchestrator)

- **なぜこの票があるか**: `npm --prefix frontend run test:e2e` が
  **31 passed / 14 failed** で、`T-PH6-127` が自分の仕事を終えているのに
  通れない。14 件の内訳は `workspace.spec.ts` 12 件と `a11y.spec.ts` 2 件
  （`:285`、`:383`）である。

- **帰属は実測で確かめた**（オーケストレーター、2026-11-25 22:20〜22:24）:
  `workspace.spec.ts` を**単独で**走らせた。

  ```text
  npx playwright test e2e/workspace.spec.ts --reporter=line
  12 failed, 1 passed (3.8m)
  ```

  **`appearance.spec.ts` が一度も走っていない実行で、同じ 12 件が落ちる。**
  だから `T-PH6-127` の口座 offset の変更とは無関係である。

- **原因も特定した**（`frontend/e2e/workspace.spec.ts` の `enter()`、
  2026-11-25 22:26 時点で 25〜53 行目付近）。**循環した待ちである。**

  1. ログイン後、`enter()` は `Promise.race` で 2 つを待つ —
     **「メッセージ」入力欄**（→ `"ok"`）と**回数制限の警告**（→ `"rate-limited"`）。
  2. ところが製品はログイン直後に **「仮パスワードの変更」**の画面を出す。
     **この時点で「メッセージ」入力欄は存在しない。** 警告も出ない。
  3. だから race は 15 秒で時間切れになり `"timeout"` に落ちる。
  4. **仮パスワードの 3 つの欄を埋めて「変更して続ける」を押すのは、
     `"ok"` の枝の中だけである。** つまり **`"ok"` の枝は永久に来ない** —
     その枝が作るはずの「メッセージ」入力欄を、枝に入る条件にしているため。
  5. 失敗時の画面を確認した: **「仮パスワードの変更」の見出しが出ていて、
     3 つの欄は空のまま**である。筋書きどおりである。

  **`appearance.spec.ts` の `enter()` は、同じ変更手順を条件なしで実行している。**
  だからあちらは通る。食い違っているのはこの 2 つの書き方である。

- **口座は枯れていない**（先に確かめた）: `tests/e2e_server.py:26` は
  サーバ起動ごとに一時ディレクトリの `test.sqlite3` を作り、
  `:50` で `range(40)` を provision する。`playwright.config.ts` は
  `reuseExistingServer: false` である。**だから「前の実行でパスワードを
  変えてしまった」という筋ではない。** そこは調べ直さなくてよい。

- **Implementation Details**:
  1. **`workspace.spec.ts` の `enter()` を、仮パスワードの変更画面を
     待てる形に直すこと。** 「メッセージ」入力欄だけを合図にしないこと。
     素直な直し方は、race の対象に**「仮パスワードの変更」の見出し**を足して
     3 つ目の結果にすることである。別の形でもよいが、
     **「自分が作るはずのものを、入る条件にしない」**ことを守ること。
  2. **`appearance.spec.ts` の `enter()` と、やり方を揃えること。**
     2 つのファイルが別の作法で同じことをしている状態が、この欠陥の温床である。
     **共通化するか、揃えた理由を REPORT に書くか、どちらかにすること。**
     共通化する場合は `a11y.spec.ts` も見ること（あのファイルは
     実行ごとの口座を自分で作る）。
  3. **`a11y.spec.ts` の 2 件（`:285`、`:383`）は、まだ測っていない。**
     同じやり方で確かめること — **単独で走らせて、原因を REPORT に書く。**
     `enter()` と同じ原因なら 1 で直る。違う原因なら、
     **直す前に何が原因かを書くこと。**
  4. **既存の検査を 1 件も削らず、緩めないこと。** `T-PH6-125` が
     自分の検査を 2 本消して緑にした前例がある（`tests/e2e_server.py` の
     コメントに残っている）。同じことをしないこと。
  5. 落ちている 14 件のうち、**product の欠陥に当たるものがあれば
     直さずに REPORT に書いて止めること**（`frontend/src/` は許可パス外）。
