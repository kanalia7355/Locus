## TASK DEFINITION (Assigned by Orchestrator)

- **なぜこの票があるか**: `T-PH6-119` の実装が自分の REPORT に書いた申し送りが
  そのまま根拠である。あの票でメディアクエリの区切り幅が `px` から `em` に
  変わった（`@media (min-width: 48em)` など）。一方 `App.tsx` は配置を
  `window.innerWidth` の **px** で決めている。

- **確認した場所**（2026-11-25 18:20、本体チェックアウト）:
  - `frontend/src/App.tsx:561-562` — サイドバーの初期状態
    `localStorage.getItem("locus-sidebar") !== "closed" && window.innerWidth >= 768`
  - `frontend/src/App.tsx:885` — 画面を移るときの
    `if (window.innerWidth < 768) setSidebar(false);`

- **何が起きるか**: 利用者がブラウザや OS の文字サイズを上げると、`48em` は
  768px より**広い**幅になる。たとえば既定が 32px なら `48em` = 1536px。
  すると 1280px の窓では **CSS は狭い配置（覆い被せ）に切り替わっているのに、
  JavaScript は `1280 >= 768` なので広い配置だと思っている**。
  サイドバーが本文の上に開いたまま残り、利用者が自分で閉じるまで戻らない。
  文字を大きくした利用者にだけ起きるので、`T-PH6-119` の狙いを削る。

- **Implementation Details**:
  1. **px の比較をやめ、CSS と同じ条件を 1 つの出どころから読むこと。**
     `window.matchMedia("(min-width: 48em)")` が素直な方法である
     （`em` のメディアクエリはブラウザの初期文字サイズで評価されるので、
     CSS の分岐と**構造的に一致する**）。数値を 2 箇所に書き写さないこと。
  2. 区切り幅の値を `App.tsx` に直接書くのを避けられるなら避けること。
     避けられない場合は、**CSS 側の値と同じであることが分かる形**にして、
     なぜそうしたかを REPORT に書くこと。
  3. 初期状態と画面移動の**両方**を直すこと（片方だけ直すと食い違いが残る）。
  4. 窓の幅や文字サイズが**後から変わったとき**の扱いを決めて REPORT に書くこと。
     `matchMedia` の `change` を聴くのか、初期判定のみにするのか。
     どちらでもよいが、**選んだ理由を書くこと**。利用者が開いたサイドバーを
     勝手に閉じないことのほうが大事なら、そう書けばよい。
  5. `localStorage` の既存の鍵と、その「閉じた状態を覚える」挙動を変えないこと。
