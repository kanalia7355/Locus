FINDINGS
- High, frontend/eslint.config.js:16 — `"no-restricted-properties": "error"` declares the rule with zero options. ESLint's `no-restricted-properties` has no default restrictions, so this bans nothing. The acceptance criteria require the six SecureContext APIs (`navigator.clipboard`, `navigator.credentials`, `navigator.mediaDevices`, `navigator.serviceWorker`, `crypto.subtle`, `crypto.randomUUID`) to be listed with a message, and `npm run lint` to pass with none declared; instead lint passes vacuously and a `navigator.clipboard` reference anywhere in `src` (exactly the call site this task is about) sails through. The attempt-2 log shows a working `{ object, property }` form was found and then lost; only the bare string survived. Smallest fix: `"no-restricted-properties": ["error", { object: "navigator", property: "clipboard", message: "...SecureContext..." }, ...five more]`.
- High, frontend/eslint.config.js:25 — the `dangerouslySetInnerHTML` restriction uses `selector: "MemberExpression[property.name='dangerouslySetInnerHTML']"`. In React this only ever appears as `<div dangerouslySetInnerHTML={{__html: x}} />`, a `JSXAttribute`, never as a member expression, so the rule is dead on arrival. The task explicitly demands this ban to brace the future Markdown renderer (T-PH6-114). Smallest fix: add `{ selector: "JSXAttribute[name.name='dangerouslySetInnerHTML']", message: "..." }` (keep or drop the MemberExpression variant).
- Medium, frontend/src/ProvisionUser.tsx:118-122 (and 47-50) — acceptance requires that, when clipboard is unusable, the UI tell the user how to copy the password ("利用者が選択してコピーできる旨を案内する"). The rendered fallback is `<span>コピーできません</span>` with no instruction, and the only guidance text ("パスワードを選択してコピーしてください。") lives in `copyPassword`'s early return, which is unreachable because the button is never rendered without clipboard. Concrete failure: a LAN-HTTP admin creates a user, sees a bare "コピーできません", and has no on-screen indication the `<code>` password is selectable. Smallest fix: put the guidance into the visible fallback (e.g. `<span>コピーできません。パスワードを選択してコピーしてください。</span>`) or delete the dead `copyPassword` branch.
- Medium, frontend/e2e/appearance.spec.ts:90-95 — the "no failure notice" assertion is `expect(await copyNotice.count()).toBe(0)` taken synchronously after `click()`. The clipboard promise and the resulting state update resolve asynchronously, and `count()` never waits, so the assertion can pass even when copying is broken (e.g. permission denied in the browser, or a regression where `copyPassword` always sets the failure notice after an awaited rejection). The test would not catch the exact bug class it was written for. Smallest fix: positively assert `await expect(page.getByText("コピーしました。")).toBeVisible()` (or wait for the notice to settle, then assert absence).
- Medium, frontend/e2e/appearance.spec.ts.bak (whole file) — a 217-line copy of the spec was staged alongside the real one (`git status` shows `A ...appearance.spec.ts.bak`). It is not linted (`.bak` matches neither eslint's globs nor Playwright's testMatch) so it is inert, but it ships a second, drifting copy of a security-adjacent test and of the banned-pattern examples, guaranteeing future divergence. Smallest fix: delete the file from the change.
