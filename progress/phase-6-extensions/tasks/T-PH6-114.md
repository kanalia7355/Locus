# Task `T-PH6-114`: 作図と、資料に根拠のない生成（`UI-007` / `D-ANALYSIS`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `UI-007`、`D-ANALYSIS`。オーナー指示 2026-11-16
  「既存の許可範囲ファイルを参照しつつ、新規に貼られたデータファイルなどを用いて
  図の作成とか普通の生成 AI ができることも行えるようにしたい」。
- **着手できない理由（意図的）**: これは見た目の追加ではなく、**製品の約束の変更**。
  いまの Locus は「回答は必ず参照範囲内の資料が根拠で、出典が付く。根拠が無ければ
  推測せず『確認できません』と言う」という作りで、研究用途で信用できる理由がそこにある。
  「普通の生成 AI ができること」を入れると、**資料に根拠のない出力**が同じ画面に混ざる。
  利用者が、目の前の文が資料由来かモデルの作文か区別できなくなる。
  だから見た目から先に作らない。
- **オーナーに回答をお願いしている 3 点**（`OWNER_DECISIONS.md` に起票済み）:
  1. **出どころの表示**: 回答を部分ごとに「資料に基づく / 添付データから計算 /
     モデルの知識」と示す案でよいか。（開発側の推奨: よい）
  2. **作図の実現方法**:
     - **A** モデルには数値と図の種類だけを出させ、描画はアプリ側で行う。
       コード実行なし。棒・折れ線・散布など定型の図に限られる。
     - **B** モデルにコードを書かせて実行する。任意の図が作れるが、これは
       **任意コード実行**そのもの。`T-PH6-104` のサンドボックスが前提で、
       しかもファイル解析より危険（入力ではなく命令を実行するため）。
     （開発側の推奨: **A から始める**。研究資料の図の大半は定型で足りる）
  3. **資料に根拠のない質問に答えてよいか**。答える場合、その回答に出典は付かない。
     付かないことを画面で明示する前提でよいか。
- **回答が入ったら確定すること**: `allowed_paths`、`test_cmd`、受入条件。
  A 案なら「モデルの出力を図の仕様として検証し、検証を通らなければ図にしない」
  （モデルが任意の描画指示を送り込めないこと）が受入条件の中心になる。
