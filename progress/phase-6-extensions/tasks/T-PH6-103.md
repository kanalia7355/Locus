- **Background**:
  - いま対応形式は `backend/app/service.py` の `ACCEPTED_EXTENSIONS = {".txt", ".md", ".csv"}`
    という集合リテラル 1 か所だけでなく、フロントエンドの
    `/\.(txt|md|csv)$/i` と `accept=".txt,.md,.csv"` にも散っている。
  - 形式を増やすたびに複数箇所を直すことになり、どれか 1 つを直し忘れると
    「画面では選べるのにサーバが 422 で弾く」か、その逆が起きる。
  - **本タスクは対応形式を増やさない**。増やせる構造にするところまで。
    実際の抽出（PDF・Office・画像 OCR）は `T-PH6-104` のサンドボックスが先に必要。
- **Implementation Details**:
  1. 新規 `backend/app/formats.py` に、形式を 1 枚の表として宣言する。
     1 行 = 拡張子 + 種別（例 `text`）+ 最大バイト数 + 抽出方式の名前。
     既定の表は**いまと同じ 3 形式（`.txt` `.md` `.csv`、256 KiB、プレーンテキスト）**だけ。
  2. `service.py` の `ACCEPTED_EXTENSIONS` / `MAX_CONTENT_BYTES` / `unsupported_extension()` を
     この表を読む形に変える。`upload` と `inventory` が同じ表を読むこと
     （両者が食い違わないことは `T-PH5-101` の受入条件でもある）。
  3. 対応形式を**API で配信**する。`GET /api/formats`（名前は既存の API 命名に合わせてよい）が
     拡張子一覧と各形式の最大バイト数を返す。認証は既存の読み取り系と同じ扱いにする。
     フロントエンドの修正は本タスクの対象外（許可パスに入れていない）。
  4. 表に項目を 1 行足すだけで、`upload` の受理・`inventory` の判定・API の配信が
     **同時に**変わること。これをテストで固定する。
  5. 既存の名前規則（`unsafe_document_name`）は変えない。拡張子以外の検証は対象外。
- **Acceptance Criteria**:
  1. `tests/test_document_formats.py` に次の合成テストがある。
     - 既定の表では、受理される拡張子が**いまと完全に同じ 3 つ**であること
     - 表に合成の 1 行を足すと、`POST /api/documents`・`POST /api/inventory`・
       形式配信 API の**3 つすべて**が同時にその形式を認めること
       （どれか 1 つでも取り残されたら落ちるテストにすること）
     - 表から 1 行を外すと、同じ 3 経路が同時に拒否すること
     - 形式ごとの最大バイト数が `upload` と `inventory` の両方で効くこと
  2. 既定の挙動が変わっていない（`tests/test_ingestion_inventory.py`、`tests/test_api.py` に退行なし）。
  3. 形式の追加が `formats.py` の表 1 行で済むことが REPORT に手順として書かれている。
  4. 変更は許可パス内に収まる。既存テストの削除・緩和は禁止。
