# Task `T-PH6-126`: プロジェクトを切り替えても前のプロジェクトのジョブが追ってくる

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `T-PH6-113` のレビュー所見（`opencode/longcat-2.5-free`,
  2026-11-19）。UI 方針（`UI_IMPLEMENTATION_BASELINE.md` の基準幅）。
- **このジョブが存在する理由**: `T-PH6-113` のレビューが挙げた Low の所見は
  **`T-PH6-113` 以前からある欠陥**で、確認ダイアログを足したことで目立つようになった。
  修正範囲が `switchProject` とポーリングの終了処理に及ぶため、別の票に移した。
  受入条件を緩めたのではない。
- **Background（レビューの記述を要約。行番号は `T-PH6-113` 当時のもの）**:
  - `switchProject` は `pendingJob` を `streaming` のときだけ消しており、
    **待機列に入っているジョブは意図的に残している**。
    一方で確認ダイアログは「生成中の回答は画面から閉じられ…」と約束している。
    待機中の回答については**この約束が成り立っていない**。
  - 再現手順: モデルのスロットが埋まっている状態で質問を送る（待機列に入る）→
    プロジェクトを切り替えて承諾する → 新しいプロジェクトの画面に
    `順番待ちあり` が出たままになり、送信ボタンが `!!pendingJob` で `disabled` のまま。
    さらに古いジョブが `failed` になる（あるいはポーリングが失敗する）と、
    **古いプロジェクトの失敗が新しいプロジェクトの画面に書き込まれる**。
  - レビューが挙げた最小の修正は 2 通り。どちらを採ってもよいが、**理由を書くこと**。
    1. `switchProject` で在線中のすべてのジョブについて `pendingJob` を消す
       （回答は古い会話に確定済みで、`調査履歴` から辿れる）
    2. ポーリングの終了処理（`setError` / `setNotice` / `setCancelledJob`）を
       **そのジョブ自身の会話・プロジェクトに限定する**
  - 2 の方が筋が良い可能性がある（画面の更新がどのジョブのものか分かるようになるため）。
    ただし影響範囲が広い。**どちらを選んだかと、選ばなかった側を選ばなかった理由**を
    報告に書くこと。
- **併せて直すこと（別の穴）**: `UI_IMPLEMENTATION_BASELINE.md` は基準幅として
  **320px** を挙げているのに、外観ゲート（`appearance.spec.ts` の `WIDTHS`）は
  1280 / 768 / **360** しか見ていない。320px が一度も測られていない。
  - `WIDTHS` に 320px を足すこと。
  - **足した時点で既存の検査が落ちる可能性がある。落ちたら直すこと。**
    検査の方を緩めて通すのは禁止（幅を外す・`toBeLessThanOrEqual` を広げる等）。
  - 320px で本当に成り立たない制約が見つかった場合は、**実測値を添えて報告し、
    基準文書側を直す提案をすること**（文書と実装のどちらが誤りかを判断するのは
    オーケストレータの仕事。勝手にどちらかを変えない）。
- **Acceptance Criteria**:
  1. `App.test.tsx` に次の合成テストがある。
     - 待機列にジョブがある状態でプロジェクトを切り替えて承諾すると、
       新しいプロジェクトの画面に `順番待ちあり` が**残らない**
     - 切り替え後に古いジョブが `failed` を報告しても、
       その失敗が**新しいプロジェクトの画面に出ない**
     - 古い会話に回答が確定していること（失われていないこと）
  2. `appearance.spec.ts` の `WIDTHS` に 320px が含まれ、**全件 PASS**。
  3. `npm --prefix frontend run test` / `typecheck` / `lint` が PASS。
  4. 既存テストの削除・緩和は禁止。変更は許可パス内に収まる。
     バックエンドを変更しない。
