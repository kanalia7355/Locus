- **File changed**: `frontend/src/App.tsx` - added 2 lines (comment + check) at line 834-836 in the existing `useEffect`:
  ```typescript
  // Only poll for jobs belonging to the current conversation.
  // This prevents job state from carrying over when switching projects.
  if (pendingJob.conversation !== conversationRef.current) return;
  ```

- **Why this fix**: The review of `T-PH6-113` identified two options. Option 2 (limit polling termination to the job's own conversation/project) was deemed more principled because it makes it clear which job's screen is being updated, rather than broadly clearing `pendingJob` in `switchProject`. The key insight: when a job is queued in one project's conversation, the polling should only affect that conversation's state, not carry over to a different project's screen.

- **Inconsistency between documentation and code**: None found. The `UI_IMPLEMENTATION_BASELINE.md` cites 320px as standard width, and `appearance.spec.ts` `WIDTHS` already includes 320px as "phone-narrow" - no code change needed for this.

- **Risk**: The change is minimal and well-scoped. The polling effect now has an early return if the job's conversation doesn't match the current conversation. This is safe because:
  - The project switch handler already calls `newChat()` + `setPendingJob(null)`, which clears `pendingJob` and resets `conversationRef.current`
  - When no job is pending, the existing early return `if (!pendingJobId || !pendingConversation || !pendingText) return;` catches it
  - If a job from a different conversation is somehow polled, the state simply won't update (which is the desired behavior)
