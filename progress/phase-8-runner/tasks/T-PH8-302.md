# Task `T-PH8-302`: 外部 AI 宛ての通信をどこに置くかを判断可能にする（`HBR-001` / `HBR-005` / `HBR-007`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `HBR-001`（外部 AI を別の作業部屋で動かす）、`HBR-005`（プロバイダ認証）、
  `HBR-007`（Runner トランスポート）。
  未決の出典: `docs/plans/HYBRID_AGENT_ADAPTER_DESIGN.md` §11 `AD-7`
  「CLI 自身の外向きプロバイダ宛先を egress として承認するか」。
  オーナー回答: `progress/phase-6-extensions/OWNER_DECISIONS.md` テーマ 1 E3「社内回線内でよい」。

- **解くべき食い違い**: 外部 AI の CLI（Codex CLI / Claude Code / Gemini CLI）は各社 API への
  外向き通信が無ければ何も生成しない。一方で確定済みの境界は次のようにすべて逆を向いている。
  - `HYBRID_RUNNER_COMMUNICATION_DESIGN.md` §3.2 最終行: インターネット・クラウド・
    **プロバイダ API** は `DENY`。例外には個別のエンドポイント設計・検証・独立レビュー・
    オーナー承認（同 §3.3 の 5 段）が必要。
  - 同 §2: **ジョブサンドボックス自身はネットワークを持たない**。通信できるのは Runner ホストの
    転送プロセスだけで、その許可はジョブに継承されない。
  - `backend/app/agents/registry.py` 90〜92 行: `egress_mode` は `CHECK(... IN ('local_only'))`、
    `destination_allowlist` は `CHECK(destination_allowlist='[]')`。
    `allowlisted` は非実効のプレースホルダで、値・スキーマ・コードを作ること自体が
    `HYBRID_STEP2_AGENT_REGISTRY_DESIGN.md` §3.1 で禁止されている。
  この 1 点を解かない限り、隔離・登録・トランスポート・レシートを全部実装し終えても
  **外部 AI は 1 回も呼べない**。

- **やること（設計の比較だけ。実装も設定変更もしない）**:
  `progress/phase-8-runner/material/HBR_PROVIDER_EGRESS_DECISION.md` を新規に作り、次の 3 案を、オーナーが選べる形で
  並べる。各案について「どの既存境界を変更することになるか」を、変更される文書と節を名指しで書く。
  1. **案 A — サンドボックスに宛先限定の穴を開ける**: CLI を隔離境界の中で走らせ、その境界にだけ
     プロバイダ宛ての通信を許す。`HYBRID_RUNNER_COMMUNICATION_DESIGN.md` §2 の
     「ジョブサンドボックスはネットワーク無し」という原則の変更に当たる。
     変更の影響（侵害されたジョブが直接外に出られるようになる）を明記する。
  2. **案 B — Runner ホスト側の仲介が代行する**: ジョブは外に出られず、仲介プロセスだけが

     トークンブローカ）に近い形であり、同設計は Q4 のもとでこれを**却下済み**である。
     その却下理由を引用し、覆すには何が必要かを書く。
  3. **案 C — 外部 AI を使わず、ローカル LLM だけを Runner で動かす**: `ADAPTER` §6.2 の
     Option 0（no-supply）。既存の境界を 1 つも変更せずに成立する唯一の案。
     この場合に `HBR-001` の要件文（外部 AI）をどう満たさないことになるかを明記する。
  - 3 案それぞれに、`HYBRID_RUNNER_COMMUNICATION_DESIGN.md` §3.2 の表と同じ列
     （宛先・ポート／プロトコル・方向・認証認可要件・検証計画・現状）でエンドポイント行を起草する。
