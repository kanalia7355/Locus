## 当番が参考にしてきたもの（実測、2026-11-28 23:17）

**Opencode はこの機械に入っているが、配られているのはコンパイル済みの
実行ファイルだけで、読めるソースは無い**（`@opencode/cli` は
`bin/opencode.exe` と `postinstall.mjs` のみ）。**T3code はこの機械には無い。**
そこで実行ファイルの中の文字列を数えて、どの仕組みを使っているかを測った。

| 探した語 | 出現 | 読み取れること |
|---|---|---|
| `sandbox` | 313 | 隔離は後付けでなく中心概念として実装されている |
| `namespace` | 920 / `bwrap`（bubblewrap）5 / `cgroup` 10 | **Linux 側は bubblewrap + cgroups** |
| `AssignProcessToJobObject` | 2 | **Windows 側は Job Object** |
| `seatbelt` / `landlock` / `AppContainer` / `CreateRestrictedToken` | **0** | どれも使っていない |
| `permission.ask` | 10 | 境界の上に**人に訊く層**がある |

設定の形も文字列から読み取れた。**能力ごとに名前が付いている**:

```text
sandbox.enabled
sandbox.filesystem          sandbox.filesystem.disabled   sandbox.filesystem.allowRead
sandbox.credentials         sandbox.credentials.awsPairs  sandbox.credentials.allowPlaintext…
sandbox.ripgrep             sandbox-runtime               bwrapPath（bwrap の絶対パス）
allowUnsandboxedCommands    sandboxSwitches               sandboxSettings
```

**倣うべき形**: 「隔離されているか」を 1 つの真偽値で持たず、
**能力ごと（ファイル系・資格情報・個別のツール）に名前を付けて持つ**こと。
`T-PH6-104` の `SUBPROCESS_GUARANTEES` / `DOCKER_GUARANTEES` が
`verified` / `unverified` を項目ごとに持っているのと同じ考え方で、
**この repository はすでに同じ方向に居る。**

**倣ってはいけない形**: Opencode には `allowUnsandboxedCommands` という
**隔離を外す口**がある。`HYBRID_ISOLATION_PROFILES.md` §9 は
**no-VM downgrade path を明示的に禁じている**ので、Locus では作らない。
参考にしたのは設定の面の切り方であって、逃げ道ではない。

## 当番の提案（オーナーが別を言えばそれに従う）

- **プロファイルは `W-D`（Windows デスクトップ）を本命とする。**
  製品が動いているのはこの形であり、4 候補の証跡は相互に流用できない
  （§3 冒頭）。**ただし `T-PH8-304` の `selected` を埋めるのはオーナーである**
  —— あの票の受入条件が `selected: null` を要求して通っているので、
  当番が埋めると受入条件を事後に書き換えることになる。
- **Windows の実装手段は Job Object**（Opencode と同じ）。
  CPU・メモリ・プロセス数・実時間の上限を 1 つのオブジェクトで掛けられ、
  親が死んでも子孫が残らない。
- **資源上限の既定値（当番が提案する数値。計測後にオーナーが直す）**:
  CPU 1 コア相当 / メモリ 1 GiB / プロセス数 32 / ディスク 256 MiB /
  出力 8 MiB（`sandbox.extract_with_sandbox` の既定と同じ）/ 実時間 60 秒。
  **この数値はこの票では「ハーネスが上限を受け取れること」の確認にしか
  使わない** —— 本当の値決めは実測後である（§2.4）。
- **独立検証者は、ループが別モデルを割り当てる仕組みで満たす。**
  `jobloop` は実装したモデルにレビューをさせない（CLAUDE.md の譲らない 3 条件の
  1 つ）。§7 項目 4 の「実装・設定の作成者と分離」はこれで満たせる。
  **人を任命する必要があるとオーナーが判断されるなら、ご指示を頂きたい。**

## Implementation Details

1. `runner/probes/` に**ハーネス**を作る。テスト ID は
   `HYBRID_ISOLATION_ENGINEERING_DETAIL.md` §3.2 の族名をそのまま使う:
   `FS` `PROC` `NET` `RES` `XFER` `CLEAN` `B6`。
2. **各族に正のコントロールを必ず付ける**（§3.1 手順 2）。
   **正のコントロールが落ちた場合、対応する負の結果は無効であって
   合格ではない。** これをハーネスの構造として持つこと ——
   報告の書き方の約束ではなく、**コードが丸められないようにする。**
3. **台帳**を作る。失敗・ブロック・スキップを**合格に丸めない**（§3.3）。
   スキップは台帳に残る。
4. **境界は差し替えられる形にする**（注入）。この票は**合成の境界**に対して
   動かす。`T-PH8-307` が本物の境界を差し込む。
5. **プローブを 1 本も実行しない。** この票で走るのは
   「ハーネスが正しく判定するか」の検査だけである。

## Acceptance Criteria

1. 7 つの族（`FS` `PROC` `NET` `RES` `XFER` `CLEAN` `B6`）が台帳に存在し、
   **それぞれに正のコントロールが定義されている**こと。族を数えて報告すること。
2. **正のコントロールが落ちたとき、その族の負の結果が「合格」にならないこと。**
   合成の境界で正のコントロールを意図的に落とし、**族全体が無効
   （合格でも不合格でもなく無効）**と判定されることを実行結果で示すこと。
   **これがこの票の中心である。**
3. **スキップが合格に丸められないこと。** スキップを 1 件起こし、
   台帳にスキップとして残り、合格数に入らないことを実行結果で示すこと。
4. **「観測できなかったプローブ」が合格にならないこと**（§3.2 `NET` 行）。
   ホスト側の捕捉が無い `NET` の結果は**失敗**として扱われることを
   実行結果で示すこと。クライアント側のエラーだけでは遮断の証明にならない。
5. **`B6`**: 合成のレシートらしきものとテスト用 Runner を存在させた状態で
   dispatch が**明示的に拒否される**ことを確かめる。
   **「Runner が無いから拒否された」は合格の証明にならない**ので、
   Runner が在る状態で拒否されることを示すこと。
6. 資源上限（CPU・メモリ・プロセス数・ディスク・出力バイト・実時間）を
   **外から受け取れる**こと。**数値をコードに埋め込まないこと** ——
   本当の値決めは実測後のオーナー判断である。
7. **プローブを 1 本も実行していないこと。** ホストのファイル・プロセス・
   ネットワークに触る実行が無いことを報告で示すこと。
8. **実データ・実資格情報・実プロバイダ・実エンドポイントを使わないこと。**
   合成のみ。
9. **隔離を外す口（`allowUnsandboxedCommands` に当たるもの）を作らないこと**
   —— §9 の no-VM downgrade path の禁止。
10. **既存の Docker QA（`loop_engine/docker_boundary.py`、
    `tests/integration/test_live_docker_boundary.py`）の結果を、製品 Runner の
    隔離の証拠として引かないこと。** あれは `LOCUS_LIVE_DOCKER=1` が無ければ
    スキップされ、**スキップは合格ではない。**
11. `python -m pytest tests/test_hbr_probe_harness.py tests/test_hbr_isolation_selection.py -q` が **PASS**。件数を報告すること。
12. **`T-PH8-304` の `HBR_ISOLATION_SELECTION.json` の `selected` と
    `independent_reviewer` を書き換えないこと**（あの票の受入条件が
    `null` を要求している）。既存の検査を削除・skip・緩和しない。
    変更が `allowed_paths` 内に収まっている。
