# Task `T-PH5-103`: 能力を偽らない待ち時間・上限表示（`UI-006`）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `UI-006 — Multi-user admission and fairness`
  （gap state `実装中`、remaining: "Define no invented capacity target; measure representative
  concurrency and implement bounded queues/deadlines/cancel/fairness with truthful display"）
- **Background**:
  - 実測は `T-PH4-105` で完了（`progress/phase-4-closeout/tasks/T-PH4-105.md`）。
    同時 10 人・応答 2 秒で 10/10 回答、待ち最大 22.1 秒。**モデルスロットは 1 本の直列処理**のため、
    同時 N 人の行列の末尾は約 N×1 応答ぶん待ち、`CHAT_WAIT_SECONDS = 300` を超えると失敗する。
  - 管理画面の負荷表示（`/api/admin/load`）は現在、待機件数・上限・待機中の利用者別件数を返す。
    **残っているのは「待機上限（締め切り）が存在することを管理者が読み取れる形で返すこと」**。
  - **能力値（何人まで使える等）を新設してはならない**（roadmap §4 P3「measure before claiming」）。
    返すのは設定値と観測値のみ。
- **Implementation Details**:
  1. 先に `backend/app/service.py` の `/api/admin/load` 相当の集計（`chat_queue` を作る箇所）と
     `CHAT_WAIT_SECONDS` / `CHAT_QUEUE_LIMIT` / `CHAT_USER_QUEUE_LIMIT` の定義を読むこと。
  2. `chat_queue` の返り値に次を**追加**する（既存キーの意味は変えない）:
     - `wait_deadline_seconds`: `CHAT_WAIT_SECONDS`（待機上限。超過した質問は失敗する）
     - `oldest_queued_wait_seconds`: 現在待機中で最も古い質問の経過秒（待機なしなら `0`）
     いずれも**設定値と観測値**であり、能力の約束ではない。
  3. 値は既存の集計と同じトランザクション内で読むこと。利用者名・質問本文は追加しない
     （metadata-only 原則）。
  4. テストは新規ファイル `tests/test_truthful_load_display.py` に書く。
     既存の `tests/test_admin_project_storage_load.py` は変更しない。
- **Acceptance Criteria**:
  1. `wait_deadline_seconds` が `CHAT_WAIT_SECONDS` と一致し、ハードコードされた別の数値ではない。
  2. 待機ありの状態で `oldest_queued_wait_seconds` が増加方向の値を返し、待機なしで `0` になる。
  3. 応答に利用者名・質問本文が含まれないことがテストで示されている。
  4. キュー上限・待機上限・1 人あたり上限の**値そのものは変更していない**。
  5. 既存の負荷表示テストに退行がない。
  6. 変更は許可パス内に収まる。

## ORCHESTRATOR RULING (2026-11-15T17:10:00+09:00)

ワーカーが停止して出した判断要求は妥当だった: `tests/test_admin_project_storage_load.py` の
`test_load_display_reads_queue_limits_and_running_job_without_chat_content` は `chat_queue` を
**完全一致**で検証しているため、キーを追加すると既存テストが落ちる。

裁定（`T-PH4-102` 2026-11-14 の前例と同じ方針）:

1. `tests/test_admin_project_storage_load.py` の**追記形式の拡張のみ**を許可する。
   既存アサーションの削除・緩和は禁止。
2. `wait_deadline_seconds` は定数なので、完全一致の期待値に**キーを追加**して通すこと。
3. `oldest_queued_wait_seconds` は時刻依存で毎回変わるため、完全一致の辞書から取り出し
   （`pop`）、**別に範囲で検証**すること（待機なしなら `== 0`、待機ありなら
   `0 < value < 妥当な上限`）。キー自体を検証から外してはならない。
4. 上記以外のファイルは触らないこと。キュー上限・待機上限の値は変更しないこと。

この裁定でジョブを再開する（試行回数は消費していない: 停止は推測より良い結果である）。
