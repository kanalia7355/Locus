  outcomes"）
- **Background**:
  - `docs/planning/research-app-concept.md` §8 は取り込み前に
    「ファイル一覧を事前確認（件数・容量・形式・権限・対象外）」を行い、
    「未対応・暗号化・権限不足・破損などは黙って除外せず理由を表示する」ことを求めている。
    現状は個別アップロードが 422 で弾かれるだけで、**何件が対象外になったのかを一覧で示す経路がない**。
  - 既存の制約（`backend/app/service.py::upload`）は UTF-8 の `.txt` / `.md` / `.csv`、
    本文 256 KiB 以内、キュー上限（全体 32・1 人 4）、資料数上限（全体 1000・1 人 100）。
    **これらの上限・対応形式を本タスクで変更してはならない。** 形式拡張は owner 判断待ち（`DATA-007`）。
- **Implementation Details**:
  1. 先に `backend/app/service.py` の `upload` と `_metadata`、`backend/app/main.py` の
     アップロード経路を読むこと。
  2. `Service` に **読み取り専用の検査メソッド** を 1 つ追加する（例 `inventory`）。
     入力は「これから登録しようとする候補の一覧」で、候補 1 件は名前と本文の長さ（バイト数）のみ。
     **本文そのものを受け取らない / 保存しない / 監査に書かない。**
  3. 各候補について、`upload` が実際に使う判定と**同じ規則**で次のいずれかを返す:
     `accepted`（登録可）/ `unsupported_format`（拡張子が対象外）/ `too_large`（256 KiB 超）/
     `invalid_name`（安全でない名前）/ `queue_full`（キュー上限）/ `limit_reached`（資料数上限）/
     `not_permitted`（当該プロジェクトへの `upload` 権限なし）。
     判定規則を二重実装しないこと（共通化するか、同じ定数・同じ関数を参照する）。
  4. 集計（件数・合計バイト数・理由別件数）も返す。権限のないプロジェクトを指定した場合は
     インベントリ自体を拒否する（既存の `require` を使う）。
  5. `backend/app/main.py` に対応する API を 1 つ追加する。入力検証は既存の `Input` モデルに合わせ、
     候補は最大 200 件、名前は 160 文字以内、サイズは非負整数のみ受け付ける。
  6. テストは新規ファイル `tests/test_ingestion_inventory.py` に書く。既存テストは変更しない。
- **Acceptance Criteria**:
  1. 対象外の候補が**理由付きで**返る（黙って除外しない）。7 つの理由すべてに合成テストがある。
  2. 本文を受け取らない・保存しない・監査に残さないことがテストで示されている。
  3. 権限のないプロジェクトではインベントリが拒否される（deny-by-default）。
  4. 既存の対応形式・サイズ上限・キュー上限・資料数上限の値は変更されていない。
  5. 既存テスト（`tests/test_api.py`）に退行がない。
  6. 変更は許可パス内に収まる。
