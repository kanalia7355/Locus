# Task `T-PH9-415`: 答えなかった派遣を、試行として数えない

## SCOPE — レビュアーへ（先に読むこと）

- **これは予算（1800 秒）を伸ばす票ではない。** 数え方だけを直す票である。
  予算が適切かどうかは、この票が入って所要時間が読めるようになってから別に決める。
- **本当の失敗を見逃す実装にしないこと。** 答えが返ってきて受入条件を満たさなかった試行は、
  これまでどおり消費する。消費しないのは**答えが一度も返らなかった**派遣だけである。

## TASK DEFINITION (Assigned by Orchestrator)

- **なぜこの票があるか**: `timeout: no reply within 1800s` で終わった派遣が、
  受入条件を満たせなかった試行と**同じ 1 回**として数えられている。
  答えが返っていないので、その票の仕事の出来については**何も分かっていない**。
  枠切れ（`Ending.EXHAUSTED`）と供給障害（`Ending.OUTAGE`）は既に
  「試行を消費せず冷却してローテーションする」扱いになっている。
  時間切れも同じ側に属する。

- **実測された証拠**（2026-11-25）:
  - `T-PH6-121` は 10:40:57 と 11:25:34 の 2 回、どちらも
    `timeout: no reply within 1800s` で終わり、**それだけで 2/3 を消費した**。
    同じモデル（`opencode/nemotron-3.5-lightning-free`）である。
    次の派遣で上限に当たるところを、オーケストレーターが手で 0/3 に戻した。
  - 同型の前例: 2026-11-20 に `404 Endpoint is unavailable` が返る 8 分間で
    5 件が未着手から 3/3 になった。あれは `Ending.OUTAGE` を足して解決した。
    時間切れだけが取り残されている。

- **Implementation Details**:
  1. 時間切れで終わった派遣は**試行を消費しない**こと。既存の枠切れ・供給障害と
     同じ経路に乗せるのが素直である（モデルを休ませて次へ回す）。
  2. ただし**同じ票が時間切れを繰り返すことは記録に残すこと。** 消費しない扱いにすると、
     何も残らなければ永久に繰り返しうる（`T-PH9-414` と同じ失敗の形）。
     繰り返し回数が読める記録を出し、**既定の回数に達したら escalate** して
     人が「票を割る」判断をできるようにすること。回数は実装者が決めてよいが、
     **理由を記録に書くこと**。
  3. 記録に**実際の所要時間**を書くこと。予算が適切かを後から判断する材料になる。

## ACCEPTANCE CRITERIA

1. 時間切れで終わった派遣が試行を消費しないことを示す試験がある。
2. **答えが返ってきて受入条件を満たさなかった試行は、これまでどおり消費する**ことを示す
   試験がある（1 の実装が本当の失敗を見逃していないことの証明）。
3. 同じ票が時間切れを繰り返したとき、既定の回数で escalate されることを示す試験がある。
4. 時間切れの記録に、実際の所要時間と、その票の時間切れ連続回数が入っていることを示す
   試験がある。
5. `python -m pytest tests/test_jobloop.py -q` が緑。
6. `python -m ruff check jobloop tests` と `python -m ruff format --check jobloop tests` が緑。
