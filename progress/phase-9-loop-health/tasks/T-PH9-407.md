## TASK DEFINITION (Assigned by Orchestrator, 2026-11-24 05:25)

- **なぜこの票があるか**: `shift_check.py` のモデル検査は
  `.jobloop/roster.json` の**記録件数**を分母にしている。

  ```
  ok    11 of 14 recorded models resting, soonest back in 123 min
  ```

  ところが `roster.json` には**供給側がもう出していないモデルの記録が残り続ける**。
  `Roster.available()` が見るのは `self.models`（**いま提供されている分**）なので、
  記録にあって提供されていないモデルは**永遠に「休んでいない 1 件」として数えられる**。
- **実測（2026-11-24 05:23）**: 記録 14 件のうち冷却が切れていたのは 4 件
  （`minimax-m3.1-flash-free` は 11-17、`glm-5.3-flash-free` は 11-18、
  `longcat-2.5-free` は 11-23、`qwen4-max-free` は 05:12 で期限切れ）。
  **しかし `jobloop doctor` は「10 eligible」、`status` は
  `available models: none`、ループは全フェーズで `no-model` だった。**
  つまり**使えるモデルは 0 件**で、計器の「4 件空いている」は嘘だった。
- **何を損したか**: 2 シフト連続で、オーケストレーターが
  「空きがあるのに動いていない＝欠陥か？」を疑って調査に入った
  （2026-11-24 04:35 と 05:23）。**計器が誤解させた分の時間である。**
  いまの行末には `(whether any can run is the loop's no-model line, not this count)`
  と注意書きがあるが、**注意書きで補う数字は、直すべき数字である**。
  2026-11-18 に「死んだループを生きていると 17 時間報告した」のと同じ型
  （計器が嘘をつく）であって、規模だけが違う。
- **Implementation Details**:
  1. 分母を**いま提供されているモデル**にする。`jobloop.roster` の
     `eligible()` と `Roster.available()` を使って数えること
     （数え方を自分で再実装しない。二重実装は必ずずれる）。
  2. 表示は「提供 N 件のうち M 件が冷却中、使えるのは K 件」が分かる形にする。
     **`K` が 0 のときは、それが一目で分かること** — 今夜の 5 時間半は
     その一点を知りたかった。
  3. 記録にしか無いモデル（提供されていないもの）は、**数に混ぜない**。
     参考として別に出すのは良いが、主たる数字は提供されている分である。
  4. 行末の注意書き（`not this count`）は、数字が正しくなるので**消すこと**。
