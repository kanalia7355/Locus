# Task `T-PH9-416`: 屑掃除の試験データが、その票自身の屑を守ってしまうのを直す

## SCOPE — レビュアーへ（先に読むこと）

- **「参照されているパスは掃かずに止める」という判断自体は正しい。壊さないこと。**
  範囲内のテキストが名指しするパスは「範囲が狭すぎた本物の作業」であり、
  止めるのが正しい。この票は**その判断を撤回する票ではない**。
- **`gates.litter` の docstring が言う偏り（「ジョブを止めるのは取り返せるが、
  ワーカーのファイルを消すのは取り返せない」）を反転させないこと。**
  迷ったら止める側に倒すままでよい。
- **自己弁護の穴を再び開けないこと。** `T-PH7-211` のワーカーが `git status` の出力を
  `git_status.txt` に保存し、その一覧が兄弟の屑 8 件すべてを名指して集合ごと
  掃き出しから守った、という前例がある。だから参照元は**範囲内のテキストに限る**
  という現在の制限がある。これも維持すること。

## TASK DEFINITION (Assigned by Orchestrator)

- **なぜこの票があるか**: 屑掃除（`jobloop/gates.py` の `litter()`）は、緩いパスが
  **範囲内のテキストから言及されていれば掃かない**。ところが屑掃除自身の試験
  （`tests/test_jobloop.py`）は、試験データとして屑の名前を**文字列で持っている**。
  したがって**範囲に `tests/test_jobloop.py` を含む票は、自分の屑を掃けない。**

- **実測された証拠**（2026-11-25 13:21、オーケストレーターが手で測った）:
  - `T-PH9-406` が `test_output.txt` で `out-of-scope change` として停止した。
    中身は pytest の出力そのもの（`77 passed in 25.57s`、183 バイト）で、
    変更が参照している実体ではない。**掃かれるべき屑だった。**
  - 掃かれなかった理由は、同じ票の範囲内にある `tests/test_jobloop.py` が
    `"test_output.txt"` を **436・444・474・477・480 行**で試験データとして
    持っていたことである。
  - 同じ試験データには `check_select3.py` と `debug_test.py` も出てくるので、
    それらの名前でも同じことが起きる。
  - これは `diagnose` に **REGRESSION** と表示されるが、掃除が壊れたのではない。
    **掃除の試験が掃除を無効化している**という別の形である。

- **Implementation Details**:
  - 直し方は実装者が決めてよい。性質だけを示す: **試験データの中の名前は、
    緩いパスを守る根拠にならない。** 実際に使っている形（import、ファイルを開く、
    設定に書かれたパスなど）は、これまでどおり守る根拠になる。
  - **どう区別したかを記録に書くこと。** 区別の基準が後から読めないと、
    次に同じ穴が開いたときに判断できない。

## ACCEPTANCE CRITERIA

1. 範囲に `tests/test_jobloop.py` を含む票の、ワークツリー直下の追跡外 `test_output.txt`
   が**掃かれる**ことを示す試験がある（`T-PH9-406` と同じ形）。
2. **実際に使われているパスは、これまでどおり掃かれずジョブを止める**ことを示す試験がある
   （範囲内のコードが import する、または開くファイルを緩いパスに置いた場合）。
3. `git_status.txt` 型の自己弁護（屑が屑を名指して集合ごと守る）が**依然として効かない**
   ことを示す既存試験が通り続けること。
4. 範囲内のファイルが 1 つでも読めなかったときは**何も掃かない**という現在の安全側の挙動が
   壊れていないことを示す既存試験が通り続けること。
5. `python -m pytest tests/test_jobloop.py -q` が緑。
6. `python -m ruff check jobloop tests` と `python -m ruff format --check jobloop tests` が緑。
