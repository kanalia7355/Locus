# Task `T-PH3-101`: 取り込み状態の粒度・再開性強化（PH-ROADMAP-3 残部）

## TASK DEFINITION (Assigned by Orchestrator)

- **Requirement IDs**: `PH-ROADMAP-3` 残部（`docs/plans/PHASE_STATUS.md` Phase 3 Remaining 列のうち
  isolation 可能な「ingestion status improvements」）。roadmap §4 は
  「ingestion/UI status improvements can proceed in parallel if isolated」を許可している。
- **Out of scope（gate 付き・本タスクでは実施しない）**: PDF/OCR パーサ隔離、外部ストレージ
  コネクタ（ローカルフォルダ/NAS/オンライン）、production DB/vector アダプタ、分散 resumable jobs。
  対応フォーマットは現状の text/MD/CSV のまま。
- **Background**:
  - 現状の取り込みは bounded text ingestion（スキャナ default quarantine、queue/cancel、
    source/page/chunk metadata 付き）。`frontend/src/IngestionProgress.tsx` に状態表示がある。
- **Implementation Details**:
  1. 先に `backend/app/service.py` の取り込み・キュー実装と IngestionProgress UI を読む。
  2. 状態の粒度: 取り込みジョブの状態を `queued / scanning / indexing / done / failed(reason)`
     で報告し、UI に各段の進行を表示する（失敗理由は機密値を含まない短い区分）。
  3. 再開性: 同一 bounded 範囲内で、ジョブ実行中の再起動・失敗時に
     **チェックポイント（完了済みチャンクの索引再利用）**から再開できるようにする。
     分散実行・複数ワーカーは範囲外（単一プロセス内の再開のみ）。
  4. ACL: 取り込み中・再開中を通じて既存の live permission checks を維持。
     スキャナ fail-closed（検査不能時は隔離のまま）を維持。
  5. テスト: 状態遷移 API テスト、再開テスト（強制中断 → 再開 → 完成一致）、
     権限喪失時の取り込み拒否テストの追加。
- **Acceptance Criteria**:
  1. 取り込み状態が段階表示され、失敗時に区分理由が出る。
  2. 単一プロセス内での再開が動作し、重複索引チャンクが生成されない（合成テストで検証）。
  3. 既存の quarantine・取消・削除伝播の退行なし。
  4. 変更が許可パス内。

- Summary:
  - Added coarse stages (queued/scanning/indexing/done/failed) to document
    metadata (`stage`) while keeping persisted statuses backward compatible
    (`ready` stays the usable status; `quarantined`/`cancelled` map to failed).
    `failure_code` exposes a short non-sensitive category
    (permission_revoked / scanner_rejected / scanner_unavailable / index_failed /
    cancelled); existing Japanese reasons are unchanged.
  - Added `documents.index_checkpoint` and a resumable indexing path. Indexing
    writes one page per transaction and commits the checkpoint before the next
    page. `_index` reuses pages at or below the checkpoint and replaces only the
    incomplete page, so a restarted run does not duplicate chunks. The existing
    `_index(db, row)` call contract and its checked final transaction are kept.
  - `recover_jobs` requeues scanning/indexing work and retries `index_failed`
    jobs from their checkpoint. ACL is re-checked before scanning and on every
    indexed page; losing permission cancels the job and deletes its chunks.
    Scanner fail-closed/quarantine behavior is unchanged. Cancel now also covers
    indexing and removes chunks; delete propagation still relies on the chunks
    FK cascade.
  - `IngestionProgress` now shows the indexing stage, active jobs with their
    stage, and incomplete jobs with the short failure category.
  - Design/scope note: `frontend/src/App.tsx` (outside the allowed paths) still
    gates polling on `queued`/`scanning` only, so a client may need a manual
    refresh to observe the `indexing` status while it is active. The persisted
    status itself and the UI component support the new stage.
  - Docs/code inconsistency observed: `statusName` in `frontend/src/api.ts`
    (outside allowed paths) has no `indexing` entry; `IngestionProgress` uses a
    local label instead. No documentation conflict affecting this task found.
