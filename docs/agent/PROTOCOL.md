# Locus 自律開発ハーネス 通信・運用プロトコル (`PROTOCOL.md`)

本書は Locus リポジトリにおける自律開発ループの役割分担、ファイル所有権、状態遷移、進捗報告フォーマット、およびサイクル・マージ規約を定義する正本である。
Superpowers 等の外部スキルフレームワークの手順が本書と衝突する場合は、**常に本書の規定を優先**する。

---

## 1. 役割分担

| 役割 | 担当実行系 / モデル | 責務と権限の境界 |
|---|---|---|
| **ハーネス実行基盤** | `pi` (`.pi/extensions/harness/`) | 30分間隔の `progress/` ポーリング、差分検出時のオーケストレーター（Luna）起動、モデルローテーション・cooldown 状態（`.pi/harness/state.json`）の保持。 |
| **オーケストレーター + QA** | Codex CLI (`gpt-6-luna`) | タスク分解、重み付け（`heavy` / `medium` / `light`）、担当モデル割当、`status` 遷移管理、QA（受入条件とテスト結果の機械的照合）、Phase サマリ（`PROGRESS.md`）の更新。**コードの実装・改変は一切行わない。** |
| **実装ワーカー (Implementer)** | `agy` モデル群 / OpenCode 無料モデル / `ollama/gemma3:4b` | 割り当てられた個別 git worktree 内でのコード実装、変更関連テストの実行、担当タスク進捗ファイル（`REPORT` / `TEST` 欄および frontmatter の `status: review`, `updated`, `attempts`）の更新。 |
| **レビューワーカー (Reviewer)** | 実装ワーカーとは**別のモデル**（`agy` / OpenCode 無料モデル） | 実装差分と受入条件の照合、担当タスク進捗ファイルの `REVIEW` 欄への指摘記録、および frontmatter の `status`（合格時は `qa`、差し戻し時は `doing`）と `updated` の更新。**プロダクトコードの直接改変は行わない。** |
| **人間 (Owner)** | リポジトリオーナー | 改善点の指示、`blocked` タスクや仕様判断（要決定事項）の裁定のみ。 |

## 2. 通信規約とファイル所有権表

- **直接通信の禁止**: エージェント同士（ワーカー間、またはワーカーからオーケストレーターへ）の直接通信・プロセス起動・メッセージ送信は禁止する。すべての連携はリポジトリ内の Markdown ファイル経由で行う。
- **ワーカーの完了境界**: ワーカーの仕事は、自身の git worktree 内で作業し、担当タスクの進捗報告 Markdown ファイルを更新するところまでとする。

### ファイル所有権表（誰がどのファイルを書けるか）

| パス / 対象 | オーケストレーター (`Luna`) | 実装ワーカー | レビューワーカー | ハーネス (`pi`) | 人間 |
|---|---|---|---|---|---|
| `progress/<phase>/PROGRESS.md` | **書込可（専任）** | 読取のみ | 読取のみ | 読取のみ | 読取 / 指示 |
| `progress/<phase>/tasks/<TASK-ID>.md` (frontmatter: `id`, `phase`, `weight`, 初期割当, `qa`/`done`/`blocked` 遷移) | **書込可** | 読取のみ | 読取のみ | 読取のみ | 読取 / 指示 |
| `progress/<phase>/tasks/<TASK-ID>.md` (`REPORT` / `TEST` 欄、frontmatter の `status: review`, `updated`, `attempts`) | 読取のみ | **書込可（担当タスクのみ）** | 読取のみ | 読取のみ | 読取 |
| `progress/<phase>/tasks/<TASK-ID>.md` (`REVIEW` 欄、frontmatter の `status: qa` または `doing`, `updated`) | 読取のみ | 読取のみ | **書込可（担当タスクのみ）** | 読取のみ | 読取 |
| プロダクトコード・テスト（担当 worktree 内の許可パス） | **書込禁止** | **書込可（担当範囲のみ）** | **書込禁止** | 書込禁止 | 任意 |
| `.pi/harness/state.json` | 読取のみ | 触らない | 触らない | **書込可（専任）** | 任意 |
| `.pi/extensions/harness/**` | **改変禁止** | **改変禁止** | **改変禁止** | 実行のみ | 保守のみ |
| `docs/planning/**`, `docs/plans/**`, `loop_engine/**`, `.loop/**` | **改変禁止** | **改変禁止** | **改変禁止** | 触らない | **専任** |

- ワーカーは**自分に割り当てられたタスク進捗ファイル1つだけ**を更新でき、他タスクの進捗ファイルや `PROGRESS.md` を書き換えてはならない。
- `_template/` 配下の雛形ファイル（`progress/_template/**`）は参照専用のテンプレートであり、ポーリング差分で検出された場合もオーケストレーターは状態遷移や割当の対象から除外する。

## 3. `status` 語彙と状態遷移

タスク進捗ファイルの `status` は以下の **6語彙のみ** を使用する（大文字小文字を含め厳密に一致させること）。

```text
todo → doing → review → qa → done
  ↘      ↓        ↓      ↓
            blocked
```

| `status` | 意味 | 遷移させる主体 | 次の遷移条件 |
|---|---|---|---|
| `todo` | 未着手（タスク分解・重み付け済み、ワーカー割当待ち） | オーケストレーター (`Luna`) | オーケストレーターが担当モデルを決定し `doing` へ遷移させる |
| `doing` | 実装ワーカーによる実装・修正および関連テスト実行中 | オーケストレーター（初回割当時）またはレビューワーカー / QA（差し戻し時） | 実装と関連テストが完了したら実装ワーカーが `review` へ遷移させる |
| `review` | 実装モデルとは**別のモデル**によるコードレビュー待ち・実施中 | 実装ワーカー | 指摘なし（承認）ならレビューワーカーが `qa` へ、要修正なら `doing` へ戻す（レビュー周回上限2周） |
| `qa` | オーケストレーター (`Luna`) による受入条件・テスト結果の機械的照合待ち | レビューワーカー | 受入条件とテスト証跡がすべて揃っていれば `Luna` が `done` へ、不足があれば `doing` へ戻す |
| `done` | 1サイクル（実装 → レビュー → QA）完了 | オーケストレーター (`Luna`) | サイクル完了コミットおよび CI グリーン確認後のマージ対象となる |
| `blocked` | 試行上限到達、全モデル枠枯渇、仕様上の未決事項・判断境界への到達により停止 | オーケストレーター (`Luna`)（または上限到達を検知した主体） | タスク進捗ファイルおよび `PROGRESS.md` に理由を記録し、heavy レビューまたは人間の判断を待つ |

## 4. 進捗報告の frontmatter 規約

配置済みの `.pi/extensions/harness/poll.ts` は、ファイル先頭の `---` から次の `\n---` までを行単位（`^([A-Za-z0-9_-]+):\s*(.*)$`）で解析する。すべてのタスク進捗ファイル（`progress/<phase>/tasks/<TASK-ID>.md`）は、**厳密に以下の形式**をファイル先頭（1行目）に持たなければならない。

```yaml
---
id: T-001
phase: phase-<slug>
status: doing
assignee: agy
model: Gemini 4 Argon
weight: medium
updated: 2026-11-12T13:00:00+09:00
attempts: 1
---
```

### フィールド規定
1. **ファイル先頭**: 必ず1行目が `---` で始まり、フィールド定義の直後に単独行の `---` で閉じること（先頭に空行やコメントを置かない）。
2. **スカラー値のみ**: 値はすべて単純な1行スカラーのみとする。YAML のネスト（オブジェクト）や配列（`- item`、`[...]`）は一切使用しない。
3. **必須キー**:
   - `id`: タスク識別子（例: `T-001`）
   - `phase`: 対象 Phase スラッグ（例: `phase-3-ingestion`）
   - `status`: `todo` | `doing` | `review` | `qa` | `done` | `blocked` のいずれか
   - `assignee`: 実行ハーネス種別（`agy` | `opencode` | `ollama` | `codex` | `unassigned`）
   - `model`: 担当モデルの表示名または slug（例: `Gemini 4 Argon`, `Claude Sonnet 5.5`, `opencode/big-pickle`, `gemma3:4b`）
   - `weight`: タスクの重み（`heavy` | `medium` | `light`）
   - `updated`: 最終更新日時（ISO 8601 形式、例: `2026-11-12T13:00:00+09:00`）。**ファイルを更新するたびに必ず現在時刻へ書き換えること**（`poll.ts` は `status` または `updated` の変化で差分を検出する）。
   - `attempts`: 実装試行回数（整数スカラー `0`, `1`, `2`, `3`）。上限は `3`。

## 5. ポーリング・サイクル・ブランチ・マージ規約

### 5.1 30分ポーリングの手順
1. `pi` ハーネス拡張（`index.ts`）が **30分間隔**（`pollIntervalMs = 1,800,000 ms`）でメインチェックアウトの `progress/` 配下の `.md` ファイルを走査する（手動実行時は `/harness-poll` コマンド）。
2. `.pi/harness/state.json` の `progressSnapshot` と比較し、新規ファイルまたは frontmatter の `status` / `updated` が変化したファイルを抽出する。
3. 変化が1件以上ある場合、`.pi/harness/prompts/orchestrator.md` に差分要約を添えて `codex exec --model gpt-6-luna --sandbox workspace-write --full-auto "<prompt>"` を起動する。
4. ワーカーは自身の worktree の `progress/` に進捗を書き、1サイクルのコミットに含める（ブランチのマージによりメインチェックアウトの `progress/` に集約される）。

### 5.2 1サイクルの定義とコミット条件
- **1サイクル = 実装 (`doing`) → レビュー (`review`) → QA (`qa` → `done`)**。
- レビューは必ず**実装したモデルとは別のモデル**が担当する。
- QA でオーケストレーター (`Luna`) が受入条件とテスト結果を照合し、`status: done` となった時点で 1 サイクル完了とし、worktree の変更一式（コード・テスト・`progress/` の進捗報告 md）をコミットしてよい。

### 5.3 ブランチ階層とマージ条件
- **ブランチ階層**:
  ```text
  main ← phase/<slug> ← worktree ごとのサブブランチ (例: task/<id> 等)
  ```
- **サブブランチから `phase/<slug>` へのマージ条件**:
  - 1サイクル（実装 → レビュー → QA）が完了してコミット済みであること。
  - **GitHub Actions の CI がグリーン（`success`）**であること。
- **Phase ブランチから `main` への自動マージ条件**:
  - 当該 Phase の全タスクのループが完了し、Phase の節目でのフルスイート検証および **GitHub Actions の CI がグリーン**であることを確認したうえで、`phase/<slug>` ブランチを `main` へ**自動マージ**する。

### 5.4 試行上限とエスカレーション
- **タスク試行上限**: 1タスクあたり **最大 3 回**（`attempts: 3`）。
- **レビューサイクル上限**: 1回の試行につきレビュー差し戻しは **最大 2 周**。
- 上限に達しても `done` に至らない場合は、無制限にリトライせず、即座に `status: blocked` に遷移させ、タスク進捗ファイルおよび `PROGRESS.md` に具体的な失敗理由・証跡を記録して人間の指示を待つ（または仕様判断が必要な場合は heavy モデルのレビュー / 人間へエスカレーションする）。
- **注意**: モデルの利用枠枯渇（Quota Reached / Rate Limit）は「モデルの失敗」ではないため、`attempts` を消費せずにモデルローテーション表の次候補へ切り替える。
