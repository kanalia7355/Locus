# 設計相談・第2ラウンド（Argon へそのまま渡す用）

あなたの提案（薄型ランナー + ステートレス `codex exec` Luna + 同期ワーカー）を
土台候補として検討しています。採用前に、指摘された穴4点＋1点について、
**仕組みのレベルで具体的に詰めて**ください。「気をつけます」ではなく、
データ構造・コマンド仕様・判定手順の形で答えること。

## 穴1: レビュー判定の読み手が曖昧

- 「レビュアー終了後、APPROVED → qa / 要修正 → doing へ自動で」とあるが、
  REVIEW 本文の判定文を**誰が・どうやって**読むのかが書かれていない
- 候補として検討してほしい: レビュアーが `task-ctl` で構造化した verdict を
  記録する (例: frontmatter に `verdict: APPROVED` と `verdict_round` を書く)
  方式。この場合に答えること:
  - レビュアーが verdict の記録を忘れた / 失敗したときの検出とフォールバックは？
  - QA 差し戻し後の再レビューで、**前回の APPROVED を「済み」と誤認しない**
    仕組みは？ (実際に起きた事故: 古い判定が残っていて再レビューが永久に
    起動しなかった)。verdict と attempts / ラウンド番号の紐付け方を具体的に
  - 判定の確定はランナー (決定論) か Luna (LLM) か、どちらに寄せる？

## 穴2: コミット対象パスの指定が `git add -A` になっている

- これは過去の実事故と矛盾する: 一括 add で別タスクの成果物まで同一コミットに
  巻き込まれた。パス限定が原則
- 答えること:
  - タスク done 時のコミットに含めるパスの決定手順は？
    (タスクの Allowed Paths ∩ git status の変更分？ REPORT の Changed Files 欄？)
  - 台帳ファイル (タスクファイル自体・PROGRESS.md) のコミットは成果物と
    同一コミットか、別コミットか。その理由も
  - worktree 運用と組み合わせたときの、worktree → phase ブランチへの
    統合手順 (マージ or チェリーピック等) の具体

## 穴3: ワーカーのタイムアウト15分の根拠

- 実測では agy の重いタスクは30分級の実行がある。15分で切ると正常な作業を
  殺しかねない
- 答えること:
  - 重み別 (light / medium / heavy) のタイムアウト値の設計は？
  - タイムアウトで kill した場合、attempts は消費する？ worktree に残った
    未完了の変更は保持して再開に使うか、捨てるか？

## 穴4: 「事故は100%消滅」は言い過ぎ — task-ctl 自身のパース仕様

- task-ctl の `list` も結局は frontmatter パーサである。表面積は小さいが
  ゼロではない
- 答えること:
  - task-ctl が許容する frontmatter の範囲を仕様として明記してほしい
    (キーの順序、クォート有無、未知キー、重複キー、値の前後空白)
  - それでも frontmatter が壊れていた場合 (ワーカーが手で書き換えた等)、
    ランナーはどう振る舞う？ **黙って対象から消えることだけは絶対に避ける**
    こと (それが今回の事故の本質)。検出方法と、ユーザーへの見せ方まで

## 追加の論点: モデルローテーションの実態

- 現行の MODEL_ROTATION は全ウェイトで agy が先頭のため、OpenCode 無料モデルが
  一度も使われていない (ユーザーの元々の動機とズレている)
- light / medium の実装は OpenCode 無料プールを第一候補にする配分変更を、
  あなたの構成ではどう反映する？ ローテーション表自体の改訂か、
  ランナー側の選択ロジックか。cooldown 状態の持ち方 (キー設計) も含めて
