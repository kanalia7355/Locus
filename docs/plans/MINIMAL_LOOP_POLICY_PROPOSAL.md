# 最小構成の自律開発Loop：承認ポリシー変更案

2026-11-06。**提案のみ。未採用・未有効化。**
根拠は同日の所有者指示。旧承認の拡張や失効許可の再利用はしない。
既存Controller／Development Loop／StateStore／C-min／local_commit_pushを使用する。
新しいサービス、アカウント、認証クライアント、オーケストレーターは作らない。

## 到達点

最初のマイルストーンは、所有者が許可した`$loop 30m`が実際に推論・実装・QA・
自動コミット／専用ブランチPushを行い、終了ログと永続状態で実行時間・結果を
確認できること。設計、模擬試験、承認文書の完成では達成としない。
安全停止・Goal完了等で早期終了した場合も、30分完走とは別に報告する。
時間を埋めるための無意味な改善・再試行は生成しない。

## 提案する許可の単位

| 単位 | 承認範囲 | 個別承認を求めない通常操作 |
|---|---|---|
| 恒常ポリシー | このLocus作業環境、現在の所有者、検証済み公式CLI、既存ChatGPTログインに限定。所有者の撤回まで有効 | 公式CLIによる既存認証の利用・通常更新・同じ保存先への保存 |
| 30分セッション | 実行時のモデル・ブランチ・作業範囲・上限を固定して承認。開始は承認後、期限は一度だけ固定 | Worker／Reviewer／GoalEvaluator、局所的な修正、必要なQA・自動レビュー、Conventional Commit、loop/local-developmentへの通常Push |
| 例外判断 | 下記の重要操作のみ、その時点で対象・影響を具体化して承認 | 例外を通常操作へ読み替えない |

恒常ポリシーは無期限のモデル実行許可ではない。推論・開発には別の有限セッションが必要。
現時点のモデルはgpt-6.1-sol、APIキーによる追加従量課金は利用しない。
セッションの通常変更範囲は既存設定のbackend／frontend／tests。
制御基盤・認証・CI・安全設定をモデル自身が書き換える権限は与えない。
既存の20タスク、20評価サイクル、タスク3試行、レビュー修正2サイクル等の上限を維持する。
中断後の再開で元の実行ID・期限・試行回数を増やさない。
中継への経路強制が確認でき、送信前と確定した失敗は原上限内で修正・再検証する。
送信予約後や結果不明の同じ呼出しは、別IDを付けても自動再送しない。

### 引き続き個別承認する操作

- API課金経路への切替、契約変更、購入・課金上限の変更。
- 通常の公式認証・推論先以外への認証情報送信、抽出、複製、移行、別用途利用。
- 新規ログイン・本人認証回復、保存方式変更、ACL・アカウント・サービス・実行権限の拡大。
- 実データ・認証ファイル・復旧証跡の破壊、Git履歴改変、強制Push、main更新。
- Goal・受け入れ条件の緩和、重大な設計／機密性の変更、実研究資料の外部送信。

公式CLIが既存ログインの認証ヘッダーを同じ公式接続先へ通常利用することは、
恒常ポリシーに明記して許可する。これを第三者への認証情報流出の許可にしない。
同一PCの既存中継メモリでの一時転送も、固定された公式推論先に限定する。
この区別を曖昧にすると毎回の認証承認が再発するため、採用時に明示する。

## 保証が変わる箇所：所有者の明示承認が必要

| 現行 | 変更案 | 維持する保証／残るリスク |
|---|---|---|
| 認証ファイルのサイズ・更新日時の変化もHOLD | 公式CLIの通常更新に伴う同じファイルへの変更を許容。次の呼出しは更新後メタデータを照合 | 厳格ACL・所有者・ファイルID、差し替え／reparse拒否、エージェントの内容読取禁止を維持。サイズ・更新日時も固定する条件は外す |
| 通常v3成功receiptが通常実行開始の前提 | 事前の実接続成功receiptを初回起動の必須条件から外す。現在のコードのQA／ゲート適合性を確認し、最初の実呼出しから検証する | 未検証を事前成功と扱わない。推論を中継へ確実に誘導し、要求・応答のゼロツール検証を通すことは各呼出しで必須 |
| 単発試験の生涯枠が通常実行の準備と結合 | 単発試験は診断用に隔離し、通常セッションの前提にしない | 古い試験の履歴・保留・予算を消さず、同じ呼出しを再送しない |
| 保留された呼出しが独立した新規作業も止める | 終了・プロセス回収が確認できた診断の保留を維持しつつ、別の所有者承認セッションを許可 | 未回収プロセス、進行中配送、同じtask／attemptの不確定送信は引き続き停止条件。単なる状態ラベル変更で解除しない |
| 多重の起動receipt・専用試験承認 | ポリシー適合性と一つのセッション承認へ統合 | 各呼出しの所有権・期限・送信予約・再送防止は統合せず保持する |

認証ファイル更新を「公式CLIだけが行った」とOS監査なしで完全に証明するとは主張しない。
既存の同一Windowsユーザーと公式CLIを信頼する範囲は残る。
既存認証ファイルには平文保存のリスクがある。暗号化保証は追加しない。
通常の認証更新通信全体を推論中継が検査する保証もない。既存ログインを信頼し、
カスタムissuer／provider等の設定追加を許可しない。新しい強制ネットワーク基盤は作らない。

ゼロツール、認証情報の非抽出、既知の固定公式推論先、TLS検証、各送信の永続予約、
未知プロトコルの拒否、プロセス回収、QA／CI、独立レビューは維持する。
中継経路が実際に使われることを確認できなければ、通常操作として送信してはならない。

## 棚卸しと最初に削る複雑性

| 機能群 | 通常Loopでの扱い |
|---|---|
| Controller／Development Loop／タスクDAG／停止・復旧 | 再利用。新しい実行ループは作らない |
| ローカルQA・自動レビュー・LocalDelivery | 再利用。レビューは通常は自動で、人間への差分ごとの確認にしない |
| PR／Review App／Merge Broker／Windows監査サービス／main統合 | 通常配送では既に不要。起動判定・説明も分離し、再導入しない。設定・鍵・サービス・記録を勝手に変更しない |
| C-min中継・request／response gate・OwnedCliPeer・journal | 共通の実行境界として再利用。auditというファイル名だけで削除しない |
| 単発許可・入力契約・試験用証跡 | 診断専用に分離。通常の各タスクへ専用承認パケットを要求しない |
| 重複した起動前receipt判定・全legacyソースへの証跡依存 | 共通の起動判定へまとめ、モデル実行境界と無関係な変更で起動不能にしない |
| 証跡 | run ID、時間、件数、結果、コミット、停止理由を既存journalに記録。重複manifest群を通常操作の成果物にしない |

現状は直下のPythonモジュール93個（コンテナ内supervisorを含めると型検査対象94）。
名前による機械的分類ではApp／audit／service／broker系が34個あるが、
audit_transport等は現行C-minでも使用するため、34個全部を不要と判断しない。
最初の30分稼働より前に全体を削除・再設計しない。まず通常経路の依存を減らす。

### テストの扱い

- 継続必須：期限・承認・ACL・プロセス所有・ゲート・journal・復旧・QA・配送・Goal整合性。
- 新規ポリシーを試験する：通常refresh許容とACL／ID不正拒否、セッション内複数タスク、
  独立診断の保留を維持した新規session、未知送信の再試行拒否、実時間上限と終了。
- 旧ポリシー・App／Broker／配備テストは旧機能の回帰として区別する。
  初回移行では既存テスト・CI必須条件を削除／無効化しない。
  後の削除は到達性・要求・代替検証を示して行い、「古いから」「greenにするため」では行わない。

## 実装順序と承認範囲

1. 本案の所有者承認。設計・実装と、既存PolicyMigrationによる具体的な移行案の準備を許可する。
   未提示の将来の移行targetを承認したものとは扱わない。
2. 単発試験の失敗を、既存journalに有限の段階／終了コードだけを残す最小診断で再現する。
   本文・認証・推論ログは増やさない。実接続を再送せず、まず合成環境で直す。
3. 既存認証利用とセッション許可を接続し、通常経路から専用単発試験／手動receipt依存を除く。
4. QA・独立レビュー・専用ブランチPush・CI。新しい安全例外が必要なら自動採用しない。
5. 具体的な移行差分・targetハッシュと、有限30分の初回実セッション条件をまとめて提示する。
   既存PolicyMigrationの正確なtargetへの所有者承認を維持し、同じ確認でセッションも許可を求める。
   移行が正常に確定し、承認された条件に一致した場合だけ実起動する。
   各モデル呼出しや通常の修正・QA・コミットについて再承認は求めない。
6. 実稼働ログと永続状態を確認する。30分未達・安全停止・失敗はそのまま報告して改善する。

本案の承認は、上記の恒常利用ポリシーへの移行設計・実装・検証・具体的移行案の準備を認めるもの。
恒常許可の有効化は、具体化した移行targetの別途承認・正常適用後。
本案への承認を将来のtargetの承認へ変換したり、エージェントが自分で承認行を解決したりしない。
無制限の実行許可、現在の失敗試験の再送、今回の30分実セッションそのものの承認ではない。
本案が未承認の間は、現行の厳格な条件と保留状態を維持する。
