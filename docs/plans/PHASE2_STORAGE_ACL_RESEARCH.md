# 元保存先ACL対応 — research and design note

Status: research proposal only; no behavior or owner decision is approved by this note. Scope: interpret D5 in `PHASE2_JOB_BREAKDOWN.md` against the original design and integrated code. P4B is in flight and is not evidence of integrated functionality.

## Executive finding

The original design uses 保存先 for the *source repository/location* from which material is selected and ingested (initial candidates: local folders/NAS, later perhaps an online Drive). It distinguishes source connection and folder selection from the ingestion/indexing pipeline. The design explicitly leaves the correspondence between source ACLs and Locus permissions unresolved. It does **not** define “保存先 ACL” as simply the ACL on Locus's own database/files, nor approve any connector or credentials.

**Recommended interpretation to take to the owner:** make source identity, source authorization and source lifecycle propagation the core of D5. A source ACL should be an additional, fail-closed gate on access to the ingested document and all derived material, not a replacement for Locus project/publication ACLs. Treat source change/deletion propagation and original-byte retention as related but distinct requirements. Future connector configuration is a separate prerequisite/workstream, not an implied authorization decision in PH2-C. This is a proposal, not a decision.

No source connector or source ACL is implemented at integrated HEAD. Current uploads are bounded user-provided text in the application database; document access is currently authorized by Locus ownership, membership, publication grants, and conversation attachment rules. The current code cannot establish whether a source file still exists or whether its source ACL permits a user.

## 1. Evidence: what 保存先 meant in the original design

- `docs/requirements/PRODUCT_SPEC.md` defines organization/project/user separation, document ACLs, permission-filtered retrieval, file ingestion and provenance-aware local RAG. Its 2026-10-29 refinement points to the planning documents for folder ingestion, personal documents and role-and-scope publication. It does not name an approved storage service, connector, or source-ACL algorithm. The same spec leaves provider, capacity and retention decisions open.
- `docs/architecture/ARCHITECTURE.md` describes upload/ingestion, isolated storage, indexes and deletion propagation at a logical level. It calls the technology an initial proposal and defers refinement; it does not specify source connector semantics or source ACL inheritance.
- `docs/planning/research-app-concept.md`, section 8, is the first explicit storage-destination design in repository history (introduced with the initial planning package in commit `c48065e`, 2026-10-31). It proposes administrator-configured shared source locations and directories, with local/NAS as an initial candidate and online Drive only as a later candidate. It separates “保存先との接続” from analysis/indexing; describes manual browser upload and persistent server-side connection as distinct options; and explicitly says connection method and providers are not decided. Its table says source permissions correspondence must be examined, not that one particular mapping is approved. It proposes leaving originals at the destination and managing extracted text, chunks, index and provenance, but says copies/temporary storage and retention remain undecided.
- `docs/planning/ui-and-multiuser-design.md` explicitly leaves “元保存先の権限との対応” undecided. It also separates source-connection administration from document publication rights and says personal documents/attachments do not become public merely because a user has a role. Its administration UI labels are proposals, not evidence of an integrated connector.
- History check: `git log --all -S'保存先' -- docs` finds the initial design addition in `c48065e` and later planning/reconciliation changes. The initial `PRODUCT_SPEC.md` and `ARCHITECTURE.md` from `c48065e` mention general document ACLs/ingestion but do not define an original-source ACL. The exact ambiguity was acknowledged in the later planning text and D5; no earlier design resolves it.

Therefore “元保存先” most plausibly means the original source location of material ingested into the research library, not a destination for exporting Locus data. The storage-destination phrase is broader than the currently implemented upload flow.

## 2. Integrated HEAD: current storage and authorization behavior

### Ingestion/storage

- `docs/INGESTION_SCANNER.md` and `backend/app/scanner.py`: scanner input is bounded UTF-8 text (262,144 bytes), with a default fail-closed unavailable scanner and an optional, explicitly configured loopback ClamAV adapter. The scanner is a content safety check, **not** a connector, source-identity lookup or source ACL check. A scanner adapter may receive document content; its configuration is server-owned. Its docs warn that enabling it transfers content outside the Locus process, even though its fixed target is loopback.
- `backend/app/service.py`, `Store` schema initialization: SQLite `documents` stores `owner_id`, `project_id`, `kind`, `name`, full `content`, `status`, optional `conversation_id` and JSON publication `grants`; `chunks` store derived text and reference `documents` with cascade deletion. No storage-destination/source ID, source path/object ID, source ACL snapshot/version, connector credential or source lifecycle state exists.
- `Service.upload`, `process_next`, `_index`, `cancel`, and `delete_document` implement bounded per-user uploads, queue/quarantine, scanner checks, chunk creation, cancellation and deletion. Queued ingestion permission is checked before exposing content to the scanner and again before indexing. Cancellation clears queued/scanning document content; document deletion removes the document/chunks. These are useful fail-closed patterns but do not propagate source edits, moves, ACL changes or deletion.
- The reconciliation table (`docs/plans/PHASE_SPEC_RECONCILIATION.md`, Phase 3 row) confirms no recursive source-folder scan/listing, source-destination connector, source delta synchronization, original-file link or production storage separation is integrated. `frontend/src/App.tsx` settings show local bounded ingestion and say external AI/storage connections are disabled pending approval. P4B's task brief (`docs/plans/agent-work/PH1-P4B-admin-screens.md`) is only an in-flight assignment for a read-only view and guarded settings; it is **not integrated functionality** and adds no source ACL evidence.

### Current document ACL attachment points

- `Store` schema and `Service._permissions`/`require` implement project permission checks. At this HEAD, PH2-B's integrated implementation combines held roles, applies explicit deny over allow, and denies by default. See `backend/app/service.py` `_permissions`, `_permission_ceiling`, and membership/role methods.
- `Service._can_read` is the central document-level gate: current project permission/membership plus owner-only access for personal documents and attachments; shared documents additionally require a matching current role grant for `read` or `retrieve`. `_document` applies the gate before returning a document. `Service.publish` limits publication to same-project roles and `read`/`retrieve` operations; attachments cannot be published.
- Document metadata/list, chunks, related documents, citations, generated-answer visibility and retrieval use these checks (`documents`, `document`, `chunks`, `related`, `_citations`, `_generated`, `conversation`, `send`). Conversation history/attachments are owner-scoped and bound to the conversation; live authorization is rechecked for current citations and generated answers. This is the natural shared enforcement surface for a future additional source gate; adding checks only in upload UI would be insufficient.
- `_audit` writes metadata-only audit rows transactionally. Existing document upload/publication/deletion and ingestion operations audit action IDs, not document body text. A future source lifecycle design should preserve that property.

### Recommendation

Take **A as the narrow meaning of D5**: explicitly model source access as a second, current authorization condition, subordinate to (never replacing) existing Locus ACLs. Include **A2** as a necessary lifecycle consequence to specify, while keeping its event/freshness choices open. Treat **C/D** as linked storage/retention design inputs that must be resolved before claiming deletion or ACL propagation is complete. Treat **B** as a separate connector/security configuration phase, not as a feature PH2-C can authorize. Do not implement any interpretation as part of this documentation-only task.

## 4. Outline design for owner review (proposal only)

### Data model sketch

For a future connector-backed import, conceptually separate:

- `storage_source`: opaque ID, connector kind, owner/admin scope, enabled state and non-secret configuration reference; never expose credentials in document metadata or audit. Connector/network enablement is separately owner-approved.
- `source_object`: source ID, stable opaque object ID, canonical path/locator only if necessary, source revision/etag, last observed state/time, source ACL revision/observation status. Avoid treating a display name or mutable path as stable identity.
- `document_source_binding`: document ID, source-object ID, imported revision, sync state and provenance. Define cardinality and behavior for a document derived from multiple sources before implementation.
- Optional ACL representation: prefer a connector-specific live authorization adapter or normalized, versioned source-grant snapshot with an explicit freshness/expiry. Do not store raw credentials or presume an import credential is an end-user grant. If live authorization is unavailable/stale, deny access to source-derived content until a trusted refresh succeeds.
- Derived artifacts (content, chunks, any future vectors/graph/cache/answer provenance) remain linked to the document/source revision so revocation or source change can invalidate the whole dependency set.

This is a logical sketch, not a migration specification. The current application uses SQLite and does not implement this schema.

### Enforcement points

1. **Connector setup and scan/listing:** server-side allowlist of connector types, root/scope and credential permissions; administrator authorization; safe path/object validation; explicit source ACL and coverage preview. No user-controlled arbitrary host/path/URL. External connection is denied unless specifically owner-approved.
2. **Ingestion admission and worker:** confirm source object identity and source permission before reading; recheck permission/revision before scanner exposure and again before indexing/publishing, matching the existing `process_next` two-check pattern. If revoked, deleted, moved ambiguously, changed unexpectedly or unverifiable, do not index/serve stale content; quarantine/unavailable state needs an owner-approved lifecycle contract.
3. **Every read/retrieval path:** add source gate in the shared document authorization surface (`_can_read`/`_document` equivalent) so list, metadata, chunks, related search, citations, generated answers, attachments, exports, caches and model context cannot bypass it. Recheck live authority before returning a citation/answer and before committing long-running work. Never rely solely on UI, import-time ACL or session/job snapshots.
4. **Change/deletion/revocation propagation:** invalidate visibility first (fail closed), then reconcile/delete/re-index content and derived artifacts. Track source revision to prevent stale workers from restoring old indexed data after a newer revoke/delete/change event. Define retry/recovery behavior and a measurable freshness bound before declaring sync complete.
5. **Retention/access to originals:** whichever copy/link policy is chosen, gate access to original bytes independently and apply retention/deletion consistently to source-derived stored copies, chunks/indexes/caches/answers and backups.
6. **Egress boundary:** local-only mode remains no-egress. A connector that contacts a NAS, Drive or other network source is not implicitly approved. External source access and external AI/model transmission are distinct egress destinations and both remain owner-gated; connector data must not be sent to a cloud model as a side effect of import or retrieval.

### Audit proposal

Use the existing transaction-bound, metadata-only convention (`Service._audit`): record actor/service identity, operation, opaque source/document ID, outcome, and time for connector configuration, scan/start, permission refresh/change, source move/delete, index publication/invalidation, and denied/unknown-source decisions. Do not log document content, source credentials, raw provider responses, sensitive filenames/paths or source ACL payloads. Decide whether source identity itself is sensitive and how audit retention/access are controlled. Audit failure for a state-changing authorization transition must not leave a success-looking state; exact atomicity across connector calls and DB transactions needs connector-specific design.

## 5. Contradictions and design/code gaps recorded as findings

1. **No approved connector despite broader planning prose.** The product spec only approves general file ingestion; the concept's local/NAS and online Drive rows are candidates/proposals. Any interpretation that treats those connectors, their credentials, or external egress as approved conflicts with the documents' explicit undecided status.
2. **Source-retained-original model differs from current implementation.** The concept proposes retaining originals at the source and managing derived text/index/provenance, with copy/temporary storage unresolved. Current `Service.upload` stores full extracted text in SQLite `documents.content` and also stores derived chunk text. No source locator or original-byte handling exists. This is a design-to-code gap, not proof that retention has been decided.
3. **Deletion propagation is required abstractly but not available for external sources.** Architecture says deletion should propagate, and concept describes future source delta updates. Current `delete_document` deletes the Locus row/chunks only; it cannot delete or detect an upstream source deletion and does not cover external caches/backups. Do not claim that source deletion has been implemented.
4. **“元保存先ACL対応” is more specific than the product/architecture baseline.** Those approved baseline docs require document ACLs/provenance and broad deletion propagation but do not define source-ACL semantics. The planning text explicitly leaves correspondence open. The D5 label must therefore remain a question for owner approval, not be treated as a complete requirement.
5. **External source access and external AI egress are distinct but both gated.** The concept lists online Drive as a candidate source and separately requires administrator-authorized cloud AI. No source connection can be inferred from approval of local ingestion, and no source connector can grant permission to transmit its content to an external model. Owner authorization is required for either external path.

## 6. 【要決定】 items — intentionally unresolved

1. Confirm that D5 means source-ACL propagation (A), rather than only connector setup (B), local-storage ACL/retention (C/D), or a combination.
2. Which source types and access modes are in scope first: manual browser upload, server-local folder, NAS, or a named online service? Is any source connector in this phase at all?
3. Whether each user's source permission is checked live, represented by a bounded/versioned snapshot, mapped by Locus identity, or deliberately replaced with a separately approved Locus grant. What is acceptable freshness/maximum revocation delay? Who is the source of truth?
4. How source ACL combines with project membership, explicit deny, document publication roles, personal ownership and conversation attachment ACLs. Proposal recommends intersection/additional gate; owner must confirm.
5. What happens to a document when its source ACL is revoked or unavailable, source is disconnected, source object moves/renames, or sync misses events: hide/quarantine, delete, retain but unavailable, or another approved behavior? What happens to already-open conversations/citations/answers?
6. Does source deletion mean delete only the Locus binding/index, delete Locus-held copies and derivatives, or request deletion upstream? Who may initiate upstream deletion? Never assume permission to modify source data from read-only ingestion.
7. Are original bytes copied, temporarily cached, linked or fetched on demand? What retention and backup policy applies to originals, extracted text, chunks, embeddings, cached results, generated answers and audit records?
8. Can one Locus document derive from multiple source objects, and what is the access rule if any source is revoked? How are duplicate objects and stable identity across moves handled?
9. Which administrators may configure a source and its root/scope; who may see paths/credentials/status; how are credentials protected, rotated and revoked? Which connection requires owner approval, and what network/egress allowlist applies?
10. What are source-sync failure, concurrency, retry and race semantics? Define the authorization linearization point for source ACL changes during scan, retrieval and model generation; avoid releasing content after a denial is observed.
11. What source metadata may be logged, how long source-audit events are retained, and what privacy restrictions apply to connector administrators?
12. How does source-level permission interact with external AI policy? This proposal keeps them independent; source read permission must never be interpreted as consent to external model egress.

## 7. Phase/step placement proposal

- **PH2-C (this job):** research, evidence and owner-decision inventory only. No connector, ACL, database or code behavior is decided or implemented here.
- **Before any connector implementation:** owner answers the relevant 【要決定】 items; record a source-specific security/data-flow design and threat review. Keep outbound access disabled until explicit owner authorization. P4B's in-flight storage status UI, if integrated later, is not a substitute for this decision.
- **Phase 3 (documents/search/storage):** source adapters, bounded discovery, source identity/revision, source ACL retrieval/revalidation, indexing/sync/revoke/delete propagation, original/derived retention and source-to-citation behavior belong with the missing connector→ingestion→index lifecycle. Test the full source→ACL change/deletion→every derived read path. Phase 3 is the natural implementation home for A/A2/C/D.
- **Phase 2 authorization integration:** if a source gate changes effective document authorization, update the shared authorization model and PH2 verification matrix; do not implement it as a connector-only side check. Preserve current project, document publication and private attachment gates, including PH2-B explicit deny. PH2-D delegation must not infer source grants from delegated project rights.
- **Phase 4 admin UI/operations:** only after backend semantics and permissions are approved, provide connector configuration/status/coverage/refresh/error/audit controls. UI may not imply a source is connected or access is current when the server cannot verify it.
- **External egress/deployment gate:** owner-approved network and data-flow policy plus deployment-level egress controls are prerequisites for any external source or external AI connection. Connector implementation alone cannot authorize egress.
