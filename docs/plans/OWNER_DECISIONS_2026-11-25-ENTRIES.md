## E3 — 条件の外を理由に差し戻し続ける票を誰が閉じるか

> **03 条件の外を理由に差し戻し続ける票を誰が閉じるのか**
> A受け入れ条件を契約として扱う

**選択: A。受入条件を契約として扱う。**

**与えられた権限**: 票の受入条件 1〜n が**すべて満たされ**、条件の外の指摘が
**別票に移されている**とき、**オーケストレーターが合流を決めてよい。**

**解釈で押さえたこと（歯止め）**:

- **これはレビューの承認を与える権限ではない。** レビュアーの指摘を消す権限でもない。
  条件外の指摘は**必ず別票に残す**（捨てない）。これは今までどおり。
- **受入条件を書き換えて満たす**のは引き続き禁止。条件を変えずに満たされたときだけ
  この権限が働く。
- 使ったときは**どの条件がどう満たされたか、どの指摘をどの票に移したかを記録に書く。**
  「契約だから通した」だけでは後から検証できない。

## E6 — 確認した。結論は「MCP では置き換わらない」（2026-11-25 21:10）

### 測ったこと

**私の側の MCP は繋がった。** Google Drive の MCP コネクタで読み取り一覧を実行し、
オーナーの Drive のファイルが**実際に返ってきた**（件数と形は確認した。
中身とファイル名は私信なのでここには書かない）。Box の MCP コネクタは
この環境に**無い**。`agy mcp list` は `No MCP servers configured` である。

### それでも `T-STC-003` / `T-STC-004` は置き換わらない

理由は 3 つで、どれも設計上のものである。

1. **コネクタは製品の機能であって、エージェントの機能ではない。**
   Locus のバックエンドが、複数の利用者のために、定期的に同期する。
   私の MCP コネクタは**この CLI セッションに結び付いていて**、
   オーナー個人の Google アカウントで動き、**セッションが終われば無い**。
   バックエンドからは呼べない。
2. **MCP は資格情報を無くさない。置き場所を変えるだけである。**
   Drive の MCP サーバ自身が Google API のクライアントなので、
   同じ OAuth 許可かサービスアカウント鍵をどこかで持つ。
   手続きが消えるのではなく、**プロセスが 1 つ増えて手続きはそのまま残る。**
3. **`T-STC-001` が立てた保証を迂回する。** 取り込む文書は走査・ACL・上限を
   必ず通る、という保証である。外部の MCP サーバが文書を取ってくる経路は、
   その通り道の**外**を通る。

### 代わりに提案したいこと（オーナーの判断が要る）

手続きの重さは減らせる。**`T-STC-003` の認証方式を、サービスアカウントから
利用者 OAuth 同意に替える**案である。

| | いまの票（サービスアカウント） | 替えた場合（利用者 OAuth） |
|---|---|---|
| オーナーの手作業 | Drive API 有効化 → **JSON 鍵を発行** → **対象フォルダを共有** | Drive API 有効化 → **ブラウザで 1 回同意** |
| 鍵の保管 | JSON ファイルを機械に置く | リフレッシュトークン（同じく秘密だが**発行の手作業が無い**） |
| 見える範囲 | 共有したフォルダだけ | 同意した利用者の Drive（絞り込みは実装側） |

**どちらが良いかは、見える範囲をどれだけ絞りたいかで決まる**ので、
私では決められない。フォルダ単位で厳密に絞りたいなら今の票のままが正しい。
手続きの軽さを採るなら OAuth に替える。

鍵が無くても、**MCP で本物の応答の形を取れる**。`T-STC-003` のテストは
`httpx.MockTransport` だけで書く決まりなので、その作り物を**推測ではなく
実測した形**から作れる。鍵が来る前に実装を進められるという意味で、これは得である。
必要になった時点でやる（いま先回りはしない）。
