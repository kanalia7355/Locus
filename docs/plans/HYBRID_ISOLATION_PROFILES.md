**Status: design and test plan only; no profile is verified, selected, activated, or authorized for execution.** This package implements the R-ISO-1 design deliverable, not a platform certification. Its requirements derive from owner decision Q3 and accepted ADR-0012; its technology comparisons are options, not selections. Owner-controlled unresolved choices remain **【要決定】**. No Runner, dispatch, egress, provider authentication, credentials, or real data is used or approved here.

## 2. Scope, threat assumptions and exclusions

### 2.1 Protected assets and adversary

The profile boundary protects the host and other workspaces from a potentially hostile or compromised job process, child process, adapter/CLI, and hostile job input. Assume an adversary can execute arbitrary code with the job's in-boundary identity, create/rename files and processes within granted limits, exploit parsers, try path and namespace escapes, and attempt network access. A job is not trusted because its user or provider CLI is legitimate. Desktop profiles additionally consider the interactive signed-in user's private files and session as out of scope to the job. Server profiles additionally consider other tenants/jobs, the control-plane service, and server-local services/data.

**Trusted computing base / explicit limitations:** the profile necessarily relies on a correctly configured host OS kernel, host administrator, hardware/firmware, and—where used—the virtualization hypervisor and its management plane. Depending on the chosen design it also relies on a container/runtime manager, security policy, broker, and image/build chain. A hostile or compromised host administrator, kernel, firmware, hypervisor, or trusted broker is not claimed to be contained. VM execution does not prove immunity to hypervisor/firmware vulnerabilities. Process sandboxing and containers sharing a kernel do not provide a separate kernel boundary. These assumptions and residual risks must appear in each final platform-specific profile claim, not be hidden behind the words “sandbox”, “container”, or “VM”.

A security acceptance authority for residual shared-kernel risk and for any unverified profile is not inferred from Q3. Whether to accept a particular platform/threat level, including residual risk for non-VM profiles, remains **【要決定】**. Until exact profile evidence passes and that risk/activation authority is separately recorded, that profile cannot execute.

### 2.2 Target classes

- **Local / desktop:** a Runner on an interactive Windows or Linux workstation, with user files, sessions, and potentially other workspaces present. The hostile job must not gain the interactive user's identity, home/profile, session handles, device access, unrelated workspace access, or credential-store access. Local physical or administrative ownership does not make host access by the job acceptable. An OS administrator can defeat local controls and is outside the isolation guarantee.
- **Server:** a continuously managed Windows or Linux host that may serve multiple workspaces or jobs. Require isolation across jobs and tenants, restricted service identities, constrained service/management surfaces, controlled resource use, and cleanup even after service/host failure. A server profile must not assume a single trusted interactive user or a single job. An operator with host administrator privileges remains in the TCB.

“Windows” and “Linux” identify broad candidate families, not supported builds. Each passing profile must name the exact edition/distribution, build/kernel, architecture, enabled security features, runtime/hypervisor, image digest, configuration, and Runner/adapter artifact. No OS-family-wide claim follows from testing one version.

## 4. VM and non-VM comparison (no universal selection)

| Approach | Potential benefit | Shared assumptions / limits | Evidence required before any profile can rely on it |
|---|---|---|---|
| **Hardware-virtualized VM / microVM** | Separate guest kernel can reduce exposure to host-kernel interfaces; disposable guest can simplify state destruction and bound the job's visible OS. Can be considered where a hostile job, multi-tenancy, or host-kernel compromise consequences justify extra separation. | Host OS, hypervisor, firmware, management APIs, guest image/build, virtual devices, integration features, networking, and broker/artifact-transfer paths stay trusted. A shared folder, clipboard, host socket, guest agent, or permissive virtual network can reopen the boundary. A VM is not proof of isolation or escape resistance. | Record hypervisor/host/guest versions and policy; verify no unapproved integrations, mounts, devices, services, routes or control plane; adversarially test the host boundary and teardown; bind evidence to image/config/runtime digests; document residual hypervisor risk. |
| **OS process restrictions / restricted identity / sandbox capabilities** | May provide sufficient, lighter-weight isolation for a bounded workload when filesystem permissions, process rights, syscall/capability restrictions and network filters are explicit and complete for the specific OS/build. Avoids requiring a VM universally. | Same host kernel is shared; same-principal access, inherited handles, permission mistakes, child-process behavior, platform variation and kernel vulnerabilities can defeat the boundary. Windows Job Objects are process containment, not full isolation. A namespace or token alone may not address filesystem and network scope. | Prove effective—not intended—identity, ACL/mount/capability/syscall/network policy at OS enforcement points. Test hostile child processes and escape attempts; inspect host telemetry/config; have independent review explicitly accept/reject the residual shared-kernel threat for the named risk class. |
| **Container (process isolation)** | Reproducible image, explicit filesystem mounts, resource limits and policy composition. Rootless Linux OCI can compose namespaces, seccomp, LSM and cgroups; Windows containers offer distinct isolation modes that need their own evidence. | Usually shares the host kernel for process isolation. Runtime/daemon/host remains privileged TCB. A container name or Docker QA precedent is not a product isolation claim. Privileged mode, control socket, host namespaces or mounts defeat key boundaries. | Pin runtime/image, prove effective security configuration and unavailable-feature behavior, reject unsafe modes, and test host/tenant isolation on the exact kernel. If selected threat acceptance needs a separate kernel, a shared-kernel container cannot satisfy that claim alone. |
| **Layering** | Combining a VM with an in-guest restricted process/container can reduce exposure to both guest and application surfaces. | More components and policy can increase misconfiguration, lifecycle, image and evidence burden. Layers do not compose into a guarantee automatically. | Test each boundary independently and the combined failure paths; verify no layer silently weakens another. Document which controls are primary and which are defense-in-depth. |

Q3 resolves the decision *shape* (appropriate verified profiles, no universal VM, no execution absent proof), not the exact technology or acceptable residual risk. The concrete Windows/Linux implementations, supported builds, threat-tier-to-profile mapping, and any owner acceptance of shared-kernel/non-VM risk remain **【要決定】**. Neither this comparison nor a future preference is an activation decision.

## 5. Common enforcement and lifecycle requirements

### 5.1 Filesystem boundary

The job's only writable area is a fresh, per-job workspace inside the verified boundary. Inputs are synthetic, bounded, integrity-checked and read-only where practical; outputs are bounded and released only through an explicitly reviewed narrow transfer path. The job cannot enumerate or access sibling workspaces, user homes/profiles, OS/service state, secrets/credential stores, other Runner state, runtime sockets, host mounts, or policy/receipt/control files. Reject symlink/reparse traversal, hard-link crossings, mount/volume substitution, path aliasing/case/Unicode collisions, traversal, TOCTOU/open-handle races, unexpected device/filesystem, and writable policy/config paths. The verifier checks effective OS permissions and mounts, not an application path allowlist alone.

### 5.2 Process and identity boundary

A dedicated least-privilege Runner/job identity is distinct from the interactive user, Control Plane, host service administration, and other Runner instances. Only explicitly required descriptors/IPC are passed. The job cannot inspect host/other-job process tables, attach/debug/signal unrelated processes, acquire privileged tokens/capabilities, inherit an interactive session/handle, escape its process group/tree, or change its confinement. Process containment is combined with filesystem and network enforcement; process-tree cleanup alone is not a sandbox. Limits cover CPU, memory, process count, disk, output, and wall-clock time. Exact numerical limits and production workload sizing remain **【要決定】** under the Q7/limits track; no value is invented here.

### 5.3 Network boundary

Default deny at the host/deployment enforcement layer as well as the guest/process layer. This package authorizes **no** destination, including Control Plane. Explicitly test no external egress, no other LAN/intranet/metadata endpoint, no DNS, proxy, inherited route, UDP/QUIC, IPv4/IPv6, link-local, loopback-to-host, Unix-domain socket or named-pipe escape, and no host/guest bridge. A future exact authenticated Control-Plane transport would require its own approval and narrowly scoped policy; it is not permitted by this design. Positive controls use only an offline, disposable local test sink/capture inside the verification harness to prove that instrumentation detects an attempted connection; the sink is not a product-allowed destination and must never forward traffic. Verify denial independently from inside the boundary and with host firewall/vSwitch telemetry. If a future profile has a specifically approved internal endpoint, the allow case is separately specified, audited, and tested; all other destinations must still fail.

### 5.4 Cleanup, failure and state transition

A future supervisor must establish and verify isolation **before** launching any job process. Startup, policy/image verification, identity, networking, authorization, or resource-control uncertainty means zero job code starts. On completion, timeout, cancellation, supervisor/runtime failure, host restart, or uncertain process settlement, terminate/fence the job and all descendants; destroy or quarantine job state and reconcile mounts, namespaces, volumes, temporary files, and network attachments before another job can be admitted. Do not release outputs or reuse a workspace while cleanup is uncertain. Failure to verify cleanup quarantines the Runner/profile instance and keeps B6 denial; no retry through a weaker profile. Idempotent cleanup and durable quarantine are requirements to verify, not established implementation behavior.

## 7. Evidence package and profile-specific claim rules

For each profile, the future evidence packet binds at minimum:

1. Profile ID and exact OS edition/distribution, build/kernel, architecture, patch state, security features and system policy; host/hypervisor/runtime versions and config where applicable.
2. Runner and adapter binary identities; guest/base image provenance and immutable digest; supervisor/verifier version; relevant policy, mount, namespace, token/capability, firewall and resource configuration digests. No secrets or workload contents.
3. Positive/negative test inventory, harness and fixture identities, timestamps, raw non-sensitive outcomes, pass/fail/blocked/skipped distinction, host-side telemetry, cleanup/restart results, and hashes tying results to the exact configuration and artifacts. **A skip is never a pass.**
4. Independent security review identifying severity, evidence and residual assumptions; independently reproduced results on the claimed target where practicable. The verifier must be distinct from the implementation/configuration author. Verifier identity/qualification and evidence freshness/expiry rules remain **【要決定】**; no exact independent reviewer has been assigned in this document.
5. Explicit change invalidation: OS/kernel/security-feature, hypervisor/runtime, image, Runner/adapter, policy, mounts, identity, firewall, supervisor, or test-harness changes that can affect a boundary make the old evidence stale and profile inactive until the affected proof/review is repeated.
6. Written limitations and positive evidence for each enforcement point. No inference from a generic VM/container label, a different OS build, another deployment class, CI isolation, skipped live tests, static review alone, or passing unit tests.

**Permitted future claim form:** “Profile `<ID>` was independently evaluated on `<exact host/guest/runtime/build>` with `<artifact/config/test digests>` on `<date>`; the listed tests passed; these specific residual TCB assumptions and exclusions remain; this evidence does/does not satisfy the separately approved activation gate.” Do not use “secure sandbox”, “escape-proof”, “universal Windows/Linux support”, “isolated” without a profile-scoped qualification, or “activated” unless separately authorized and all current gates are verified. This document makes none of those claims.

## 8. Owner choices and activation gates

Explicit unresolved owner-controlled decisions remain **【要決定】**:

- Concrete isolation technology and supported Windows/Linux versions/configurations per local/server profile; whether VM, microVM, process restrictions or container layers are acceptable for each risk class.
- Threat-tier-to-profile mapping and acceptance of residual shared-kernel, host, hypervisor, runtime, broker, image/build, and local-administrator risk, especially risk acceptance for any unverified or non-VM profile.
- Runner trust root; enrollment and administrator authority; per-instance identity/key custody, OS-keystore/non-exportability/attestation requirements, rotation, revocation, recovery and compromise response.
- Any Runner network reachability, including a Control-Plane endpoint; all egress remains disallowed absent separate authorization.
- Provider credential supply/authentication and any broker; the CLI's official login terms and behavior must be verified per adapter/profile, but no credential use is approved here.
- Independent-verifier qualification/appointment and evidence freshness/expiry policy; separate owner activation decision for each profile and any risk acceptance. A passing evaluation alone does not activate a profile.

Profile activation is a future, independent decision and cannot follow solely from authoring or reviewing this package. Before any activation, the exact profile/build/config evidence must pass, an independent security review must be accepted, all applicable ADR-0012 gates must be satisfied (including B1–B7, E1/E2 receipt/identity/current-authority checks, E4 isolation, E5 egress, classification/artifact checks, audit protection and credential access-denial proof where applicable), and the owner must record a separate activation decision. Until every condition is demonstrably current, execution is unavailable and B6 stays in force.

## 9. Adversarial self-review and source tensions

- **VM-first overreach:** step-3 proposes VM-first candidates in places; this package compares them with OS-restricted/non-VM options and does not promote that proposal into a universal mandate. A specific approach remains unselected and residual-risk approval stays **【要決定】**.
- **Container proof inflation:** step-3 describes development-loop Docker QA and opt-in live tests as narrow QA precedents; ADR-0006 also says its Windows native sandbox diagnostic was incomplete. This package explicitly rejects both as product Runner proof and requires exact-profile host-side evidence.
- **No-VM downgrade path:** a non-VM candidate is not a fallback. It is inactive until separately selected, independently demonstrated to enforce every required boundary on the exact target, residual risk accepted by the authorized decision-maker, and activation gates passed. VM failure, feature absence, or test failure never routes to host-direct execution.
- **Network wording:** even internal Runner↔Control-Plane traffic is not authorized by this design. The step-2/step-3 distinction between internal control traffic and external provider egress does not create an exception to this task's no-egress boundary; endpoint and topology remain separately gated.
- **Approval/identity conflation:** receipt validity and Runner enrollment are independent conditions. The step-2 receipt contract is design input only; it is not approved by this package. No identity key, trust root or credential is created/provisioned.
- **Evidence overclaim:** exact-build independent evidence, test execution and reviewer acceptance do not exist yet. All profiles are explicitly inactive; no host execution was performed for this documentation deliverable.
- **Review limitation:** adversarial self-review is recorded here. The task forbids spawning subagents; therefore no independent reviewer was invoked from this task. Required independent security review remains a pre-activation gate, not a claimed pass.

Source status note: ADR-0012 is ACCEPTED and binds the dual-plane invariants; ADR-0013 remains DRAFT and its receipt/trust choices are not resolved here. Repository code/tests and development-loop QA provide context only and cannot establish any future product profile's live OS boundary. No code/spec/test/owner queue edits are part of this package.
