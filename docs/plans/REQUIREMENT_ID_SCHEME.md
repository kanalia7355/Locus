# Locus stable requirement-ID scheme

Status: AUD-1 proposed catalog, grounded in repository sources at `loop/local-development` HEAD `27c5a1d` (2026-11-09). IDs in this catalog are stable identifiers, not new approvals. AUD-2 should extend these IDs rather than renumber/reuse them; add IDs only for a requirement actually stated by an authoritative source and record provenance. A later owner decision may close, supersede or explicitly scope an ID, but must not erase its history.

## Reading the catalog

- **Approval status** describes the cited source's authority, not implementation or approval of this catalog. `approved baseline` means the source is an authorized product/governance requirement; `proposed` means proposal/design only; `owner-approved ...` is limited to the scope stated; `owner decision recorded` refers to a specific documented decision. An approved prototype exception never silently deletes the final-design requirement.
- **Priority**: P0 = confidentiality/safety/final acceptance blocker; P1 = core product capability or required system acceptance; P2 = important experience/extension; P3 = conditional or optional capability explicitly stated. Priority does not alter source approval.
- `Prototype-deferred` is not `out of scope`. The product spec's first-prototype exclusions only apply to the first prototype; final scope follows the original approved design and later explicit decisions.
- This catalog includes requirements from both the research product and the autonomous development controller, because both are documented original Goals in this repository. It does not treat evidence reports, aspirations, proposals or sample UI content as requirements.

## H. Proposals excluded from stable requirement catalog

These are not catalog requirements unless the owner adopts them: any unapproved option/recommendation in `PHASE2_DELEGATION_SPEC.md` §8; any unapproved choice in `HYBRID_STEP2_AGENT_REGISTRY_DESIGN.md` §6; proposed product technologies, measured capacity targets, TTLs, retention periods, deployment OS/runner trust roots, provider subscription interpretations, egress activation, cloud routing, production DB, authentication lifecycle changes and main-delivery replacements in proposal documents.
