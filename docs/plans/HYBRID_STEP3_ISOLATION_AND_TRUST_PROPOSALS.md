## 1. Evidence and design constraints

### 1.1 What existing development-loop precedents establish

- **Windows process-tree containment, not a sandbox.** `loop_engine/process.py` creates a Windows Job Object with kill-on-close, optionally limits active processes, starts children suspended, assigns them before resuming, and can require a bounded process-settlement check. This is useful lifecycle/resource containment for a supervised process. It does **not** confine filesystem access, network access, credentials, devices, or the process's OS principal; it is not sufficient by itself for T-E3/T-E4.
- **Windows local peer identification, not Runner enrollment.** `loop_engine/windows_tcp_peer.py` checks loopback TCP ownership against the kernel-reported PID and SID, and `OwnedCliPeer` additionally checks the expected executable and its active Job Object lifetime. `loop_engine/windows_pipe.py` demonstrates local named-pipe SID/DACL checks and bounded messages. These are narrow local IPC/peer-identity precedents. They do not establish a product Runner trust root, enrollment ceremony, hardware-backed identity, remote mutual authentication, workspace isolation, or resistance to a compromised process running as the same principal.
- **Linux/Docker QA containment, not product Runner isolation.** `loop_engine/docker_boundary.py` builds/checks an immutable QA image, stages a bounded Git-visible source set, mounts source read-only, runs with `--network none`, a read-only container root, dropped capabilities, `no-new-privileges`, resource limits and private tmpfs, and reconciles owned containers. `loop_engine/container_runtime/supervisor.py` stages the source into private work storage, drops to UID/GID 1000 before the test command, and terminates the container on lease/deadline loss. These controls are scoped to source-only QA and depend on a trusted Docker daemon/host and kernel; they are not evidence that an arbitrary product job, deployment, or hostile container workload is safe.
- **The live Docker tests are opt-in.** `tests/integration/test_live_docker_boundary.py` skips unless `LOCUS_LIVE_DOCKER=1`; it checks selected network, mount, read-only and process-tree behaviors when actually run. A skip is not a pass, and these tests do not establish cross-deployment or container-escape resistance.
- **A prior Windows sandbox probe was incomplete.** `docs/architecture/ADR-0006-source-only-runtime.md` records that the native Windows sandbox diagnostic allowed loopback and a policy-path write and explicitly says it is not production proof. `loop_engine/codex_runner.py` defaults to `UnprovenBoundary`, which rejects execution and host fallback. These are reasons to keep an explicit fail-closed gate, not evidence that a product sandbox is available.

### 1.2 Non-negotiable boundaries

1. Isolation must enforce process lifetime, filesystem scope, network scope, and separation from interactive user credentials. A policy check or CLI flag alone is not OS enforcement (T-E3/T-E4).
2. Runner-to-Control-Plane connectivity is not permission for arbitrary intranet access or external egress. Exact reachability and deployment topology remain **【要決定】**; owner has not approved LAN-external Runner reachability. Default deny applies.
3. Never mount the user's profile, credential directories, Docker/container control socket, host process interfaces, or unrestricted host paths into an execution guest. A credential-broker design, if any, is separate and needs its own approval and positive/negative access proof. If an official CLI cannot authenticate without exposing exportable credentials to the tool-executing process, that platform/adapter remains unavailable (see `docs/plans/HYBRID_STEP2_AGENT_REGISTRY_DESIGN.md`, §2.4).
4. If the selected platform cannot prove every required boundary, execution fails closed; there is no host fallback. B6 in the step-2 design and `loop_engine/codex_runner.py`'s `UnprovenBoundary` pattern remain in force.

## 2. Platform isolation comparison and proposal

### 2.1 Windows options

| Option | What it can provide | Important limits / evidence still required |
|---|---|---|
| Job Objects + dedicated low-privilege process identity, restrictive ACLs, and narrowly granted IPC | Process-tree lifetime/termination and resource controls (the existing `loop_engine/process.py` precedent); OS account separation can reduce access to user-profile data. | A Job Object is not a filesystem, network, credential, or kernel boundary. ACLs alone are hard to make complete over a changing host and do not prevent all same-user access. Must prove token rights, inherited handles, reparse points, child-process containment, and explicit network filtering. Not adequate as the sole T-E3/T-E4 boundary. |
| AppContainer / restricted token with explicit capabilities, plus Job Object | Smaller process authority and OS-enforced resource/capability restrictions; may be suitable for a tightly controlled native workload. | CLI/runtime compatibility and complete filesystem/network capability behavior are **【要決定】** and must be demonstrated for the pinned adapter and child processes. Does not provide a separate kernel. A permissive fallback or capability not understood by the verifier is a hard failure. |
| Windows Sandbox / Hyper-V-backed disposable VM, with no host folders, clipboard, devices, or user profile shared; narrow brokered input/output | VM boundary between hostile execution and host kernel/processes; disposable guest can bound residual state. Fits the T-E4 concern better than same-host process restrictions. | Windows edition/features, headless orchestration, network policy, image integrity, shutdown/cleanup, and controlled artifact transfer are **【要決定】**. Any host mapping/integration feature can reopen access. It does not itself solve provider credential use or prove guest escape resistance. |
| Windows containers | Process isolation and resource controls may be useful for compatible workloads. | A process-isolated container shares the Windows kernel; isolation mode, host version, runtime and filesystem/network behavior must be established. Do not infer VM-strength containment from the word “container.” **【要決定】** whether it is supported or acceptable for the threat level. |

**Proposed Windows direction:** use an ephemeral Hyper-V-isolated guest as the primary boundary for untrusted Runner jobs, where a supported configuration and exact guest lifecycle can be verified. Inside the guest, use a dedicated non-admin execution identity and Job Objects for child-process containment/cleanup; the Job Object is defense in depth, not the isolation claim. Transfer only a bounded, integrity-checked input bundle and output bundle through a small trusted broker; no shared host profile or general host folder. If a VM boundary is unavailable or any required VM/network/credential control cannot be proven, keep execution unavailable rather than substituting Job Objects/AppContainer alone. Whether this VM option is deployable for Desktop and Server Runner targets, and whether the owner accepts it, is **【要決定】**.

### 2.2 Linux options

| Option | What it can provide | Important limits / evidence still required |
|---|---|---|
| Namespaces and cgroups without a container manager | PID, mount, network, user and other namespaces plus resource limits can separate process views when configured correctly. | Correct namespace composition, UID/GID mapping, mounts, capabilities, seccomp and cleanup must be built and maintained. Namespaces are not a separate kernel; a missing namespace or inherited descriptor can defeat the intended boundary. No such product Runner configuration is established by this repository. |
| Rootless OCI container (e.g. a pinned runtime) with user/PID/mount/network namespaces, seccomp, LSM policy, cgroups, read-only root and explicit mounts | Reproducible packaging plus defense-in-depth OS restrictions; `loop_engine/docker_boundary.py` provides a narrower source-only QA example of read-only mounts, no network, dropped capabilities and resource bounds. | Shares the host kernel; container runtime/daemon and kernel remain trusted. Rootless behavior, user namespace mapping, seccomp/LSM availability and host-specific configuration vary. No Docker socket, privileged mode, host PID/network, devices, or broad bind mounts. Existing QA tests do not prove product workloads or container-escape resistance. |
| Disposable hardware-virtualized VM / microVM, optionally running a rootless container inside | Separate guest kernel boundary with container controls as defense in depth; disposable state and narrow brokered exchange can contain a compromised job better than namespaces alone. | Hardware virtualization and host support, guest image supply chain, VM lifecycle/cleanup, network enforcement and broker correctness are **【要決定】**. A VM reduces shared-kernel exposure but is not proof against hypervisor/configuration flaws. |

**Proposed Linux direction:** use a disposable hardware-virtualized VM or microVM as the primary boundary for untrusted execution, with a rootless OCI container and namespaces/seccomp/LSM/cgroups inside the guest as additional layers if their availability is verified. Never treat the namespace/container configuration alone as equivalent to a separate kernel. If virtualization is unavailable, keep execution unavailable pending an explicit owner decision accepting a tested namespace/container risk profile; do not silently downgrade to host execution. The supported VM technology, hypervisor, Linux distribution/kernel, LSM/seccomp profile, and fallback policy are **【要決定】**.

### 2.3 Verification plan for the isolation claim

Tests must run only in an isolated disposable verification environment with synthetic data. They prove behavior only for the exact identified host, OS/kernel/hypervisor/runtime, guest image, configuration and Runner build; evidence must bind to those versions and expire or become stale after a change. A successful unit test or a CI skip is not live proof.

1. **Configuration and provenance inventory:** verify the host/guest OS build, hypervisor and runtime versions, signed/pinned guest image digest, effective policy, mounts, capabilities, namespaces, firewall rules, service principal, and executable identity. Reject unknown configuration, privileged mode, unexpected mounts/devices, host PID/network, writable root, or any container/VM control socket in the guest.
2. **Filesystem confinement:** from hostile synthetic test processes attempt reads and writes to sibling workspaces, parent directories, user profiles, credentials, OS/service state, host temporary areas, and broker/control files. Cover traversal, symlinks/reparse points, hard links, case/Unicode path collisions, mount replacement, open-handle races and child processes. Only the job's designated guest workspace may be mutable; host inputs remain immutable and no unauthorized host path is observable.
3. **Network confinement:** test DNS, IPv4/IPv6, loopback, link-local/metadata ranges, private/intranet ranges, arbitrary ports, proxies and inherited environment routes. Capture at the host/vSwitch/firewall as well as from inside the guest. All unapproved destinations must be unreachable; if a future authenticated Control-Plane channel is approved, only its exact endpoint and protocol may pass. No test should contact an external service. The exact allowed endpoint/topology is **【要決定】**.
4. **Identity and credential separation:** verify the tool process runs as the expected dedicated guest identity, not the interactive user; test denial of host user profiles, OS credential stores, service secrets, host process inspection, memory/dump access, and other Runner instances. Verify that only an explicitly approved broker operation is possible, and that no raw secret enters process arguments, environment, files, logs, model input, or returned diagnostics. Until such a broker passes both intended-access and forbidden-access tests, do not enable provider authentication.
5. **Process lifecycle and resources:** launch synthetic fork/child/grandchild workloads (including detached/session-escaping children), then exercise normal completion, timeout, cancellation, supervisor crash, guest shutdown and host restart. Prove no descendant survives the job, no job can reuse stale state, and uncertain settlement blocks subsequent work. Verify memory/CPU/process/disk/output/deadline caps cannot be exceeded or changed by the workload.
6. **Boundary fault injection:** fail VM startup, image verification, policy fetch, network setup, broker connection, teardown and state reconciliation. Assert zero execution on startup uncertainty, no host fallback, no reuse of stale/unknown job state, and deny-before-side-effect on revocation or policy mismatch.
7. **Escape and independent review:** run a bounded, independently designed adversarial suite against a disposable host and review effective OS policy and host-level telemetry. Document remaining shared-kernel/hypervisor/runtime assumptions. Require fresh independent security review of the exact configuration and test evidence before any separately authorized activation.

Acceptance for a future isolation implementation must include positive control cases showing the test harness works and negative cases above showing denial. Exact test inventory, target OS matrix, success thresholds, evidence validity window and independent-verifier identity are **【要決定】**. No acceptance or activation is claimed here.

## 3. Runner trust root, enrollment, rotation and revocation

### 3.1 Options

| Trust option | Advantages | Risks / limits |
|---|---|---|
| Shared static bearer secret or shared MAC key | Simple provisioning and message authentication. | Every verifier holding the shared key may mint; copying/rotation affects all Runners; weak per-instance accountability and revocation. Not recommended for T-S1 or job authorization. |
| Trust-on-first-use / self-signed key pin | Avoids a central PKI dependency for a small installation. | First contact is vulnerable to substitution unless an independent approval channel authenticates the fingerprint. Rotation and recovery are manual and easy to confuse. No enrollment identity by itself. |
| Installation-specific CA-issued asymmetric identity per Runner, mutually authenticated transport, plus independent job-authorization signatures | Supports unique revocable instance identities, server/client authentication and key separation; job signatures can be checked after transport without giving a Runner a minting key. | Requires a protected CA/signing-key lifecycle, authenticated enrollment, revocation distribution, OS principal/code identity binding, and careful rotation/recovery. Certificates alone do not attest trusted software or a safe host. |
| Enterprise PKI/device management | May reuse mature organizational identity, hardware-backed enrollment, policy and revocation operations. | Availability and integration are deployment-specific; PKI issuance alone does not bind the Locus `runner_instance_id`, workspace policy, pinned Runner binary or job approval. **【要決定】** whether an enterprise PKI exists or is in scope. |

### 3.2 Recommended design proposal

**Candidate:** a unique asymmetric key and certificate for each immutable `runner_instance_id`, issued under an installation-specific trust anchor, used for mutually authenticated Runner↔Control-Plane transport. Separately, the Control Plane signs each narrowly scoped job envelope with a job-authorization signing key; the Runner has only public verification material and can never mint or expand authorization. Runner-signed result/artifact manifests may establish origin/integrity, but never establish authorization, classification, ACL or artifact safety.

- **Trust anchor and key custody.** Keep an offline installation root public trust anchor on the Runner; protect its private key offline. Delegate online issuance/signing to separately scoped subordinate keys held in an approved OS keystore or HSM/KMS, with least privilege and audit. Root/subordinate layout, algorithms, key lengths, hardware requirements, custody service and compromise quorum are **【要決定】**. If the deployment cannot keep issuer keys separate from tool-executing processes, no Runner identity or authorization is activated.
- **Instance identity.** Generate the per-instance private key on the Runner host where practical and mark it non-exportable in an OS/hardware-backed keystore; return only a CSR/public key. Bind the issued identity to a unique `runner_instance_id`, installation/audience, OS principal reference, pinned Runner binary identity/version, and platform. A certificate does not prove those local properties: a trusted local service must enforce dedicated OS identity, protected binary/configuration and narrowly scoped IPC, then the Control Plane must verify the enrolled binding. TPM/device attestation is optional only if separately supported and verified; it is not assumed. Non-exportability, attestation and the required Windows/Linux keystore are **【要決定】**.
- **Enrollment.** Create a pending instance; generate a short-lived, one-use enrollment challenge bound to installation, proposed instance ID and public key. An authenticated authorized administrator approves the exact fingerprint and platform through a trusted Control-Plane session and a separate local confirmation channel. On acceptance, issue the certificate and record immutable enrollment evidence, approved binary digest and OS-principal binding. Reject expired/replayed challenges, duplicate IDs/keys, weak algorithms, unknown binaries, mismatched principal evidence and any approval not bound to the same key. Do not enroll based only on a Runner's self-asserted identity, network address, PID, or SID; the existing Windows peer code is local groundwork only. Who may enroll/revoke and what local confirmation is usable for Desktop Runner are **【要決定】**.
- **Transport and authorization separation.** Require server identity validation and mTLS client identity for every connection; do not accept unauthenticated or alternate transport paths. Transport authentication is not a job approval. The Runner accepts only Control-Plane-signed envelopes that target its exact instance and still pass an online authoritative receipt/policy/revocation check immediately before execution. If the Control Plane or current revocation state is unavailable, fail closed. This preserves the approval-then-activation distinction in `docs/plans/HYBRID_STEP2_AGENT_REGISTRY_DESIGN.md`, §§2.2/2.6 and 3.3.
- **Rotation.** Rotate Runner keys/certificates per instance with explicit key IDs and bounded overlap: register and validate the new key, prove possession, switch issuance, then revoke the old key. Never reuse an instance ID/key to conceal a reinstall or compromised device; re-enrollment creates an auditable instance identity. Root rotation needs a separately signed transition trusted by the previous root and an independent recovery route. Rotation interval, overlap length, re-enrollment rules and recovery authority are **【要決定】**.
- **Revocation.** Maintain authoritative online active/revoked status by instance and key ID; check it at connection, job preflight, immediately before execution, and before accepting/releasing results. Increment a revocation/policy epoch or equivalent version so stale state is detectable. Revocation immediately denies new jobs and invalidates unconsumed envelopes; queued work is canceled, and uncertain active work is terminated or held before output release. No offline grace period for job execution. Certificate-status transport/cache limits, active-job termination semantics, audit retention and root-compromise recovery remain **【要決定】**.
- **Credential separation.** Runner identity keys are not provider login credentials, Locus user sessions, GitHub/App keys, or approval-receipt keys. Never put provider secrets in the transport certificate, job envelope, registry or Runner identity key. ADR-0009's `locus_loop_audit` account/keyless audit-worker proposal and ADR-0010's encrypted audit-only authentication cache concern a dedicated audit worker, not general product Runner enrollment, key rotation/revocation, user credential brokerage or product trust roots (`docs/architecture/ADR-0009-keyless-audit-worker-proposal.md`; `docs/architecture/ADR-0010-encrypted-audit-auth-proposal.md`). Their OS identity/key-separation lessons are narrow precedents only, as T-S1/T-I3 state.

### 3.3 Trust-root verification/test plan

Use synthetic test identities and an isolated test CA only. Do not create or provision production credentials.

1. Enrollment: approve one exact pending challenge; reject unknown/unapproved identity, altered key/fingerprint, wrong installation, wrong platform/binary digest, expired/replayed challenge, duplicate instance/key, weak/unknown algorithm and self-signed/foreign-CA clients. Verify the local OS principal and protected binary/config binding separately from TLS certificate validation.
2. Authentication: prove the enrolled key can establish mTLS to the intended test endpoint; prove untrusted CA, wrong server name, missing client certificate, another Runner's certificate, revoked certificate and expired certificate all fail before job data is accepted. Confirm network listener exposure is restricted to the approved topology (topology remains **【要決定】**).
3. Key custody: verify private key generation, access-control owner/ACL, non-exportability where claimed, and denial to interactive users, other instances, Control Plane job-execution code, and the tool process. Test backup/restore and restart semantics without reading key bytes. If OS/hardware facilities cannot satisfy the claim, block enrollment for that platform.
4. Rotation/revocation: prove old/new overlap only in the authorized window, possession of the new key before cutover, old-key rejection after revoke, instance-specific emergency revocation, stale certificate-status/policy-epoch rejection, and behavior under CA/key compromise and attempted rollback. Missing authority/state always denies.
5. Separation: verify a Runner key cannot sign a valid Control-Plane job, alter policy, approve itself, impersonate another instance, or turn an artifact signature into an authorization receipt. Verify provider credentials never enter identity or signing-key stores.
6. Audit/failure paths: test interrupted enrollment, uncertain key creation, issuer outage, stale clock, partial rotation and revoke races. Preserve an auditable held state; never auto-regenerate, retry enrollment as another identity, or silently fall back to unauthenticated transport. Exact clocks, revocation propagation SLA and retention are **【要決定】**.

## 4. Job identity, freshness and signing contract (T-T1)

### 4.1 Contract options

1. **Shared-key MAC on job JSON:** compact, but any Runner able to verify can generally mint or forge jobs for other holders of that key; poor key separation and instance revocation. Reject for authorization envelopes.
2. **Control-Plane asymmetric signature over a strict canonical envelope:** verifiable by each Runner using pinned public verification keys; the signing key is not present on a Runner. Good integrity/provenance and transport-independent verification, but alone does not prove freshness, current policy, unrevoked approval or one-time use.
3. **Online opaque job ID with every field fetched from the Control Plane:** current state can be authoritative and revocation immediate, but requires availability, authenticated binding and careful response consistency; a guessed/replayed ID or stale cache must still fail closed.
4. **Recommended combination:** strict Control-Plane signature plus online, instance-authenticated freshness/receipt/policy/revocation checks immediately before execution. Signatures prove who issued the exact envelope; online state and replay protection prove it remains usable now. No offline execution if freshness cannot be established.

### 4.2 Proposed envelope and validation rules

The following is a proposed minimum claim set, not an activated protocol. Exact encoding, algorithm, key rotation, expiry, clock-skew allowance and schema version are **【要決定】**.

| Claim | Required binding / purpose |
|---|---|
| `contract_version`, `issuer`, `key_id`, `audience` | Closed versioned schema; identifies the Control-Plane signer and the exact Runner service/installation that may consume the envelope. |
| `job_id`, unique `nonce` (and optionally per-instance sequence) | Globally unique job and one-use replay identity. Persist consumption before execution; reject duplicate use across restart, retry or another Runner. |
| `issued_at`, `not_before` if used, `expires_at` | Bounded lifetime. Validate with a trusted time source and explicit skew rule. These values and the allowed skew are **【要決定】**. A valid signature is not proof of freshness. |
| `runner_instance_id` | Exact enrolled recipient; never a runner type or adapter ID alone. |
| `actor_id`, `workspace_id`, `policy_id`, immutable `policy_version` and digest | Actor/workspace attribution and exact policy snapshot; reject stale, missing or changed policy. |
| `adapter_id`, pinned binary/version/catalog digest | Exact enrolled adapter and code identity; do not allow the Runner to substitute a binary or capability. |
| `operation`, exact destination/egress decision, resource limits | Narrow authorized operation and destination. No wildcard or Runner-selected destination. Egress remains default-deny and non-activated. |
| `authorization_receipt_id` and current authorization/revocation epoch | Reference to authoritative job-level approval; receipt source is not the envelope issuer's assertion alone. Re-check issuer/current decision, expiry, revocation and all bindings online. |
| input/artifact manifest digest, size and classification/provenance references | Bind exact input bytes and source identities/versions; absent or mismatched integrity/provenance denies. No payload accepted merely because its digest is signed. |

Encode using one deterministic, reviewed serialization and sign a domain-separated byte representation. Reject duplicate keys, unknown fields, alternate encodings, invalid types, noncanonical values, oversized envelopes and unsupported versions. Verify signature before trusting claims, then validate the full schema and every binding. The serialization (e.g. canonical JSON versus deterministic CBOR), signature algorithm, digest algorithm and key identifiers are **【要決定】**; no implementation should guess them.

Before queue admission and again immediately before any side effect, the Control Plane and Runner must verify: signature and issuer; exact recipient instance/audience; job/nonce unused and within its time window; current enrollment/key not revoked; exact adapter/binary; current workspace policy version and digest; current authoritative approval receipt and every bound actor/workspace/adapter/destination/operation field; input digest/provenance; resource limits; and current revocation epoch. If any authority is unreachable, changed, expired, revoked or ambiguous, deny and record a non-sensitive reason. A signature does not replace online revocation or protect against a compromised trusted signer.

A Runner-signed completion/artifact manifest should bind the job ID, instance ID, workspace, exact policy version, input/source digests, output digest, result status and signer key ID. The Control Plane verifies that signature and revalidates live authorization, ACL/classification and source state before persistence, reuse, export or release. This proves origin/integrity only: it does not certify that tool output is safe or authorized. Retention and artifact deletion semantics remain as in step-2 design and **【要決定】**.

### 4.3 T-T1 tamper, freshness, replay and race tests

- Mutate each signed field individually, signature bytes, key ID, audience, schema version, canonical encoding, duplicate field and input digest; every alteration/unknown field must reject before reading payload or executing.
- Test valid, expired, not-yet-valid, excessive-skew, stale-policy and wrong-runner envelopes; test clock rollback, restart and unavailable time/revocation authority. Any uncertain freshness fails closed.
- Replay identical envelope/nonce before and after restart, across duplicate delivery, another instance, concurrent requests, timeout, partial response and cancellation. At most one execution may begin; retries must be idempotent and cannot reauthorize stale work.
- Race revocation, policy change, receipt expiry/denial, key rotation and Runner disablement against enqueue, queue wait, the final pre-execution check, active execution and output release. Assert no side effect after the denial boundary; cancel/terminate or hold work and deny output as appropriate.
- Test a malicious Runner cannot edit identity/policy/limits/destination or mint the CP signature; a compromised/retired instance's signatures and credentials fail after revocation. Test the CP cannot silently accept a receipt asserted solely by a client or Runner.
- Mutate output manifests and source ACL/classification/provenance, delete/revoke a source, change workspace policy or cross workspace; reject before artifact persistence/use/export/read. Confirm valid signatures never bypass live authorization.
- Verify tests use only fake keys, synthetic payloads and a local isolated test authority; test reports record exact code/config identities, not secrets or payloads.

Signature algorithms/encoding, time authority/skew, expiry maximum, nonce retention, sequence semantics, receipt authority API, revocation SLA, cancellation guarantees, artifact-signing key custody and audit retention are all **【要決定】**. None is inferred from the existing Loop audit worker or development QA implementation.

## 5. Decisions required before implementation or activation

1. **【要決定】 Isolation technology and supported platform matrix:** accept/reject the VM-first Windows and Linux candidates; specify supported Windows editions, Linux distributions/kernels, hypervisor/runtime, required capabilities and any no-VM fail-closed rule.
2. **【要決定】 Runner deployment/topology:** Server versus Desktop ownership, permitted Control-Plane endpoint/reachability, firewall policy, and whether an endpoint can be local-only. LAN-external Runner access remains unapproved.
3. **【要決定】 Host/guest data exchange and provider authentication:** exact broker interface, mount/copy policy, credential availability, user consent and proof that tool processes cannot export provider credentials. No host-profile mapping or implicit credential reuse.
4. **【要決定】 Trust anchor and enrollment authority:** offline root/subordinate key custody, admin roles, local confirmation, hardware/OS keystore and attestation requirements, cryptographic algorithms, re-enrollment and compromise recovery.
5. **【要決定】 Rotation/revocation lifecycle:** key/certificate lifetime, overlap, revocation propagation, active-job cancellation and audit retention.
6. **【要決定】 Job protocol details:** canonical encoding, signature/digest algorithms, identity claims, expiry/skew, nonce persistence/retention, authoritative receipt check, response/artifact signing and protocol-version migration.
7. **【要決定】 Verification gates:** platform test matrix, adversarial test scope, independent verifier, evidence binding/freshness and activation authority. Tests and evidence are prerequisites, not automatic permission.

Until these decisions are recorded and implementation independently reviewed and verified, preserve B6's explicit rejection of every Runner execution attempt. No code or runtime activation follows from this proposal.
