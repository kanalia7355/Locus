## 3. 要求アーキテクチャ（仕様§4）vs 実装

| 構成要素 | 案 | 実装 | 差異と理由 |
|---|---|---|---|
| Skill Registry | ID・出典・固定コミット・ライセンス・用途・信頼レベル・必要権限・依存・有効状態を記録 | `SKILLS_REGISTRY.md`（12エントリ、全項目記録 + MIT全文掲載）を **文書メタデータとして** 実装 | **一致（形態は文書）**。理由: P0はdocs-only。registryが「有効」を権限付与と誤読されないよう、意味論を明示的に定義（`enabled: yes` = Markdown存在のみ、監査プロファイルのskills除外は不変） |
| Skill Loader | 許可済みのみ読み込み。本文は信頼された命令ではなく外部由来データとして検査 | **コード実装なし**。既存エージェント環境のスキルMarkdown取り扱いにマッピング | **差異（意図的な縮小）**。理由: Locusに現状ランタイムローダが存在しない。新規に実装する場合は実行時機構の新設でありOwner判断が必要。監査ランタイム（`audit_profile.py`のskills除外）を変更しないことを優先。仕様§4の「本文を命令として扱わない」要件は3スキル全ての前書きと優先順位宣言で満たす |
| Policy Gate | 作業dir・実行コマンド・ネットワーク・認証情報・マージ・外部送信の既存権限判断を適用 | **新規ゲートなし**。既存の不変スナップショット/Controller QAゲート/ApprovalQueue/B6・ADRゲートにマッピング | **一致（方向）**。理由: 既存ゲートが既に強制しており、Skill層に重複ゲートを作ると競合Orchestrator化する。仕様§4自体が「新たな競合Orchestratorを作らない」を要求 |
| Loop Adapter | Skill手順を既存フローへ対応付け。新Orchestrator禁止 | 設計書にマッピング表（6概念 × 既存機構 × 境界）を文書化。コードなし | **一致**。理由: 対応付けは文書で十分。コード化は実行権限の付与に見えるリスク |
| Evidence Store | 使用Skill・バージョン・入力・テスト結果・失敗原因・承認記録を保存。秘密情報は記録しない | **新規ストアなし**。既存SQLite証跡（task/execution/verification/review/decision/checkpoint）+ git/CI証拠にマッピング。「Skillの自己申告は証拠ではない」を明記 | **差異（意図的な縮小）**。理由: Skill使用記録の新規テーブルは実行時機構。 false assurance（自己申告を証拠扱い）を防ぐため既存証跡のみを権威とする設計を選択。P1以降の課題として残る |
| Rollback | Skill無効化・バージョン固定・以前の動作への復帰 | 既存Controller checkpoint/recovery/reconciliation + ブランチ履歴にマッピング。Skillはreset/force-push/削除を不可能 | **一致**。理由: docs-only実装では「ファイルを消す」こと自体がロールバックであり、既存機構が復帰を保証 |

## 6. 実装が検出・申告した新規事項（案になかった発見）

1. **上流companionスクリプトのリスク**: `find-polluter.sh`（テスト実行）、`render-graphs.js`（Graphviz実行）、環境/シークレットのログ出力指示 — 全て排除。案§2は「実行スクリプト・テレメトリ・注入経路の確認」を要求しており、この深掘りは案の意図どおり実行された。
2. **legacyスキルとの競合【要決定】**: 既存 `.agents/skills/loop/SKILL.md`（Loop CLI実行指示）と `owner-decision-request/SKILL.md`（commit/push指示）が、グローバルな「スキルファイルにexec指示を含まない」基準と文字通り矛盾。新規3スキルのみを清浄化し、既存スキルは本タスクの範囲外として未変更 — **範囲拡大の判断をOwnerに委ねた**（勝手に既存手順を書き換えない正しい挙動）。
3. **監査プロファイルの保護**: `loop_engine/audit_profile.py` が `skills.bundled.enabled=false` を設定している事実を特定し、本導入がそれを変更しないことを明記。案§4「ゼロツール公開面との境界」の具体化。

## 8. 結論

- **方向性・安全設計は案に一致**。実装は案が想定した最小構成（§5.4の最初の3スキル）を正確に守り、それ以外を理由付きで保留/見送りにした。
- **3件の判定は案より厳格**（executing-plans、code-review系）— いずれも上流の特権的指示を根拠とする安全側の格下げであり、仕様の禁止・保留趣旨と矛盾しない。
- **残課題**: (a) QA実行+push+CI緑化（steer済み、進行中）、(b) legacyスキル競合のOwner判断【要決定】、(c) P1スキルとEvidence Storeの実行時機構（将来スライス）。
- 本比較はworktree状態に基づく。Slot Uのpush・CI完了後に本書の§4.4/§4.6を更新する。
