# Master implementation roadmap: original design to final completion

Baseline: `loop/local-development` HEAD `27c5a1d` (2026-11-09). This roadmap synthesizes the original research-product design, the user-provided autonomous Controller specification, later owner-approved scoped refinements, and verified implementation/review/CI evidence. It is not an implementation authorization. Stable IDs are in [`REQUIREMENT_ID_SCHEME.md`](REQUIREMENT_ID_SCHEME.md); current gaps and source survey are in [`DESIGN_GAP_ANALYSIS.md`](DESIGN_GAP_ANALYSIS.md).

## 1. Roadmap rules

1. **The original approved design is the completion authority.** Existing product phases `P0–P5`, product MVP slices `MVP-1–6`, autonomous-loop `L1–6`, and hybrid execution steps `H1–6` remain distinct aliases. A phase number in one family does not complete a different family. Product/development completion is the conjunction of all applicable requirements in the stable catalog and the accepted task/phase gates.
2. **Prototype scope is an implementation subset, not final closure.** Prototype-approved omissions (for example no real data, no production TLS, MFA prototype omission, production DB, audit retention, runner isolation) remain in the final backlog unless the owner explicitly rules a requirement out of final scope. “Deferred” is not “out of scope.”
3. **Evidence is conjunctive.** For each work package: source-grounded acceptance, implementation at exact SHA, mandatory local QA, independent review when required, exact-head required CI, correct integration, and owner decisions for any security/scope-dependent choice. Code/tests existing alone is insufficient. Unavailable/skipped checks are blocked/skipped, never passed. Mocks and synthetic tests prove only their stated boundaries.
4. **Approval is not activation.** ADR/plan approval does not authorize credentials, real data, external egress, live runner execution, service operation or main mutation unless the exact separate activation permission and technical gates are documented.
5. **Dependencies and parallelism.** Parallelize only independent, disjoint work with explicit base syncing and conflict ownership. Material security/data-model changes need one fresh read-only review; no routine implementation agents. Pipeline jobs currently assigned by the owner/orchestrator are exceptional task assignments, not general permission to spawn agents.
6. **Bounded repair.** Each task has maximum three implementation/verification attempts including CI repair and no more than two review fix/re-review cycles. Preserve prior attempts and unresolved operations. Stop on uncertainty; do not retry external side effects blindly.
7. **Delivery mode is unresolved at the full-design level.** The 2026-11-02 exact owner-approved policy migration enables `local_commit_push` to `loop/local-development`; it is not main integration. The autonomous specification and 2026-11-09 phase policy describe protected main merge/versioning, while PR-free production-main mode remains explicitly unapproved and current broker/base-binding guarantees are incomplete. Follow the active task authorization for branch CI; do not push to main or weaken protection. Before declaring product/system final complete, obtain/implement an owner-approved, secure main-integration path or resolve the contradiction explicitly.

## 5. Phase completion, versioning and integration rules

- **Work-package completion**: record requirement IDs, scope, actual changed paths, exact SHA, local commands/results, skipped tests, independent review outcome, all branch CI runs (including same-name siblings), owner approvals, integration SHA and known residual risks. Require every mandatory check green at the exact pushed head; a failed/pending/cancelled/skipped sibling blocks. No evidence is inferred from another SHA.
- **Phase completion**: close every relevant phase gap or explicitly defer it with a recorded owner decision while keeping it on the final roadmap; satisfy phase-specific acceptance; independent aggregate review for security/material changes; exact-head full required CI green; no unresolved critical/high finding. Owner policy dated 2026-11-07 requires completed phases to be reviewed, merged to main and version-bumped before advancing; this is subject to the main-delivery contradiction/finding until a valid authorized mechanism is selected.
- **Version bump**: for a phase whose owner-approved transition includes main integration, bump all existing version-bearing project artifacts consistently (currently `pyproject.toml`, `frontend/package.json`, `loop_engine/__init__.py`) using the repository's established versioning rule. Phase 1 evidence is 0.1.0→0.2.0. No arbitrary bump amount/semantic scheme beyond that evidence is inferred; owner/maintainer must specify release cadence/major-minor semantics if not already authorized. A local dev-branch Push alone is not a release or main-phase completion.
- **Integration**: use short-lived task branch/worktree, Conventional Commit, no force-push/rebase rewrite, no direct main push, no hook/CI/protection bypass. Follow exact task branch authorization. For phase-to-main delivery, wait for all checks and required independent review, confirm intended source/base and merge subject, then verify resulting main SHA and reconcile only by authorized non-destructive procedure. Current Main proposal is NOT approved; do not activate it. Stop and request owner decision if protected delivery is impossible under current approved settings.
- **Final acceptance/release**: audit all stable IDs (including deferred final requirements), cite source and final verification evidence for each, distinguish verified prototype from final deployment, resolve all owner-decision conflicts, obtain final independent review, run current full QA/CI, verify protected main/release version according to approved policy, and report any explicitly out-of-scope requirement with the exact owner decision. There is no implicit waiver by omission.
