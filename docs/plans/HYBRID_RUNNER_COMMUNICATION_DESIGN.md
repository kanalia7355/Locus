# Hybrid Runner communication design — authenticated LAN channel

**Status: design proposal under owner-approved Entry 3 only. No endpoint has been verified, independently reviewed, separately approved, configured, activated, or contacted. No firewall rule or port is changed/opened by this document.** This defines a candidate LAN-internal communication method and its proof/approval gates; it is not a deployment or dispatch authorization.

## 1. Authority, scope, and immutable boundaries

This design implements the direction in [Owner Decision Entry 3](OWNER_DECISIONS_2026-11-10-ENTRIES.md#entry-3--runner-communication-topology--選択肢aを承認する): an authenticated, authorized, encrypted LAN-internal Runner↔Control-Plane channel; explicit endpoint details and per-endpoint design → verification → independent review → separate Owner approval; deny non-approved destinations; no implicit internet, cloud, unapproved-LAN, or provider-API access; fail closed when the path is unverifiable. Entry 5 separately approves the *trust-design direction* (OS-keystore-protected per-instance identity, verified standard TLS, enrollment, revocation, and evidence); it does not activate a transport or choose its final cryptographic profile. [ADR-0011](../architecture/ADR-0011-model-facing-zero-tool-gate-proposal.md) and accepted [ADR-0012](../architecture/decisions/0012-dual-plane-model-gate-agent-runtime.md) remain binding. See also [HYBRID_ISOLATION_PROFILES.md](HYBRID_ISOLATION_PROFILES.md) and [HYBRID_STEP3_ISOLATION_AND_TRUST_PROPOSALS.md](HYBRID_STEP3_ISOLATION_AND_TRUST_PROPOSALS.md).

This document does not enable Runner registration, network communication, dispatch/enqueue, job execution, a profile, egress, provider access, or production operation. It does not change B6: the Control Plane explicitly rejects dispatch/enqueue while B6 is active, and the Runner denies execution with no host fallback. A future separately approved communication channel would not itself authorize dispatch or execution. Plane M remains zero-tool; Plane R remains separate and uses only a versioned transport contract. The authenticated transport, job approval receipt, current authorization, artifact/classification checks, and isolation are distinct gates—none substitutes for another.

The task uses **no-egress** in its security sense: the Runner job sandbox has no outbound route or destination, and the Runner host's proposed control channel is an inactive, separately gated *internal* exception. It is not an implicit allowance created by calling a destination “LAN.” Until an exact endpoint passes all gates and receives the required separate decisions, the effective policy is default-deny for all Runner-originated traffic. There is no firewall or port change in scope.

## 2. Topology and trust boundaries

```text
                       Design target only; not active
     designated private LAN (exact segment/addressing not yet approved)
  ┌──────────────────────┐  TCP destination 443 proposed, HTTPS/TLS ┌──────────────────────┐
  │ Control Plane        │◀──────────────────────────────────────▶│ Runner host service  │
  │ exact instance TBD   │    Runner initiates; request/response  │ exact instance TBD   │
  └──────────────────────┘    on that established connection      └──────────┬───────────┘
        No other CP/                                                    validated,
        admin endpoints                                                  bounded staging
                                                                        ┌─────▼────────┐
                                                                        │ isolated job  │
                                                                        │ sandbox       │
                                                                        │ network NONE  │
                                                                        └──────────────┘

     All other LAN hosts, other VLANs, internet, cloud, provider APIs,
     DNS/proxy/time/update/status services, peer Runners: DENY unless
     a separately designed, verified, reviewed, and Owner-approved endpoint.
```

The candidate is a **Runner-host service (Plane R transport client) to one exact Control-Plane listener** over a private LAN. The Runner initiates every connection. Application replies may travel only over the authenticated, already-established connection. There is no Control-Plane-initiated connection to the Runner, listening Runner port, callback, peer-to-peer Runner path, general-purpose tunnel, or forwarding proxy. HTTPS request/response is the proposed protocol; no UDP/QUIC, WebSocket, SSH, raw TCP protocol, or alternate transport is implied.

The Runner host transport process and the job sandbox are different security principals/boundaries. Only the host service may use a separately approved Control-Plane endpoint. The job sandbox has no network access (including loopback-to-host, LAN, Control Plane, DNS, proxy, metadata, or provider paths), and cannot access the host service's socket/pipe, identity key, TLS session, process, memory, IPC, or control interface. Any future input/output movement is bounded, policy-checked staging by a trusted supervisor—not a job network route or shared writable host mount. A compromised job therefore does not inherit the Runner's channel authorization.

**Network boundary:** the exact Control-Plane instance and its explicitly designated private LAN segment only. LAN membership is not authentication or authorization. The listener must authenticate the enrolled Runner instance and authorize each operation; the Runner must authenticate the intended Control Plane. Routing, firewall/vSwitch policy, and independent host-side observation must constrain and verify the exact destination, not a broad private-address range. No assumption is made that a private IP, DNS suffix, VPN, proxy, or trusted physical LAN is safe.

- **【要決定】** The deployment-specific LAN zone/segment and exact Control-Plane destination identity (fixed IP or exact FQDN plus validated server name) must be identified before endpoint verification. No wildcard host, subnet, DNS suffix, or address range is an endpoint.
- **【要決定】** The initial CP server-trust/bootstrap mechanism for one-time enrollment must be specified and verifiably authenticated before the endpoint can be used. It must bind the approved administrator's challenge to the exact proposed Runner instance/key and validate the CP identity; if this cannot be established, enrollment is denied, with no unauthenticated fallback.
- **【要決定】** If the endpoint uses a name, the exact internal resolver and its network path require their own endpoint design, verification, independent review, and separate Owner approval. No DNS query is allowed by this design unless that resolver is separately approved. A fixed-address deployment avoids this resolver dependency but does not waive endpoint identity, TLS, or endpoint approval.
- A future remote Runner or any operation over external networks remains a final product requirement, but is **not** covered or approved here. It requires a separate design of its network boundary, reachability, threat model, authentication/authorization/encryption, egress restrictions, failure behavior, evidence, and Owner approval. LAN approval cannot be reused for VPN, internet, cloud relay, or remote access.

## 3. Candidate transport and authorization contract

### 3.1 Transport and identity

- Use HTTPS over **TCP destination port 443** as the candidate listener and no other transport/port. Encryption and mutual peer authentication use a vetted standard TLS configuration, consistent with Entry 5. Plain HTTP, downgrade, invalid/expired/mismatched certificates, unknown trust roots, wrong server identity, missing client identity, and unapproved protocol versions/configurations must fail closed. The exact TLS versions, cipher suites, certificate profile, key lifetime, and rotation values are established only through the separate trust-design verification based on standard methods and evidence; this document does not invent or activate them.
- Bind the client identity to the enrolled, revocable `runner_instance_id`, its OS-keystore-protected instance key, exact Runner principal and pinned binary identity. Bind server authentication to the exact Control-Plane service identity. IP allowlisting alone is insufficient. A transport certificate is not a user identity, job receipt, job authorization, or permission to select a destination.
- Authenticate and authorize each logical operation, with least-privilege scopes and closed/versioned schemas. Unknown route, method, content type, version, field, identity, workspace, policy, or operation is denied. Do not pass transport credentials, secret bytes, or arbitrary command/path/URL data into a job payload. Do not log credentials, TLS private material, sensitive payloads, or provider data.
- The Control Plane's authoritative job approval receipt and E1 checks remain necessary before any enqueue; the Runner's independent E2 freshness/authority/revocation and binding recheck remains necessary immediately before any execution. Loss of authority, revocation, stale policy, expired approval, identity mismatch, or unavailable verification means deny/hold. In particular, while B6 is active, reject dispatch/enqueue explicitly even if a Runner or a valid transport exists; Runner execution also remains denied.

### 3.3 Per-endpoint approval state machine

For **each** endpoint ID (including any optional resolver or later-added service), record an immutable endpoint specification: purpose, exact source and destination identities, destination address/name, port, protocol/TLS profile, direction, network boundary, API operation scope, authn/authz rules, and allowed/denied cases. The required sequence is:

1. **Design:** produce the exact endpoint record and threat/failure analysis; no endpoint is enabled by writing a proposal.
2. **Verification:** test the exact endpoint and all denial paths in an isolated synthetic environment, with in-boundary behavior and independent host-side network observation. Skipped, unverifiable, unavailable, or ambiguous checks are failures/holds, not passes.
3. **Independent review:** a reviewer separate from the designer examines the exact design, implementation/configuration, evidence, and residual risk. The reviewer does not implement, activate, or approve on the Owner's behalf.
4. **Separate Owner approval:** obtain a recorded decision for that exact endpoint specification and evidence. Approval of one endpoint does not approve another endpoint, destination, protocol, port, operation, or a changed configuration.
5. **Operational activation:** separately authorize any implementation, firewall/port change, listener, Runner communication, or profile activation. These operational acts are explicitly outside this task and are not implied by either Entry 3 design approval or a future per-endpoint design approval.

Any security-relevant change to endpoint identity, port, protocol/TLS policy, API scope, trust binding, routing, firewall/vSwitch policy, Runner build, or host profile invalidates affected evidence and returns the endpoint to **unverified/inactive**. Audit every future approval/denial and endpoint configuration change without recording sensitive payloads.

## 5. Verification plans (future work; not run here)

All verification below is a future gate. It must use a disposable isolated lab, synthetic identities/payloads, a local non-forwarding mock Control Plane/test resolver where applicable, and host-side observation. No real Runner, provider, public endpoint, user credential, research data, port opening, or production network is used. No verification is claimed by this document.

### 5.1 Network and endpoint verification

1. **Inventory and identity:** bind the test result to the exact CP instance identity/address, Runner build/instance, OS profile, network interfaces/routes, effective host/guest filtering policy, protocol version and TLS configuration. Reject unknown/unexpected values. Confirm endpoint identity at both client and listener; IP filtering never substitutes for mTLS or application authorization.
2. **Positive controls:** on a synthetic isolated test network only, demonstrate the harness detects a narrowly scoped, correctly authenticated request to the mock CP endpoint after test-only policy setup. Confirm the intended request/response reaches only that mock endpoint and host-side telemetry sees the exact destination/port. This demonstrates the test harness, not production reachability or permission.
3. **Negative destination matrix:** attempt (without reaching external services) unlisted LAN hosts/ports, other VLAN/private ranges, internet-routed sink, provider/API names, cloud metadata/link-local addresses, IPv4 and IPv6, DNS and alternate resolvers, proxy variables, VPN/inherited routes, TCP/UDP/QUIC, loopback-to-host, and unexpected network interfaces. All must be denied both from the Runner service except its separately approved target, and from every job process including descendants. Capture host firewall/vSwitch counters and packet traces; unexplained traffic or missing instrumentation blocks the profile.
4. **Protocol/authentication:** test wrong/missing/revoked/expired client identity, wrong server name/trust, malformed TLS/protocol, downgrade, replay, duplicate fields, unknown version/field/route, unauthorized method, wrong `runner_instance_id`, workspace or policy, expired/revoked receipt, stale policy, and unavailable Control Plane. Confirm deny before side effect; no plaintext/alternate connection or job fallback.
5. **DNS conditional case:** if and only if a DNS endpoint receives separate approval, use a controlled test resolver to verify exact resolver/query scope, no search suffix/public fallback, rejection of poisoned/ambiguous answers, and mandatory TLS service-identity validation. Otherwise prove no DNS packets are emitted and use the explicitly approved fixed-address configuration.
6. **Boundary and lifecycle faults:** remove/change the endpoint record, trust store, certificate, host route/filter, interface, process monitor, or authorization authority; interrupt handshake, session, response, and cleanup; simulate restart and clock/revocation uncertainty. Assert no job starts, no unapproved retry or alternate endpoint occurs, the channel is closed/held, work/output is quarantined as applicable, and B6 remains effective.
7. **Independent observations:** correlate client-side denial/connection results with host firewall/vSwitch captures/counters and mock CP audit events. Test probes must be known to traverse the observation points. A client error alone does not prove traffic was blocked. Any unexpected packet, unobserved probe, unresolved route, or disagreement between evidence sources is a failure/hold.

### 5.2 File and artifact boundary verification

- Prove the job can access only its designated fresh workspace and approved bounded input/output staging. The Runner channel identity/configuration, keystore, CP socket/session, receipt/policy/control files, host profile, user files, OS/service state, sibling workspaces, runtime sockets, and other tenants remain unreadable and unwritable from the job, every descendant, and alternate path API.
- Probe path traversal, symlinks/reparse points, hardlinks, mount/volume replacement, path aliases, TOCTOU/open handles, inherited descriptors, and malicious artifact names/content. Verify immutable inputs and bounded output staging; no network transfer or host-wide mount is used as a shortcut.
- Verify artifact schema, size, digest, source provenance, job/Runner/workspace/policy binding, classification ceiling, live ACL/revocation and audit requirements before any later persistence or release. Tamper, missing provenance, stale policy, source deletion/revocation, or interrupted validation must hold the artifact and fail closed. Transport authentication/signatures do not certify safe content or authorize data access.
- Record effective OS ACLs, mounts, identities and host-side access telemetry. Any extra file visibility, uncertain cleanup, writable policy path or inability to observe a negative probe blocks profile activation.

### 5.3 Process, identity, and channel separation verification

- Verify Runner transport process runs under the dedicated enrolled OS principal, has only the required bounded channel operations, and the job runs under a distinct least-privilege identity/boundary. Confirm no interactive token/session, inherited handle, private-key access, TLS memory/session, service IPC, container/VM runtime socket or control-plane authority is exposed to the job.
- Launch bounded synthetic child/grandchild processes. Attempt host/other-tenant process enumeration, debug/handle access, signal/termination of unrelated services, privilege/capability acquisition, process-group/job/namespace escape, daemonization, and persistence. All cross-boundary access is denied; all descendants terminate/fence before cleanup is considered complete.
- Assert losing the Runner service, verifier, policy, authorization authority, process monitor, or isolation mechanism cannot cause a job to inherit host identity/network, use an alternate listener, or start before proof. On cancellation, timeout, service failure, or uncertain termination, close/fence the channel as applicable, hold results, quarantine the instance, and preserve B6. Process-tree containment alone is not filesystem or network proof.
- Bind observations to exact OS build, runtime/hypervisor, Runner/CP build, image/config/policy digests and test harness. Repeat invalidated checks after relevant changes; skipped tests are never passes.

## 7. Adversarial self-review and consistency notes

- **LAN exception creep:** the topology proposes one internal CP destination, not broad private-network access. Every other destination—including a private IP on the same LAN—is denied. DNS and other auxiliary services are not implicit.
- **No-egress ambiguity:** a future narrowly approved host control channel is distinct from job egress. Job execution remains network-isolated; no job-to-CP route exists. This document does not activate that host exception.
- **Direction ambiguity:** Runner initiates; responses return only on the established connection. No inbound Runner listener, push channel, callback, peer path or firewall opening is proposed.
- **TLS-as-authorization error:** mTLS authenticates transport peers only. Operation authorization, current receipt/policy/revocation, B6, classification and artifact gates remain separate.
- **Port overclaim:** TCP/443 is an explicitly identified design candidate, not a currently approved/open port. Any alternate port or protocol requires the complete endpoint sequence and separate decision; do not silently substitute.
- **Isolation bypass:** the job sandbox cannot share the Runner control socket, key, process identity, host network, user VPN/proxy/DNS, or unrestricted artifact mount. A Runner host allow rule cannot be inherited by job processes.
- **Future remote scope:** remote Runner/external network operations remain a final requirement, not dropped, but need independent boundary design and approval. This LAN endpoint table grants no remote reachability.
- **Evidence honesty:** no endpoint was contacted, no listener/firewall was configured, no profile activated, no independent review was performed, and no activation evidence is claimed. Per-endpoint Owner approval and operational authorization remain separate gates.
