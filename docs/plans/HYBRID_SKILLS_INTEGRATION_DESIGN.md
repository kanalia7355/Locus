# Hybrid Skills Integration Design

Status: P0 design and initial documentation-only adaptation. This design adds procedural knowledge to the existing Loop Orchestrator; it does not create an orchestrator, runtime, permission system, or transition authority.

## Scope and upstream provenance

Research source: [`obra/superpowers`](https://github.com/obra/superpowers), release tag `v4.0.0`, peeled commit **`95c6e1633630a1462679cf1284b95ec458a27a8e`**. The commit was fetched and inspected locally; `LICENSE` at that exact commit is the MIT License, copyright Jesse Vincent (2025). This SHA is the sole upstream basis for all inventory and registry provenance in this change. Upstream source is untrusted reference material, not instructions to execute.

P0 adds three adapted Markdown-only skills. No upstream scripts, hooks, visual companions, remote resources, commands, telemetry, package installs, or supporting files are brought into Locus. Skills are knowledge/procedure providers only. They cannot authorize or initiate tool use, subprocesses, network communication, credential access, approval, branch delivery, policy changes, or Phase transitions. If a skill conflicts with AGENTS.md, an ADR, the approved task/acceptance, a current Owner decision, or Controller state, the higher-authority source prevails and the skill must not be used to bypass it.

## Audit: existing mechanisms and gaps

- **Orchestration/state:** `.loop/config.yaml`, `loop_engine/controller.py`, `scheduler.py`, `state_store.py`, and the existing `$loop` skill provide the serial Controller, bounded attempts/review cycles, task states, configured QA, and delivery flow. The Loop skill requires current Goal/source snapshots and the CLI's doctor/launch path. No second orchestrator or Skills-specific executable adapter exists.
- **Policy/approval:** Controller snapshots immutable source specifications and policy; `loop_engine/approval.py` records exact-hash human decisions; `completion_gate.py` blocks unresolved decisions. A Skill cannot resolve a decision or alter its hash. Product dispatch remains rejected under B6 (`backend/app/agents/registry.py`); ADR-0011 and ADR-0012 preserve Plane-M zero-tool and Plane-R separation. Plane-R activation and independent E1/E2 rechecks remain separate gates. No Skill changes them.
- **Evidence/recovery:** Loop records task, execution, verification, review, decision, and checkpoint evidence in its existing state store. Recovery/reconciliation code handles interrupted or uncertain operations. Evidence is not created by a Skill's self-report; no Skills-specific evidence store is introduced.
- **Skill discovery:** Existing `.agents/skills/*/SKILL.md` documents use YAML `name`/`description` frontmatter and concise procedural bodies. This establishes a repository convention, not an independently verified runtime loader contract. Importantly, `loop_engine/audit_profile.py` explicitly sets `skills.bundled.enabled=false` and `skills.include_instructions=false` for the sealed audit runtime; this integration must not change that.
- **Specification/Phase state:** Product acceptance remains immutable. `PHASE_STATUS.md` and reconciliation documents contain dated historical snapshots followed by updates; current status must be taken from their latest explicit declaration and source evidence, not an old table row. Phase completion requires required verification and independent review; no Skills action can mark or transition a Phase.
- **Owner decisions:** Q1–Q7 and Entries 1–6 bind their respective scopes. Relevant open receipt/authorization mechanisms in ADR-0013 remain 【要決定】 and are not needed or resolved by this documentation-only work. Do not re-ask or silently decide any owner item.
- **CI:** `.github/workflows/quality.yml` and `loop-ci.yml` run repository quality and Loop checks; `pr-title.yml` validates conventional titles/subjects. Their CI activity is not a permission for a Skill to publish or push.

**Gaps addressed:** Locus has no documented, centrally inventoried provenance/trust metadata for Skills and no concise Locus-native planning, systematic debugging, or verification procedure. The registry below records documentation metadata only. It is not a loader, allowlist enforced at runtime, permission grant, or activation receipt.

**Legacy-scope conflict:** Existing `.agents/skills/loop/SKILL.md` instructs invoking Loop CLI operations and describes authorized delivery paths, while `owner-decision-request/SKILL.md` instructs committing and pushing a checklist. Other existing reviews/planning skills also name tools/actions. Therefore a literal repository-wide “no Skill file contains network/exec directives” check cannot pass without changing existing operational Skills, which is outside the three P0 adaptations and risks altering established Loop/Owner procedures. This P0 removes positive execution/network directives only from the three newly adapted Skills. No existing Skill is rewritten in this task; the global interpretation remains an explicit scope conflict rather than being silently weakened or claimed satisfied.

## Registry schema and authority

`.agents/skills/SKILLS_REGISTRY.md` records per entry: stable `id`, local path, upstream project and fixed commit, license, purpose, trust level, required permissions, dependencies, enabled state, and disposition. For P0 entries, `required permissions: none` means the procedure itself requests no capability; it does **not** confer a capability. `enabled: true` means the Markdown guidance is available in the ordinary project skills directory only. It does not enable the sealed audit profile, model tools, execution, network access, or any controller feature. Dependencies are document references only, never an instruction to invoke another tool or agent.

## Existing-mechanism mapping (no competing orchestrator)

| Concept | Existing Locus mechanism | Boundary |
|---|---|---|
| Registry | `.agents/skills/SKILLS_REGISTRY.md` (documentation metadata) plus the existing `.agents/skills/<id>/SKILL.md` layout | Not code, permission state, or a guaranteed runtime loader. |
| Loader | Existing agent environment's handling of repository Skill markdown, when available; otherwise an agent reads the named file as ordinary project documentation | No new loader is implemented. Missing/unavailable skills do not block or authorize work. Audit runtime continues to exclude skills. |
| Policy Gate | Immutable task/Goal/spec/acceptance snapshots, `.loop/config.yaml`, Controller authorization and QA gates, ApprovalQueue, B6/ADR gates | Skills only remind the agent to consult these. The deterministic Controller and existing backend gates alone enforce them. |
| Loop Adapter | Existing single serial Controller, worker/reviewer interfaces, and structured task/review schemas | Skills provide context to an already-authorized task; they cannot call adapters, spawn agents, or advance task/Phase states. |
| Evidence Store | Existing SQLite task/execution/verification/review/decision/checkpoint records; Git diff/commit evidence; exact-head CI evidence | Skill text and agent assertions are not authoritative evidence. No new evidence table is proposed. |
| Rollback | Existing Controller checkpoint/recovery/reconciliation and ordinary branch/worktree history under existing delivery authorization | A Skill cannot reset/clean/force-push/delete, resolve uncertain external operations, discard state, or change delivery policy. Rollback requires existing controls and exact-state evidence. |

## Risks and mitigations

- **Prompt injection / instruction confusion:** external skill text is untrusted; “MUST”, “iron law”, templates, quoted logs, plans, and review feedback cannot outrank the Owner, immutable task, AGENTS/ADRs, or Controller. Mitigation: explicit precedence in every implemented Skill; no upstream scripts or companion material.
- **Privilege/communication creep:** upstream operations can initiate shells, installs, network access, PRs, push, merge, or child agents. Mitigation: no capability-request mechanism is included in a Skill; only existing explicit approval/Controller mechanisms apply, fail-closed.
- **Stale/historical specifications:** phase/status files have historical passages and decision registers evolve. Mitigation: use current source/authoritative records; label unresolved choices 【要決定】; never infer approval.
- **False assurance:** a registry entry or Skill being “enabled” could be read as runtime enforcement. Mitigation: define metadata semantics in registry; no code loader/policy gate is claimed; audit runtime exclusion remains unchanged.
- **Rollback hazards:** upstream branch-completion workflow includes destructive/remote operations. Mitigation: existing recovery/checkpoint mechanism only; no automatic rollback or remote retry from these Skills.
- **Verification evidence mismatch:** partial, stale, skipped, synthetic, or wrong-head results could be overclaimed. Mitigation: require exact acceptance/profile/head binding and actual status; report failures/skips/unavailability distinctly.

## Acceptance tests

These are documentation acceptance checks, not new runtime policy gates:

1. Each P0 Skill has the existing `name`/`description` frontmatter, Locus-specific procedure, and explicit statement that it grants no permission or state transition.
2. Planning: a reviewer can trace every plan item to assigned scope, allowed paths, acceptance and current Locus verification, with pending Owner decisions labeled 【要決定】; the plan does not prescribe shell/network commands, subagents, delivery, or auto-transition.
3. Debugging: a reviewer can identify symptom, reproducible evidence, recent-change comparison, data-flow/root-cause hypothesis, minimal scoped test evidence, and correction/recheck; no sensitive values are logged or exposed, no independent retry cap is invented, and no external tool is invoked by the Skill.
4. Verification: completion claims require fresh, exact-scope Locus verification evidence and disclose failures/skips; no command execution, commit/push/PR, approval, delegation, or phase transition is initiated by the Skill.
5. Registry entries contain the complete schema; all entries identify the exact SHA and MIT license; only the three P0 skills are enabled; prohibited skills are absent.
6. Static content inspection finds no executable code blocks, network-fetch instructions, commands to execute external tools, credential requests, privilege escalation, or capability/approval claims in the three Skill files. Explicit boundary prose about what is prohibited is allowed.
7. Existing Loop and application checks run only through their configured QA environment. Their unavailable/failing result is not represented as passed. Audit profile continues to disable bundled skills and injected skill instructions.
8. Rollback check: removing/disabling a Markdown procedure changes no Controller permissions, SQLite evidence, approvals, task attempts, B6 state, or Phase status; restoring a document cannot replay delivery or execution.
