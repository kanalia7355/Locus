5. 外部のAIサービスと手元のAIを分ける処理で、修正を求められたまま上限に達した件

ひとことで言うと

外部のAIサービス（OpenAI互換サービス）と手元のPC内で動かすAIを区別して扱うプログラムについて、チェック担当から修正を求められたままやりとり回数の上限に達したため、どうするか決めてほしいです。

いまどうなっているの

挑戦回数は3回中2回ですが、チェック担当とのやりとり回数が2回中2回の上限に達し、判定は「修正が必要（CHANGES_REQUIRED）」のまま止まっています。チェック担当はプログラム（backend/app/main.py）について、次の3点を指摘しています。

  • 中くらいの問題（1つ目）：外部のAIの候補が「手元用」のリストにも混ざっている
    使えるAIモデルを探す処理（discover_models）で、外部のAIサービス（openai-compatible）の候補まで、手元で動かすAI用の登録リスト（runtime.registered）に書き込まれてしまっています。本来は手元用と外部用を分ける約束になっており、隠れたテストで失敗するおそれがあります。
  • 小さな問題（2つ目）：AIを無効にしても接続先や鍵がメモリに残っている
    接続先のURL（_base_url）やパスワードにあたる鍵（_api_key）が、AIモデルを無効にしたとき（disable）に消されず、プログラムの一時記憶（メモリ）に残り続けています。
  • 小さな問題（3つ目）：未設定のときに返す情報の項目がそろっていない
    現在の設定状況を取得する処理（model_runtime GET）で、外部サービス側が選ばれているのにまだモデルが設定されていないとき、手元側が未設定のときには出ない「api_key_present: False」という項目だけが残ってしまい、形がそろっていません。

決めないとどうなるの

この T-AIC-002 の作業が完了できず止まったままになります。ほかにどの作業がこの決定を待っているかは元の文に書かれておらず、ここは分かりません。

選べるやり方

チェック担当は、次の直し方を示しています。

1. 有効期限（TTL）が長い通行証の安全対策

残る弱点

通行証の有効期限（TTL）が長くなるほど、もしその通行証が外部に漏れてしまったときに、悪い人に使われてしまう時間も長くなります。

開発側が代わりに入れる対策

決定どおりの長い期限で進めますが、弱点を補うために「後から通行証を取り消せる仕組み（revoke）」と「いつ誰が使ったかの利用履歴の記録」の2つを必ず入れます。もしオーナーから「もっと短くしてほしい」と指示があれば、いつでも設定で短く変えられます。

2. 社内ネットワーク（LAN）の安全に対する考え方と2つの対策

残る弱点

「社内や研究室のネットワーク（LAN）の中だから攻撃は起きない」という前提には、開発側としては賛成していません。同じネットワークの中であっても、ウイルスなどに感染して踏み台になった端末や、外から持ち込まれた端末、同じネットワーク内の別の部署からのアクセスは起こりえます。

開発側が代わりに入れる対策

対策にどれだけお金や手間をかけるかの判断はオーナーの役割なので、仕組みが重くなる「お互いに厳しく本人確認し合う仕組み（重い相互認証）」は入れずに進めます。その代わり、費用がほぼかからずに効果がある次の2つだけは入れます。

  • 作業を実行するプログラム（Runner）を登録するときに使う、一回限りの合言葉。
  • 利用許可証（リース）の使用記録（誰のどの許可証が、いつ、どの Runner で使われたか）。

これらを入れておけば、将来「もっと本人確認を強くしたい」となったときの土台にもなります。

3. 危ないファイルの受け入れと隔離箱（サンドボックス）の採用

残る弱点

「危ないデータを入れるのは入れた本人の責任」という考え方は、被害がその本人のパソコンの中だけに収まる場合にしか成り立ちません。Locus はみんなで使う共有ツールなので、悪意のあるファイルを誰かが開いた瞬間に、サーバー側（つまり全員の資料）にまで被害が広がるおそれがあります。

開発側が代わりに入れる対策

その危険の広がりを防ぐために、ファイルを安全な隔離箱（サンドボックス）の中で開く仕組みを採用します。その安全対策を前提として、決定どおり「幅広い種類のファイルを許可する」形で実装します。

4. 同時に動かす数（スロット）を増やしたときの機械への負担

残る弱点

同時に処理できる数（スロット）を増やすと、それに比例してパソコンの一時記憶容量（メモリ）や画像・計算用の装置（GPU）の消費も増えます。実際にどこまで動かせるかの上限（N）は、システムを置く実機の性能によって決まります。

開発側が代わりに入れる対策

同時実行数（N）は設定で変えられるままにしておき、システムを起動したときに実際の機械の性能を測って、無理がある数になっていれば警告を出すようにします。

5. 二段階の本人確認（MFA）を使わない代わりに標準で入れる対策

変更の確認と残る弱点

パスワードに加えてスマホのアプリなどで確認する「二段階の本人確認（MFA）」は、2026-11-09の記録では「本番では必須」と整理されていましたが、今回のオーナーの回答で「不要」に変わりました。そのため、関連項目（IAM-005）の扱いを「実装しない（オーナー判断 2026-11-16）」に改めます。

IDとパスワードだけの場合、パスワードが1つ漏れただけで、そのまま全員の資料が見られてしまうという弱点が残ります。

開発側が代わりに入れる対策

二段階の本人確認を入れない代わりに、次の4つを標準の設定として入れます。

  • パスワードの最低限の複雑さ（文字数や種類の強さ）の決まり。
  • ログインに何度も失敗したら、一時的に入れなくするロック機能。
  • アカウントを発行したときと、管理者がリセットした後の初回ログイン時に、必ずパスワードを変更させる仕組み（must_rotate。定期的な変更を強制するものではありません）。
  • 誰がいつログインしたかの履歴を、管理者が確認できるようにすること。

6. AIが書いたプログラムを動かして図を作る機能の安全対策

残る弱点

「B（プログラムのコードを動かして図を作ること）」は、これまでのファイルの中身を読み取る機能（ファイル解析）よりも危険の度合いが高い境界になります。ファイル解析は「攻撃者が選んだデータを読む」だけですが、作図は「AIモデルが書いた命令を実際にコンピュータ上で動かす」ためです。

開発側が代わりに入れる対策

T-PH6-104 の安全境界をそのまま使い回すのではなく、作図専用に次の4つの条件を追加する前提で進め、これらを T-PH6-114 の合格条件に入れます。

  • 動かすのはAIが作ったプログラムだけにし、利用者の元の資料は書き換えられない状態（読み取り専用）で渡す。
  • 外に出せる結果は、画像1枚と画面の文字出力（標準出力）だけに限る。
  • インターネットや外部への通信（ネットワーク）は遮断する。
  • 動かせる時間と一時記憶容量（メモリ）の上限は、作図専用の別枠で制限する。
