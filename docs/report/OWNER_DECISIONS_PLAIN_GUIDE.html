申し送り通行証の有効期限（TTL）が長いことによる弱点と補い方

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

システムを使うための通行証の有効期限（TTL）を長くすると、もし通行証が外に漏れてしまったときに、悪い人がその通行証を使える時間も長くなってしまうという弱点が残ります。

開発側では、この弱点を補うために次の 2 つを必ず入れる方針で進めます。

  • 漏れた通行証をあとから使えなくする機能（取消 / revoke）
  • いつ誰が通行証を使ったかの記録（利用履歴）

なお、あとから「有効期限をもっと短くしたい」と指示していただければ、いつでも設定で変えられるようにします。

申し送り建物内のネットワーク（LAN）での本人確認の弱点と補い方

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

「建物内のネットワーク（LAN）だから攻撃は起きない」という前提には、開発側としては同意していません。LAN の中であっても、乗っ取られたパソコン（踏み台になった端末）、外から持ち込まれたパソコン、同じ LAN につながっている別の部署のパソコンからアクセスされることは起こりうるためです。

ただし、どれだけ費用や手間（コスト）をかけるかを判断するのはオーナーの役割なので、仕組みが大がかりになる「お互いを厳しく確認し合う仕組み（重い相互認証）」は入れずに進めます。

その代わり、費用がほとんどかからず効果のある次の 2 つだけは入れます。

  1. 作業を実際に動かすコンピュータ（Runner）を最初に登録するときに使う、1回限りの合言葉
  2. 一時的な利用許可（リース / lease）の使用記録（誰のどの利用許可が、いつ、どの Runner で使われたか）

この 2 つは、あとから本人確認をもっと強くしたくなったときの土台にもなります。

申し送りいろいろなファイルを広く受け入れるときの安全対策

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

「危ないデータを入れるのは本人のせい（自己責任）」という考え方は、被害がその人だけに収まる場合にしか成り立ちません。Locus はみんなで使う共有ツールなので、悪意のあるファイルが開かれた瞬間に、みんなで使っている中心のコンピュータ（サーバ側）＝全員の資料にまで被害が広がるおそれがあります。

そのため、外に被害が出ないように隔離された安全な箱（サンドボックス）を用意して危険との差を埋めることにし、その安全な箱を使うことを前提として、ファイルを「広く許容」する仕組みを作ります。

申し送り同時に動かせる作業の枠（スロット数 N）の決め方

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

同時に動かせる作業の枠（スロット）を増やすと、それに比例してメモリ（作業用の記憶領域）や GPU（画像や計算を高速に処理する部品）の消費が増えます。

いくつまで増やせるかの上限（N の上限）は、実際にソフトを動かすコンピュータ（配備先の実機）の性能によって決まります。そのため、N の値はあとから変えられる設定値のままにしておき、起動したときに実際の性能を測って、もし設定が多すぎる（超過している）ときは警告を出すようにします。

申し送り二段階の本人確認（MFA）を使わない場合の弱点と補い方

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

パスワードに加えて別の方法でも本人確認をする仕組み（MFA）は、2026-11-09 の記録では「本番で必須」と整理されていましたが、今回の回答で「不要」に変わりました。そのため、本人確認の要件番号 IAM-005 の扱いを「実装しない（オーナー判断 2026-11-16）」に改めます。

ID とパスワードだけでログインする場合、パスワードが外に漏れると、そのまま全ての資料を見られてしまう弱点が残ります。そのため、代わりに次の 4 つを標準（既定）の仕組みとして入れます。

  • パスワードの最低限の強さ（最低強度）を決める仕組み
  • 何度もログインに失敗したときに一時的に使えなくする仕組み（一時ロック）
  • すでにある must_rotate（新しく発行したときと、管理者がリセットしたあとの最初のログインで必ずパスワードを変えさせる仕組み。定期的に変えさせる強制ではありません）
  • 誰がいつログインしたかの履歴を管理者が確認できる仕組み（ログイン履歴の管理者可視化）

申し送りプログラムを動かして図を作る機能（B：コード実行）の安全対策

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

プログラムを動かして図を作る機能（B：コード実行）は、ただファイルの中身を読み取る機能（ファイル解析）よりも一歩踏み込んだ危険な境目になります。ファイル解析は「攻撃者が選んだデータを読む」だけですが、図を作る作業（作図）は「AI のモデルが書いた命令を実際に動かす（実行する）」ためです。

そのため、作業番号 T-PH6-104 で用意した安全の境目をそのまま使い回すのではなく、作図用として次の制限を追加する前提で進めます。

  • 動かすのは、新しく作られたプログラム（生成されたコード）だけにする
  • 利用者の元の資料（資料原本）は、書き換えられない形（読み取り専用）で渡す
  • 外に出せる結果は、画像 1 枚と、画面に出る文字の結果（標準出力）だけに限る
  • インターネットや外部への通信（ネットワーク）は遮断する
  • 動かせる時間と使えるメモリは、作図専用の別の枠として決める

これらの条件は、作業番号 T-PH6-114 の「できあがりを認める条件（受入条件）」として書き込みます。

申し送り開発ルールを書いたファイル（CLAUDE.md と AGENTS.md）の食い違い

対象：phase-6-extensions（第6段階の拡張作業）

報告の内容

現在、開発のルールを書いたファイルである CLAUDE.md と AGENTS.md には「サブエージェント駆動開発・並列エージェント起動を行わない（複数の作業用 AI を同時に動かして開発しない）」とはっきり書かれていますが、今回の指示とは内容が食い違っています。

この食い違いをそのままにしておくと、次に別の担当者が読んだときに、どちらのルールが正しいのか分からなくなってしまいます。

そのため、開発チームからは実態に合わせて両方のファイルを書き直すことを提案します。ただし、開発のルール管理（governance）の文章を変えるにはオーナーの承認が必要なため、ここではまだ書き換えず、提案だけにとどめています。
