3. 通行証の有効期限（TTL）を長くしたときの弱点と対策

ひとことで言うと

通行証の有効期限（TTL: 一度発行した通行証が使える時間）が長いと、万が一漏れたときに悪用される時間も長くなるという報告です。

オーナーの決定どおりに作ると残る弱点

通行証の有効期限（TTL）を長く設定するほど、もし誰かに通行証を盗まれたり漏れたりした場合に、その通行証を使われてしまう時間も長くなります。

開発側が代わりに取る対策

この弱点を補うため、次の2つを必ず入れる方針で進めます。

  • 通行証を後から強制的に使えなくする仕組み（revoke: 取消）
  • 誰がいつ使ったかの利用履歴の記録

決める前に知っておくこと

  • この項目は決定待ちではなく報告です。
  • 有効期限（TTL）を短くしたいという指示をいただければ、いつでも設定で変更できます。

4. 研究室内のネットワーク（LAN）の安全性と本人確認

ひとことで言うと

研究室内のネットワーク（LAN）だから安全とは言い切れないため、費用がほぼかからない最低限の守りだけ入れて進めるという報告です。

オーナーの決定どおりに作ると残る弱点

開発側としては「内部ネットワーク（LAN）の中だから攻撃が起きない」という前提には同意していません。内部であっても、乗っ取られて踏み台になった端末、外から持ち込まれた端末、同じネットワーク内の別部署からのアクセスは起こりえます。

ただし、セキュリティにどれだけ費用をかけるかはオーナーの判断であるため、お互いが本物かを厳しく確かめ合う重い仕組み（相互認証）は入れずに進めます。

開発側が代わりに取る対策

費用がほぼゼロで効果がある、次の2つだけを入れます。

  • 作業を動かす機械やプログラム（Runner）を登録するときに使う、1回限りの合言葉
  • 作業を任せた貸し出し記録（lease: 誰のどの許可が、いつ、どの Runner で使われたか）の保存

決める前に知っておくこと

  • これら2つの仕組みは、将来もし本人確認をもっと強くしたくなったときの土台としても使えます。

5. 危ないファイルが開かれたときの被害範囲と隔離の仕組み

ひとことで言うと

共有ツールでは1人のミスが全員の資料に被害を広げるため、隔離された安全な仕組み（サンドボックス）を前提に実装するという報告です。

オーナーの決定どおりに作ると残る弱点

「危ないデータを入れるのは本人の責任」という考え方は、被害が本人の範囲だけで終わる場合にしか成り立ちません。Locus はみんなで使う共有ツールなので、悪意のあるファイルが開かれた瞬間に、みんなのデータが入っている中心のコンピュータ（サーバ）側、つまり全員の資料へ被害が及ぶおそれがあります。

開発側が代わりに取る対策

本人の責任だけでは防げない差を埋めるために、外に影響が出ないよう隔離する仕組み（サンドボックス）を採用します。その隔離の仕組みがあることを前提として、「データを広く受け入れる」方針を実装します。

決める前に知っておくこと

  • どのようなファイル形式や制限になるかの詳しい条件は、元の文には書かれていません（ここは分かりません）。

6. 同時に動かせる作業の数（N）と機械の性能

ひとことで言うと

同時に動かす作業の数（スロット: N）を増やすと機械への負担も比例して増えるため、起動時に性能を測って限界を超えていたら警告するという報告です。

オーナーの決定どおりに作ると残る弱点

同時に動かせる作業の枠（スロット）を増やすと、記憶領域（メモリ）や画像・計算を速くする部品（GPU）の消費量もそれに比例して増えます。いくつまで動かせるか（N の上限）は、実際に設置する機械の性能によって決まります。

開発側が代わりに取る対策

設定された数（N）はそのまま受け入れつつ、システムを起動したときに実際の機械の性能を測り、無理な数になっていたら警告を出すようにします。

決める前に知っておくこと

  • 具体的な上限の数値は、配備先の機械の性能によって変わるため、元の文には書かれていません（ここは分かりません）。

7. 二段階認証（MFA）を不要にした場合のパスワード対策

ひとことで言うと

二段階認証（MFA）を入れない決定に変わったため、パスワードが漏れたときの被害を減らす4つの対策を標準で入れるという報告です。

オーナーの決定どおりに作ると残る弱点

二段階認証（MFA: パスワードに加えてスマホなどで本人確認をする仕組み）は、2026-11-09 の記録では「本番運用で必須」と整理されていました。しかし今回の回答で「不要」に変わったため、この機能（要件番号 IAM-005）の扱いを「実装しない（オーナー判断 2026-11-16）」へ改めます。

ID とパスワードだけで入る仕組みにすると、もしパスワードが外に漏れた場合、それだけで全員の資料を見られてしまう弱点が残ります。

開発側が代わりに取る対策

二段階認証の代わりに、次の4つを標準の設定として入れます。

  • パスワードに最低限の強さを求めること
  • 一定回数ログインに失敗したら一時的に使えなくすること（一時ロック）
  • パスワードを定期的に変えてもらう既存の運用（must_rotate）を続けること
  • いつ誰がログインしたかの履歴を管理者が確認できるようにすること

決める前に知っておくこと

  • これらは二段階認証を入れないことによる弱点を補うための対策です。

8. 図を作るためにプログラムを動かすときの安全対策

ひとことで言うと

図を作る機能（B: コード実行）は、ただファイルを読むよりも危険度が高いため、専用の厳しい制限を追加して進めるという報告です。

オーナーの決定どおりに作ると残る弱点

ファイルを解析するだけの作業は「攻撃者が用意したデータを読み取る」だけですが、図を作る作業は「AI（モデル）が書いた命令そのものを実際に動かす（コード実行）」ため、より踏み込んだ危険な境界になります。そのため、既存の解析用の安全対策（作業番号 T-PH6-104）をそのまま使い回すだけでは足りません。

開発側が代わりに取る対策

図を作る作業専用に、次の制限を追加する前提で進めます。

  • 動かすのは作られたプログラムだけにし、利用者の元の資料は「見るだけ（読み取り専用）」で渡して書き換えられないようにする
  • 結果として外に出せるのは、画像1枚と画面に出る文字の結果（標準出力）だけに限る
  • 外部や他の場所との通信（ネットワーク）は遮断する
  • 動かせる時間と使える記憶領域（メモリ）は、図を作る作業用の別枠で制限する

決める前に知っておくこと

  • 上記の対策は、作業番号 T-PH6-114 が完了したと認めるための条件（受入条件）として組み込みます。
