2. 申し送り（決定どおりに作るうえでの注意点・報告）

説明

申し送りとは何か・言葉の意味（凡例）

ここからの項目は、オーナーに新しく何かを決めてもらうものではありません。 「オーナーの決定どおりに作るが、その代わりこういう弱点や注意点が残るため、開発側ではこういう対策で補います」という報告です。

  • 【回答】：オーナーが答えたそのままの言葉
  • 【解釈】：プログラムを作るときに従う決まり
  • 【解禁】：その決定によって着手できるようになる要件の番号（ID）
  • 【申し送り】：開発側としてそのままでは同意していない点、または確認しておきたい注意点
申し送り

通行証の有効期限（TTL）が長いほど漏れたときのリスクが増える件

段階：phase-6-extensions

どういうことか： TTL（通行証が使える期限の長さ）が長いほど、もしその通行証が外に漏れたときに「悪い人に使われ続ける時間」も長くなります。

開発側の対応と残る点： 決定どおりに進めるため、「あとから通行証を使えなくする仕組み（取消 / revoke）」と「いつ誰が使ったかの利用履歴の記録」の 2 つを必ず入れて弱点を補います。期限を短くしたいという指示があれば、いつでも設定で変えられます。

申し送り

同じネットワーク（LAN）の中なら安全という前提について

段階：phase-6-extensions

どういうことか： 「同じ建物や組織内のネットワーク（LAN）の中だから攻撃は起きない」という前提には、開発側としては同意していません。同じネットワーク内でも、乗っ取られて踏み台になった端末、外から持ち込まれた端末、同じネットワーク内の別部署からのアクセスは起こりえます。

開発側の対応と残る点： ただし、どこまで費用をかけるかの判断はオーナーが決めることなので、手間や費用の重い「お互いの本人確認の仕組み（相互認証）」は入れずに進めます。その代わり、費用がほぼゼロで効果がある次の 2 つだけは入れます。

  1. 作業を動かす機械（Runner）を登録するときの「一回限りの合言葉」
  2. 貸し出し許可（リース / lease）の利用記録（誰のどの許可が、いつ、どの機械で使われたか）

これら 2 つは、あとから本人確認を強くしたいときの土台にもなります。

申し送り

危ないデータの受け入れと隔離された箱（サンドボックス）

段階：phase-6-extensions

どういうことか： 「危ないデータを入れた本人の責任」という考え方は、被害がその本人だけにとどまるときにしか成り立ちません。Locus はみんなで共有して使う道具なので、悪意のあるファイルが開かれた瞬間に、サーバ側（つまり全員の資料）へ被害が広がるおそれがあります。

開発側の対応： 隔離された安全な箱（サンドボックス）を使うのは、その危険を埋めるためです。この安全な箱を使うことを前提として、「いろいろなデータを広く受け入れる」仕組みを作ります。

申し送り

同時に動かす枠（スロット数 N）と実機の性能

段階：phase-6-extensions

どういうことか： 同時に動かせる枠（スロット）の数 N を増やすと、それと同じ割合でメモリ（作業用の記憶場所）や GPU（画像や複雑な計算を処理する部品）の消費量が増えていきます。実際にこのシステムを置くパソコンの性能によって動かせる上限が決まります。

開発側の対応： N の数は設定で変えられるままにし、起動したときに実際のパソコンの性能を測って、上限を超えていたら警告を出すようにします。

申し送り

二重の本人確認（MFA）を使わない場合のパスワード運用（IAM-005）

段階：phase-6-extensions

どういうことか： MFA（パスワードに加えてスマホの確認コードなどを使う二重の本人確認）は、2026-11-09 の記録では「本番で必須」と整理されていましたが、今回の回答で「不要」に変わりました。そのため、IAM-005 の扱いを「実装しない（オーナー判断 2026-11-16）」に改めます。

残る弱点と開発側の対応： ID とパスワードだけの場合、パスワードが外に漏れるとそのまま全員の資料が見られてしまう弱点があります。そのため、代わりに次の 4 つを標準で入れます。

  • パスワードの最低限の強さのルール
  • 入力を一定回数間違えたときに一時的にログインできなくする仕組み（一時ロック）
  • 以前からある must_rotate（新しく発行したときと、管理者がリセットしたあとの最初のログインで必ずパスワードを変えさせる仕組み。定期的な変更を強制するものではありません）
  • いつ誰がログインしたかの履歴を管理者が確認できる仕組み
申し送り

決まったことの作業化（PROGRESS.md）と申し送りの扱い

段階：phase-6-extensions

  • 今回決まった項目は、PROGRESS.md という進行表の作業（ジョブ）に書き換えます。決まっていない項目は作業にしません。
  • 「申し送り」は、オーナーの決定をひっくり返すものではありません。弱点を補うために開発側が取る対策をはっきり示しているだけで、「不要」と指示されれば外します。
申し送り

AIが書いた命令を動かす「作図」の安全境界（T-PH6-114）

段階：phase-6-extensions

どういうことか： 「B（プログラムの命令を動かす仕組み＝コード実行）」は、ファイルを読み取るだけの「解析」よりもさらに気をつけるべき境目になります。解析は「攻撃者が選んだデータを読む」だけなのに対し、作図は「AI（モデル）が書いた命令そのものを動かす」からです。

開発側の対応： T-PH6-104 で作った安全な境目をそのまま使い回すのではなく、作図用に次の 4 つを追加する前提で進めます。これらは T-PH6-114 の合格条件（受入条件）に入れます。

  • 動かすのは作られたプログラム（コード）だけにし、利用者の元の資料は書き換えられない「読み取り専用」で渡す
  • 外に出せる結果は「画像 1 枚」と「文字の出力（標準出力）」だけに限る
  • ネットワーク通信は遮断する
  • 動かせる時間とメモリの量は、作図用に別の枠を用意する
申し送り・提案

ルール文書（CLAUDE.md と AGENTS.md）の食い違いについての提案

段階：phase-6-extensions

どういうことか： CLAUDE.md と AGENTS.md というルール文書には、現在「別のAI担当（サブエージェント）を増やしたり、同時に複数動かしたりしない」とはっきり書かれており、今回の指示と食い違っています。

開発側からの提案： 実際の進め方に合わせて両方のファイルを書き換えることを提案します。ただし、ルール（governance）の文章を変えるにはオーナーの承認が必要になるため、ここでは提案だけにとどめます。食い違いをそのままにしておくと、次に別の担当者が読んだときにどちらが正しいのか分からなくなります。
