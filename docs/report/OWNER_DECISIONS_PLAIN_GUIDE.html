3. 通行証の有効期限（TTL）が長いときの弱点と対策

ひとことで言うと

TTL（通行証が使える有効期限）を長くする決定どおりに作りますが、通行証が漏れたときの危険を減らす対策を合わせて入れます。

残る弱点と気をつけること

TTL（有効期限）が長いほど、万が一その通行証が外に漏れたときに「他人がその通行証を悪用できる時間」も長くなります。

開発側が代わりに入れる対策
  • 通行証を途中で無効にする機能（取消 / revoke）を必ず入れます。
  • いつ使われたかを残す「利用履歴の記録」を必ず入れます。
  • もし「やっぱり期限を短くしたい」という指示があれば、いつでも設定で変更できるようにしておきます。

4. 研究室内のネットワーク（LAN）での安全対策

ひとことで言うと

「研究室内だから安全」という前提には開発側として同意していませんが、費用のかかる厳しい認証は入れず、ほぼ費用ゼロで効く2つの対策だけを入れて進めます。

残る弱点と気をつけること

LAN（研究室などの内側のネットワーク）の中であっても、ウイルスなどに感染して乗っ取られた端末（踏み台になった端末）、外から持ち込まれた端末、同じLANにつながっている別部署の端末から攻撃が届くことは起こりえます。そのため、「LAN内だから攻撃がない」という前提には、実装（作る側）としては同意していません。

開発側が代わりに入れる対策

お金や手間（コスト）をどれだけかけるかの判断はオーナーの役割なので、重い相互認証（お互いが本物かを厳しく確かめ合う仕組み）は入れずに進めます。その代わり、費用がほぼゼロで効果がある次の2つだけは入れます。

  • Runner（作業を動かす機械やプログラム）を登録するときの「1回限りの合言葉」
  • リース（作業用の許可枠）の利用記録（誰のどのリースが、いつ、どのRunnerで使われたかの記録）

これらを入れておくと、あとから本人確認を強くしたくなったときの土台にもなります。

5. みんなが使う道具（共有ツール）としての安全対策

ひとことで言うと

「広く許容する」という決定どおりに作りますが、1人の危険なファイルで全員の資料が壊れないよう、安全な隔離の箱（サンドボックス）を使う前提で進めます。

残る弱点と気をつけること

「危ないデータを入れるのは本人の責任」という考え方は、被害がその本人だけに収まるときしか成り立ちません。Locus はみんなで使う共有ツールなので、悪意のあるファイルが開かれた瞬間に、サーバ側（みんなの資料を保存して動かしている中心のコンピュータ）にある全員の資料へ被害が広がるおそれがあります。

開発側が代わりに入れる対策

その危険を埋めるためにサンドボックス（外や他の資料に被害が広がらないように隔離された安全な箱）を使います。サンドボックスを使うことを前提として、オーナーの決定どおり「広く許容」を実装します。

6. 同時に動かせる数（スロット）と機械の性能

ひとことで言うと

同時に動かす数（N）は設定で変えられるままにし、起動したときに実際の機械の性能を測って、無理な数になっていたら警告を出します。

残る弱点と気をつけること

スロット（同時に動かせる作業の枠）を増やすと、それに比例してメモリ（作業のために一時的に使う記憶場所）やGPU（画像処理や計算を担当する部品）の消費量も増えます。最大いくつ（N）まで動かせるかは、実際に設置する機械の性能によって決まります。

開発側が代わりに入れる対策

N の値は設定で決められるままにしておき、システムを起動するときに実際の機械の性能を測って、N が上限を超えていたら警告を出すようにします。

7. 多要素認証（MFA）を使わない場合のパスワード対策

ひとことで言うと

MFA（多要素認証）を使わない決定に合わせて実装しないことにしますが、パスワードが漏れたときの危険を和らげる別の対策を初期設定にします。

いままでの経緯と残る弱点

MFA（多要素認証：パスワードに加えてスマホの確認など別の確認も使う仕組み）は、2026-11-09 の記録では「本番で必須」と整理されていました。しかし今回の回答で「不要」に変わったため、要件番号 IAM-005 の扱いを「実装しない（オーナー判断 2026-11-16）」に改めます。

ID とパスワードだけでログインする仕組みにすると、パスワードが1つ漏れただけで、すべての資料を見られてしまう弱点が残ります。

開発側が代わりに入れる対策

代わりに、次の4つを初期設定（既定）にします。

  • パスワードの最低限の強さのルール
  • ログインに何度も失敗したときの一時ロック
  • すでにある must_rotate（アカウント発行時と、管理者がリセットした後の初回ログイン時に、必ずパスワードを変更させる仕組み。定期的な変更を強制するものではありません）
  • いつ誰がログインしたかの履歴を管理者が確認できる仕組み

9. AIが書いたプログラムを動かす（作図）ときの安全対策

ひとことで言うと

作図のためにプログラムを動かす機能は、ファイルを読み取るだけの機能より危険が大きいため、作図専用の厳しい制限を追加して進めます。

残る弱点と気をつけること

B（コード実行＝プログラムの命令をそのまま動かすこと）は、単なるファイル解析より踏み込んだ危険な境界になります。ファイル解析は「攻撃者が選んだデータを読む」だけですが、作図は「モデル（AI）が書いた命令を実行する」ためです。

開発側が代わりに入れる対策

T-PH6-104 という作業で作った安全の境界をそのまま使い回すのではなく、作図用として次の4つを追加する前提で進めます。これらは T-PH6-114 の受入条件（完成と認めるための条件）に入れます。

  • 実行するのは作られたコード（プログラム）だけにし、利用者の元の資料は「見るだけ（読み取り専用）」で渡して書き換えられないようにする
  • 外に出せる結果は「画像1枚」と「標準出力（画面に出す文字の結果）」だけに限る
  • ネットワーク（外部との通信）は遮断する
  • 動かせる時間と使えるメモリ（記憶場所）の上限は、作図用に別枠で設ける
