5. 開発側の意見

3. 決めないとどうなるの

この項目は決定を待つものではなく、オーナーの決定に対する報告（申し送り）です。

4. 選べるやり方

選択肢は示されていません。

5. 開発側の意見

MFA（エムエフエー：パスワードだけでなくスマホの確認など複数の方法で本人を確かめる仕組み）を「不要」とするオーナー判断に合わせて実装しないことにしますが、パスワードが漏れると全資料を見られてしまうため、代わりに 4 つの安全対策を標準で入れます。

2. いまどうなっているの

2026-11-09 の記録では、MFA は「本番で必須」と整理されていました。しかし今回の回答で「不要」に変わったため、IAM-005（本人確認に関するルールの管理番号）の扱いを「実装しない（オーナー判断 2026-11-16）」に改めます。

3. 決めないとどうなるの

この項目は決定を待つものではなく、オーナーの決定に対する報告（申し送り）です。

4. 選べるやり方

選択肢は示されていません。

5. 開発側の意見

ID（利用者を見分ける名前や番号）とパスワードだけの場合、パスワードが外に漏れるとそのまま全員の資料の閲覧につながってしまいます。そのため、代わりに次の 4 つを標準（既定）にします。

  • パスワードの最低限の強さ
  • ログインに一定回数失敗したときの一時ロック
  • 既存の must_rotate（アカウント発行時と管理者によるリセット後の初回ログインで必ずパスワードを変更させる仕組み。定期変更の強制ではありません）

6. 決める前に知っておくこと

MFA を使わないため、パスワードが漏れたときの危険は残ります。なお、上記の代替策も不要と指示されれば外せます。

3. 決めないとどうなるの

4. 選べるやり方

選択肢は示されていません。

5. 開発側の意見

作図用には次の 4 つを追加する前提で進めます。

  1. 実行するのは作られたプログラム（コード）だけにし、利用者の資料の原本は読み取り専用（書き換え不可）で渡す
