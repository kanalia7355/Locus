T-PH6-132：やり直し回数の上限に達した作業の扱い

記録日時：2026-11-26 15:20:48（日本時間）／ 当番による確認：15:26

1. ひとことで言うと

待っているあいだに別の作業で問題が直ってしまった T-PH6-132 を、どうやって終わらせるかを決めてほしいです。

2. いまどうなっているの

T-PH6-132 は、やり直し回数（3回中3回）も、確認担当とのやりとり回数（2回中2回）も上限に達して止まっています。もともとこの作業が直す予定だった2本のファイルは、待っているあいだに別の作業 T-PH6-127（変更番号 fff6a0a、当日 02:39、「画面ゲートを e2e 全体に広げ、腐っていた 12 件を直す」）によってすでに直されました。

実際に本体を測ったところ、T-PH6-132 の変更を1行も入れない状態で、画面テスト（npm --prefix frontend run test:e2e）は50件すべて合格（2.6分）、文法チェック（lint）も問題なく通っています（exit 0）。しかし、合格条件の1つ（受入条件2：「直した内容を1件ずつ、直す前の失敗内容とともに報告する」）について、1つも直していないため書けるものが無く、確認担当（レビュアー）から修正要求が出たまま止まっています。

3. 決めないとどうなるの

T-PH6-132 の作業票が「やり直し上限で停止中」のまま終わらずに残ります。この作業を待っている別の作業があるかどうかは、元の文に書かれていないため、ここは分かりません。

4. 選べるやり方

選択肢 A：T-PH6-127 によってすでに終わったもの（消化済み）として閉じる
  • よいところ：すでに別の作業で直ってテストも通っている現実と合っており、無理に条件を書き換えずに済みます。
  • よくないところ：元の文には特に書かれていません。
選択肢 B：合格条件（条件2）を「12件がどの変更で直ったかを変更履歴（git log）で示す」に書き換える
  • よいところ：元の文には特に書かれていません（T-PH6-104 と同じ「移動」の扱いになると書かれています）。
  • よくないところ：できあがるものが他人の変更の説明だけになってしまいます。また、プログラムを1行も変えない作業は「何も変更しなかった（changed nothing）」と判定されて失敗扱いになり、やり直し回数を消費してしまいます。
選択肢 C：やり直し回数と確認回数を元に戻して、もう一度やり直す
  • よいところ：元の文には特に書かれていません。
  • よくないところ：これまでの3回とも同じ結論（変更なし）になっており、やり直しても同じ結果になる見込みが高いです。

第2部：申し送り（決定に対する注意・補足報告）

前提と用語

申し送りの読み方とルール

ここからの項目は、オーナーに新しく決めてもらうものではありません。「オーナーの決定どおりに作りますが、その代わりこういう弱点や注意点が残るので、開発側ではこういう対策を入れます」という報告です。

  • 決まった項目は PROGRESS.md（作業の進行表）の作業へ変換します。決定がない項目は作業にしません。
  • ここでの「申し送り」は、オーナーの決定をくつがえすものではありません。弱点を補うための対策を示しているだけなので、「不要」と指示されれば外します。
元の文のラベル やさしい意味
【回答】 オーナーが答えた言葉そのまま
【解釈】 プログラムを作るときに従うルール
【解禁】 この決定によって着手できるようになる要件の番号
【申し送り】 開発側として同意していない点、または確認してほしい点
申し送り 1

通行証の有効期限（TTL）と悪用への備え

報告内容：有効期限（TTL：通行証が使える時間）が長いほど、万が一その通行証が外に漏れたときに不正に使われてしまう時間も長くなります。

開発側が取る対策：通行証を途中で無効にできる「取消機能（revoke）」と、「いつ誰が使ったか」の利用履歴の記録を必ず入れて補う方針で進めます。もし「やはり有効期限を短くしたい」と指示があれば、設定でいつでも変えられます。
申し送り 2

社内ネットワーク（LAN）内の安全対策と費用のバランス

報告内容：「同じ社内ネットワーク（LAN）の中だから攻撃は起きない」という前提には、開発側としては同意していません。LAN の中でも、乗っ取られて踏み台になった端末や、持ち込み端末、同じネットワーク内の別部署からのアクセスは起こりえます。

開発側が取る対策：ただし、どこまで費用や手間をかけるかの判断はオーナーの役割なので、仕組みが重い「相互認証（お互いに証明書などで厳しく確認し合う仕組み）」は入れずに進めます。その代わり、費用がほぼゼロで効果がある次の2つだけを入れます。
  1. 作業を実行する機械（Runner）を登録するときの「1回限りの合言葉」
  2. 貸し出し許可証（lease）の利用記録（誰のどの許可証が、いつ、どの機械で使われたか）
これらは、後から本人確認をもっと厳しくしたくなったときの土台にもなります。
申し送り 3

危険なファイルを開いたときの影響範囲と隔離（サンドボックス）

報告内容：「危ないデータを入れるのは入れた本人の責任」という考え方は、被害がその人だけにとどまる場合にのみ成り立ちます。Locus はみんなで使う共有ツールなので、悪意のあるファイルが開かれた瞬間に、サーバー側（＝全員の資料）へ被害が広がるおそれがあります。

開発側が取る対策：その危険を埋めるために、外に影響を出さない隔離された箱（サンドボックス）を使う前提で、「いろいろなファイルを広く受け入れる」仕組みを作ります。
申し送り 4

同時に動かす数（スロット N）と機械のメモリ・GPU

報告内容：同時に動かせる枠（スロット数 N）を増やすと、それに比例してメモリや画像処理装置（GPU）の消費量が増えます。実際にいくつまで動かせるかの上限は、設置する実機（パソコンやサーバー）の性能によって決まります。

開発側が取る対策：N は設定値のままにしておき、起動するときに実際の性能を測って、上限を超えている場合は警告を出すようにします。
申し送り 5

2段階認証（MFA）を無しにする場合の安全対策

報告内容：2段階認証（MFA：パスワードに加えてスマホなどで確認する仕組み）は、2026-11-09 の記録では「本番で必須」と整理されていましたが、今回の回答で不要に変わりました。そのため、IAM-005 の扱いを「実装しない（オーナー判断 2026-11-16）」へ改めます。ただし、ID とパスワードだけの場合、パスワードが外に漏れるとそのまま全員の資料が見られてしまう弱点が残ります。

開発側が取る対策：代わりに次の4つを標準（既定）の仕組みとして入れます。
  • パスワードに最低限の強さ（最低強度）を求めること
  • 一定回数続けて間違えたら一時的にロックすること
  • アカウント発行時や管理者がリセットした後の最初のログインで必ずパスワードを変更させる仕組み（既存の must_rotate。定期的な変更の強制ではありません）
  • ログインの履歴を管理者が確認できるようにすること
申し送り 6

作図のためのプログラム実行（コード実行）の制限

報告内容：決定された「B（コード実行）」は、単なるファイルの解析よりも危険度が高い境界になります。ファイルの解析が「攻撃者が選んだデータを読む」のに対し、作図は「AI モデルが書いた命令を実際に動かす」ためです。

開発側が取る対策：T-PH6-104 の安全境界をそのまま使い回すのではなく、作図用として次の4つの制限を追加する前提で進め、T-PH6-114 の合格条件に入れます。
  • 実行するのは生成されたプログラムだけにし、利用者の元の資料は「見るだけ（読み取り専用）」で渡す
  • 出力できるものは「画像1枚」と「文字の画面出力（標準出力）」だけに限る
  • 外部との通信（ネットワーク）は遮断する
  • 動かせる時間とメモリの上限は、作図用に別枠で設ける
申し送り 7

ルール文書（CLAUDE.md と AGENTS.md）の食い違いについて

報告内容：現在のルール文書である CLAUDE.md と AGENTS.md には「別の補助 AI に分担させたり、同時に複数動かしたり（並列起動）しない」と書かれており、今回の指示と内容が食い違っています。このまま放置すると、次に別の担当者が読んだときにどちらが正しいのか分からなくなってしまいます。

開発側からの提案：ルールの文面（governance）を変えるにはオーナーの承認が必要なため、ここでは「実態に合わせて両方のファイルを更新すること」を提案するにとどめます。
