1. T-PH6-132：別の作業で直ってしまった問題の仕事をどう閉じるか

記録日時：2026-11-26 15:20（当番判断の保留：15:26）

ひとことで言うと

別の作業によってすでに解決してしまった仕事について、完了扱いで閉じてよいか、完了条件を書き換えるか、もう一度やり直させるかを決めてほしいです。

いまどうなっているの

この仕事は「挑戦できる回数（3回のうち3回）」と「確認者（レビュアー：できたものを点検する担当）からのやり直し回数（2回のうち2回）」を使い切って止まっています。

もともとこの仕事が直すはずだった2つの場所は、別の仕事（T-PH6-127、今日02:39の変更記録 fff6a0a）によってすでに直されていました。そのため、今回の担当が何も変更しなかった（the worker changed nothing）のは正しい判断でした。開発側が変更を1行も当てない状態で全体の自動テスト（プログラムが正しく動くか確かめる作業）を測ったところ、50件すべて合格し、書式チェック（lint）も問題なく通っています。

しかし、この仕事の完了条件の2番目に「直した内容を1件ずつ、直す前の失敗内容とあわせて報告すること」と書かれています。実際には1つも直していないため報告できることがなく、確認者が合格を出せずに止まっています。当番の担当者が勝手に完了条件を書き換えることはできないため、オーナーの判断が必要です。

決めないとどうなるの

この仕事（T-PH6-132）を完了にするかやり直すかが決まらず、止まったままになります。なお、ほかにこの決定を待っている別の作業があるかは、元の文章に書かれていないためここは分かりません。

選べるやり方

選択肢A：別の仕事（T-PH6-127）で解決済みとして閉じる

  • よいところ：すでに問題が直っている実態に合っており、無駄なやり直しを増やさずに仕事を終えられます。
  • よくないところ：元の完了条件2のとおりの報告書は作られません。

選択肢B：完了条件2を「どの変更記録で12件が直ったかを履歴（git log）で示すこと」に書き換える

  • よいところ：完了条件を満たす形に整えてから進められます。
  • よくないところ：できあがる成果が他人の変更記録の説明だけになってしまいます。また、プログラムを1行も変えない作業を再び任せると「何も変更しなかった」と判断されて挑戦回数を失うおそれがあります。

選択肢C：挑戦回数と確認回数を元に戻して、もう一度やり直させる

  • よいところ：手順どおりに再挑戦させられます。
  • よくないところ：すでに3回とも同じ結論（直すべきものが無い）に行き着いているため、やり直しても進まない可能性が高いです。

開発側の意見

選択肢Aをおすすめします。

理由：この仕事が待っていた問題は別の仕事（T-PH6-127）によってすでに終わっており、何も変更しない状態で自動テスト50件と書式チェックがすべて通っているためです。選択肢Cは3回とも同じ結論になっており、おすすめしません。

決める前に知っておくこと

  • 作業場所に残っている39行と14行の差は、すべて自動整形ツール（prettier）による改行の折り返しだけで、テストの意味は変わっていません。
  • 詳しい調査結果は progress/phase-6-extensions/tasks/T-PH6-132.md に記録されています。

phase-6-extensions / 申し送り

1. 通行証（TTL：使える有効期限）の長さについて

オーナーの決定どおりに進めます。

残る弱点と補い方：通行証の有効期限（TTL）が長いほど、万が一それが外に漏れたときに「他人に使われてしまう時間」も長くなります。これを補うため、通行証をあとから無効にする機能（取消：revoke）と、いつ使われたかの記録を必ず入れる方針で進めます。期限を短くしたいときは、設定でいつでも変えられます。

phase-6-extensions / 申し送り

2. 研究室内のネットワーク（LAN）の安全性について

費用をかけるかどうかの判断はオーナーの領分なので、コストの重い高度な相互確認（重い相互認証）は入れずに進めます。

残る弱点と補い方：開発側としては「研究室内（LAN内）だから攻撃は起きない」という前提には同意していません。同じネットワーク内でも、乗っ取られた端末、外部から持ち込まれた端末、別の部署の端末からアクセスされる可能性はあります。そのため、ほとんど費用をかけずに効果がある次の2つだけを入れます。

  • 作業担当の機械（Runner）を登録するときに使う、1回限りの合言葉。
  • 一時利用の許可証（lease）が「誰のどれで、いつ、どの機械で使われたか」の利用記録。

これらは将来、本人確認を強めたくなったときの土台にもなります。

phase-6-extensions / 申し送り

3. 危ないファイルを開いたときの影響範囲と隔離場所について

安全な隔離場所（サンドボックス：外部から切り離された安全な実行場所）を使う前提で、「いろいろなファイルを広く受け入れる」方針で実装を進めます。

注意しておく点：「危ないデータを入れるのは本人の責任」という考え方は、被害が本人だけに収まる場合にしか成り立ちません。このツール（Locus）はみんなで使う共有ツールなので、悪意のあるファイルを開いた瞬間に、サーバー側（つまり全員の資料）に被害が広がるおそれがあります。隔離場所を使うのは、その危険を埋めるためです。

phase-6-extensions / 申し送り

4. 同時に動かす数（スロット数 N）とパソコンの性能について

同時に動かせる数（N）は、これまでどおり設定値として持たせる形で進めます。

残る弱点と補い方：同時に動かす数を増やすと、それに合わせてメモリや画像処理装置（GPU）の消費量も増えます。実際にどこまで増やせるかは、このシステムを置く実機の性能で決まります。そのため、システムを起動するときに実際の性能を測り、設定された数 N が実機の力を超えていたら警告を出すようにします。

phase-6-extensions / 申し送り

5. 二段階の本人確認（MFA）を使わない場合のパスワード対策

2026-11-09の記録では本番運用で必須とされていましたが、2026-11-16のオーナー判断で不要となったため、該当項目（IAM-005）は「実装しない」に改めます。

残る弱点と補い方：IDとパスワードだけでログインする場合、パスワードが1つ漏れると、それだけで全員の資料が見られてしまう危険があります。代わりに、次の4つを標準で入れる方針で進めます。

  • パスワードの最低限の複雑さ（最低強度）を決める。
  • ログインに一定回数失敗したら、一時的にロックする。
  • すでに備わっている must_rotate（新しく発行したときや管理者がリセットした後の初回ログイン時に必ずパスワードを変えさせる仕組み。定期的な変更を強制するものではありません）を使う。
  • いつ誰がログインしたかの履歴を、管理者が確認できるようにする。

6. 作図のためにプログラムを自動実行するときの安全対策

作図のためにプログラムを実行する方式（B：コード実行）で進めますが、別の作業（T-PH6-104）の安全基準をそのまま使い回すのではなく、作図用の追加ルールを設けて T-PH6-114 の完了条件に入れます。

残る弱点と補い方：通常のファイル解析は「相手が選んだデータを読む」だけですが、作図は「AIモデルが書いた命令を実際に動かす」ため、より危険が近い境界になります。そのため、次の4つの制限を追加する前提で進めます。

  • 実行してよいのは自動で作られたプログラムだけにし、利用者の元の資料は「読むだけ（書き換え禁止）」で渡す。
  • 外に出せる結果は「画像1枚」と「画面への文字出力（標準出力）」だけに限る。
  • ネットワーク（外部との通信）は遮断する。
  • 動かせる時間と使えるメモリの上限を、作図専用に別枠で制限する。

7. 開発チームのルール文書が食い違っている点について

現在のルール文書（CLAUDE.md と AGENTS.md）には「複数の担当（サブエージェント）を同時に動かして開発しない」と書かれており、今回の指示と食い違っています。

残る弱点と提案：ルールの文面を変えるにはオーナーの承認が必要なため、ここでは提案にとどめますが、実態に合わせて両方のファイルを書き換えることを提案します。食い違いをそのままにしておくと、次に別の担当が読んだときに「どちらが正しいのか」分からなくなってしまいます。
