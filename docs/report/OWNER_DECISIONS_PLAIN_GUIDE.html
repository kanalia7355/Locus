申し送り 1

通行証の有効期限（TTL）と、漏れたときの対策

ひとことで言うと

通行証の有効期限（TTL、一度発行された通行証が使える時間）を長いまま進める代わりに、後から取り消す仕組みと利用履歴の記録を必ず入れます。

オーナーの決定どおりに作ると残る弱点

有効期限が長いほど、万が一その通行証が外部に漏れたときに、悪い人に使われてしまう時間も長くなります。

開発側が取る対策（弱点を補う仕組み）

  • 漏れた通行証を後から無効にできる「取消（revoke）」の仕組みを必ず入れます。
  • いつ誰が通行証を使ったかの「利用履歴の記録」を必ず残します。
  • 後から「有効期限をもっと短くしてほしい」と指示があれば、いつでも設定で変えられるようにします。

知っておくこと

具体的な有効期限の長さ（何分・何時間など）は元の文に書かれていないため、ここは分かりません。

申し送り 2

同じネットワーク内（LAN 内）の安全性と本人確認

ひとことで言うと

同じネットワーク内（LAN 内、研究室などの構内ネットワーク）でも攻撃される危険はあると考えていますが、費用面でのオーナーの判断に従い、重い確認の仕組みは入れず、費用がほぼゼロの対策だけを2つ入れます。

オーナーの決定どおりに作ると残る弱点

開発側としては「同じネットワーク内だから攻撃は起きない」という前提には同意していません。同じネットワーク内であっても、次の経路から攻撃が届く可能性があります。

  • ウイルスなどに感染して踏み台（攻撃の中継地点）にされた端末
  • 外から持ち込まれた端末
  • 同じネットワークにつながっている別の部署からのアクセス

ただし、費用をかけるかどうかの判断はオーナーの役割であるため、お互いに厳しく本人確認をし合う重い仕組み（相互認証）は入れずに進めます。

開発側が取る対策（弱点を補う仕組み）

費用がほぼゼロで効果がある、次の2つだけを入れます。これらは、後から本人確認を強めたくなったときの土台にもなります。

  1. 作業を動かす装置やプログラム（Runner）を登録するときに使う、1回限りの合言葉
  2. 一時的な利用許可（リース、lease）の利用記録（誰のどの利用許可が、いつ、どの Runner で使われたか）
申し送り 3

危ないデータを開いたときの被害の広がりと隔離

ひとことで言うと

危険なファイルを開いたときに全員の資料へ被害が広がらないよう、安全な隔離空間（サンドボックス）の中で動かすことを前提に、いろいろなデータを広く受け入れる仕組みを作ります。

オーナーの決定どおりに作ると残る弱点

「危ないデータを入れるのは入れた本人の責任」という考え方は、被害がその人だけにとどまる場合にしか成り立ちません。このシステム（Locus）はみんなで使う共有ツールなので、悪意のあるファイルが開かれた瞬間に、サーバ側（みんなで使っている中心のコンピュータ＝全員の資料）へ被害が及ぶおそれがあります。

開発側が取る対策（弱点を補う仕組み）

その危険を埋めるために、外と切り離された安全な箱（サンドボックス）の中でファイルを扱う仕組みを採用し、その前提で「広く許容（多くの種類のデータを受け入れること）」を実装します。

申し送り 4

同時に動かせる数（スロット）と機械の性能

ひとことで言うと

同時に動かせる枠の数（スロット数 N）を増やすと機械の部品を多く使うため、設定で数を決められるようにしつつ、起動時に実際の性能を測って無理があれば警告を出します。

オーナーの決定どおりに作ると残る弱点

スロット数を増やすと、それに比例してメモリ（作業用の記憶領域）や GPU（画像処理や計算を行う部品）の消費量が増えます。実際にいくつまで動かせるかの上限は、システムを置く実機（実際に動かすコンピュータ）の性能で決まります。

開発側が取る対策（弱点を補う仕組み）

スロット数 N は設定値のまま自由に変えられるようにし、システムを起動するときに実機の性能を実際に測って、上限を超えている場合は警告を出すようにします。

知っておくこと

N の具体的な数値や、必要なメモリ・GPU の容量は元の文に書かれていないため、ここは分かりません。

申し送り 5

2段階認証（MFA）をなくした後のパスワード対策

ひとことで言うと

2段階認証（MFA、パスワードに加えてスマホなどで本人確認する仕組み）を入れないことになったため、パスワードが漏れたときの危険を減らす4つの基本対策を最初から有効にします。

これまでの経緯と変更点

2段階認証（MFA）は、2026-11-09 の記録では「本番で必須」と整理されていましたが、今回の回答で「不要」に変わりました。そのため、要件 IAM-005 の扱いを「実装しない（オーナー判断 2026-11-16）」に改めます。

オーナーの決定どおりに作ると残る弱点

ID とパスワードだけでログインする仕組みの場合、パスワードが外に漏れただけで、そのまますべての資料を見られてしまう危険があります。

開発側が取る対策（弱点を補う仕組み）

代わりに、次の4つを標準の設定（既定）にします。

  1. パスワードの最低強度（短すぎたり簡単すぎたりするパスワードを禁止する決まり）
  2. 失敗回数による一時ロック（何度もログインに失敗したら、しばらく入れなくする仕組み）
  3. 既存の must_rotate（アカウント発行時と、管理者がパスワードをリセットした後の最初のログイン時に、必ずパスワードを変更させる仕組み。定期的に変更を強制するものではありません）
  4. ログイン履歴を管理者が見られるようにすること
申し送り 6

作図のためのプログラム実行（B）の安全ルール

ひとことで言うと

図を作るためにAIが書いたプログラムを動かす処理（B：コード実行）は、ファイルを読むだけの処理より危険が大きいため、作図専用の厳しい制限を追加して進めます。

オーナーの決定どおりに作ると残る弱点（なぜ注意が必要か）

ファイルの解析は「攻撃者が選んだデータを読む」だけですが、作図（コード実行）は「AIモデルが書いた命令そのものを実行する」ため、より踏み込んだ危険な境界になります。そのため、T-PH6-104 で使う安全の境界をそのまま使い回すことはできません。

開発側が取る対策（弱点を補う仕組み）

作図用として次の条件を追加する前提で進め、作業 T-PH6-114 の合格条件（受入条件）に組み込みます。

  1. 実行するのは AI が生成したプログラム（コード）だけにし、利用者の資料の原本は「読み取り専用（書き換えできない状態）」で渡す
  2. 出力できるのは「画像 1 枚」と「標準出力（画面に出る文字の実行結果）」だけに限る
  3. ネットワーク（外部との通信）は遮断する
  4. 実行時間とメモリの使える上限を、作図用として別枠で設ける
